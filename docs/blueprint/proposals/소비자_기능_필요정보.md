# 소비자 기능과 전체 구조 토의 자료

상태: **토의 자료. 미확정.** 2026-10-10

- 논의 순서(사용자 지정): **소비자 기능 → 전체 구조와 레이어 → 레이어 간 연결 → 세부 데이터 모델**. 이 문서는 앞의 두 단계 자료다. 레이어와 데이터 모델은 정하지 않는다.
- §1·§2·§3은 사용자가 제시한 방향을 옮긴 것이다(§3은 2차 토의). §4는 구현자 의견, §5·§6은 조사 결과를 경험별로 다시 읽은 것이다. 모두 합의 전이다.
- 근거 조사: [2026-10-10 공시 출처 조사](../../research/2026-10-10_source_survey/README.md). 데이터 모델 쟁점은 [데이터 모델 토의 보완안](데이터모델_토의_보완안.md)에 보류 상태로 있다.

## 1. 온전이 돕는 판단 (사용자 제시)

> 온전은 소비자가 "왜 이 보험이 필요한지, 다른 상품과 무엇이 다른지, 어떤 상황에서 얼마나 받을 수 있는지"를 스스로 판단하게 만드는 서비스여야 한다. 약관을 쉽게 요약하는 것만으로는 부족하고, 그 내용을 자기 상황에 적용할 수 있어야 한다.

핵심 기능(사용자 제시):
1. 자기 상황에 필요한 보험과 보장을 이해한다.
2. 원하는 보장을 보험사별로 비교한다.
3. 특정 사건에서 자기 계약으로 받을 수 있는 금액과 조건을 확인한다.
4. 이 과정을 복잡한 약관을 직접 읽지 않아도 직관적으로 수행한다.

## 2. 중심 흐름과 여섯 경험 (사용자 제시)

**중심 흐름:** 내게 필요한 보장 찾기 → 같은 조건으로 상품 비교 → 사건을 넣어 작동 확인. 기존 계약이 있는 사람은 "내 보험 확인"에서 바로 들어온다.

| 경험 | 소비자에게 보이는 것 | 지켜야 할 것 |
|---|---|---|
| E1. 상품을 고르기 전에 감당하기 어려운 상황 찾기 | 짧은 질문("치료 때문에 일을 쉬면, 생활비를 얼마나 버틸 수 있나요?")에서 시작. 부양가족, 소득 중단 대비, 이미 가진 보장, 걱정하는 상황을 이어서 보험으로 보완할 부분과 스스로 감당할 수 있는 부분을 보여 준다 | 답하지 않은 정보는 미확인으로 남긴다. "지금은 추가 가입이 필요하지 않을 수 있어요"도 말할 수 있어야 한다 |
| E2. 상품보다 같은 상황에서의 차이 비교 | "이 진단을 받으면 A·B·C 상품은 각각 어떻게 처리하나요?" 첫 화면에 차이 나는 항목부터: 보장하는 범위, 지급 제한, 지급 횟수·한도, 유지 조건(갱신·종료·보험료 변화), 가격(어떤 가입 조건의 금액인가) | 공통 내용은 접는다. 종합점수로 줄 세우지 않고, 본인이 중요하게 보는 조건으로 비교한다 |
| E3. 사건을 넣으면 계산 과정까지 보여 주기(대표 기능 후보) | 필요한 정보만 차례로 묻는다. 결과를 셋으로 나눈다: 현재 입력과 확인된 약관으로 계산한 금액 / 추가 확인에 따라 달라질 수 있는 금액 / 계산에서 제외된 담보와 이유. 큰 숫자 아래 "왜 이 금액인지". 가입일·사건일을 바꾸면 면책·감액 때문에 결과가 어떻게 달라지는지 확인 | 실제 지급 확정과 약관 기반 계산을 화면에서 분명히 구별한다 |
| E4. 내 보험이 작동하는 지도 | 담보명 수십 개 대신 진단·치료·입원·회복·일을 쉬는 기간·간병 같은 생활의 흐름으로 펼친다. 상황을 누르면 관련 보장이 모이고 조건과 금액을 확인한다 | 빈칸을 곧바로 "부족"이라고 하지 않는다. 보장 없음, 자료 없음, 적용 여부 미확인을 다르게 보여 준다 |
| E5. 갈아타기 전에 얻는 것과 잃는 것 | 현재 계약과 바꿀 계약을 나란히 놓는다. "이 보장은 넓어지지만, 이 조건은 달라져요." 보험료 외에 없어지는 보장, 새 가입 조건, 면책·감액, 유지·해지 조건 | 자료가 부족하면 비교를 완성한 척하지 않고 무엇을 더 확인해야 하는지 알린다 |
| E6. 설명 검증(후속) | 설계안·설명 문구를 넣으면 약관과 대조한다. 결과는 근거로 확인됨 / 조건이 빠져 있음 / 자료로 확인할 수 없음. 상담 자리에서 물을 질문을 만들어 준다 | 사람을 평가하지 않는다 |
| 공통 | 한 번 눌러 근거 보기: 짧은 결론 → 조건 펼치기 → 정확한 원문 위치 | — |

**전체 구조에 대한 사용자 제안(1차, §3에서 구체화):** 보험 지식 기반 위에 **필요성 판단·상품 비교·사건 계산** 세 기능을 구분하고, 앱이 이를 하나의 자연스러운 흐름으로 잇는 안부터 논의한다. 필요성 판단은 약관 데이터와 계산 엔진만으로 저절로 나오지 않으므로 별도의 판단 기능이 필요하다. 지급액 계산은 확인된 계약 조건과 규칙을 정확하게 적용해야 한다. 상품 ID와 병합 규칙은 이 기능들이 요구하는 정확성과 이력 추적을 뒷받침하는 하위 설계로 다룬다.

## 3. 사용자가 제안한 전체 구조 (2차 토의, 사용자 제시)

### 3.1 바로잡은 세 가지

1차 분석(구현자)에서 아래 세 가지를 바로잡았다.

| 1차 분석 | 바로잡은 내용(사용자) |
|---|---|
| 상품 비교는 사건 계산의 엔진을 쓴다 | **상품 비교 전체가 계산 엔진을 필요로 하지는 않는다.** 보장 범위·면책·갱신·가격 조건 비교는 지식 조회로 할 수 있다. "같은 사건에서 얼마를 받는가"를 비교할 때 계산 엔진을 쓴다 |
| 필요성 판단·상품 비교·사건 계산의 요구 정확성이 다르다 | **가상 상품 비교와 내 계약 계산의 정확성 기준은 같아야 한다.** 다른 것은 입력의 성격이다. 하나는 명시한 가정이고, 다른 하나는 확인한 실제 계약·사건이다 |
| 약관을 확보하면 담보 조건을 비교할 수 있다 | **약관을 확보했다고 바로 비교할 수 있는 것은 아니다.** 적용 범위·특약 구성·질병 정의를 해석하고, 서로 대응하는 비교 항목인지 확인해야 한다 |

기존 설계와의 관계: 상태 어휘의 기능 자격(`capability`)은 이미 `compare_conditions`(같은 비교축으로 조건 비교)와 `simulate`(규칙 엔진으로 상황 계산)를 독립된 값으로 둔다. 하나가 다른 것을 자동으로 켜지 않는다(ADR-0012). 첫 번째 정정과 같은 방향이다.

### 3.2 영역

| 영역 | 구성 | 책임 |
|---|---|---|
| 공개 자료 기반 | 발견·수집·원본 보존·문서 복원 | 무엇을 어디서 언제 확보했는지 증명 |
| 보험 지식 기반 | 상품·담보·조건·가격·관계·검수·버전 | 보험이 무엇을 보장하고 어떤 조건으로 작동하는지 표현 |
| 판단 기준 | 필요성 평가 기준·참고 통계·사용자 가정 | 어떤 상황에서 무엇을 우선 고려할지 설명 |
| 판단 기능 | 필요성 분석·상품 비교·사건 계산 | 지식과 입력을 결합해 소비자의 질문에 답함 |
| 사용자 경험 | 질문 흐름·비교 화면·보장 지도·근거 보기 | 복잡한 내부 구조를 이해하기 쉬운 행동으로 제공 |
| 비공개 개인 영역 | 내 계약·상황·선호·동의·사건 기록 | 개인 정보를 보관하고 필요한 기능에 최소한으로 제공 |

보험 지식과 판단 기준은 나눈다. "이 특약은 이런 경우에 지급한다"는 약관 해석이고, "당신은 이 보장을 우선 고려할 만하다"는 가정과 가치 판단이 들어간 결론이다. 둘 다 근거와 버전을 남기되, 소비자에게 같은 종류의 사실처럼 보여 주지 않는다.

### 3.3 소비자 행동으로 본 연결

| 행동 | 흐름 | 지켜야 할 것 |
|---|---|---|
| ① "나한테 뭐가 필요해?" | 개인 상황·걱정·기존 계약 → 필요성 분석 → 우선 살펴볼 보장과 이유 | 처음부터 소득·자산·가족력을 모두 요구하지 않는다. 적은 입력으로 시작해서 결론을 바꿀 때만 추가로 묻는다. 보험을 더 가입하지 않는 선택도 결과에 넣는다 |
| ② "그 보장을 어느 보험사에서 들까?" | 원하는 보장·선호·예산 → 상품 비교 → 조건 차이와 적용 가능한 가격 | 지식 기반에서 직접 조건을 비교하고, 필요하면 같은 시나리오를 여러 상품에 적용해 지급액을 비교한다. 계산을 지원하지 않는 상품도 확인된 조건 비교에는 남는다 |
| ③ "이 일이 생기면 나는 얼마를 받아?" | 개인 계약·사건·시점 → 적용 조건 확인 → 계산 → 금액과 미확인 사항 | 상품 비교와 같은 규칙 실행 엔진을 쓰되, 실제 계약의 특약·변경 이력·개인별 조건을 적용하는 과정이 더해진다 |

### 3.4 AI의 역할

AI는 사용자의 말을 이해하고, 필요한 질문을 고르고, 근거 있는 결과를 설명한다. 지급액·가격·적용 조건은 검증된 데이터와 규칙으로 산출하고, AI가 대화 중에 임의로 만들어 내지 않는다.

### 3.5 중심 원칙 후보와 가장 큰 선택

**중심 원칙(사용자 제시. 정본 기록 여부는 확인 전):**

> 온전의 설명은 사용자를 겁줘서 가입시키거나 미리 정한 상품으로 유도하는 방향으로 흐르지 않는다. 추가 가입·현재 유지·보류 중 어느 선택이든, 본인이 이유를 이해하고 결정할 수 있게 한다.

**가장 큰 선택: 필요성 분석이 어디까지 결론을 내리는가.** 사용자 의견은 다음과 같다. 살펴볼 보장과 그 이유를 제시하고, 상품 후보와 선택의 득실까지 비교해 준다. 다만 하나의 종합점수로 "당신의 정답 상품"을 단정하지 않는다. 상품에 점수를 매기는 대신, 사용자가 중요하게 여기는 조건으로 좁혀 간다.

예시(사용자 제시):

> A는 매달 부담이 적어요. 대신 이 상황은 보장하지 않아요.
> B는 그 상황까지 보장해요. 다만 표시된 보험료가 본인에게 적용되는지는 추가 확인이 필요해요.

**모든 제안에 따라붙는 네 가지(사용자 제시):**

| 보여 줄 것 | 소비자가 이해할 내용 |
|---|---|
| 제안 이유 | 내 어떤 상황·선택 때문에 이 보장을 보여 주는가 |
| 선택의 득실 | 무엇을 얻고, 어떤 비용·제한을 받아들이는가 |
| 확인되지 않은 것 | 무엇을 더 알아야 판단이 달라질 수 있는가 |
| 근거 | 어느 계약 조건·공시·사용자 입력에 기반하는가 |

판단 기능이 앱에 넘기는 결과는 추천 상품 목록이면 부족하다. 후보, 제안 이유, 조건별 차이, 미확인 사항, 원문 근거를 함께 넘겨야 앱이 직관적으로 풀어낼 수 있다. 정보를 끝없이 늘어놓지 않고, 지금 선택을 바꿀 만한 근거부터 보여 준 뒤 차례로 펼친다.

기존 설계와의 관계: 상태 어휘의 `plan_action`(초안 행동: `keep` 유지, `add` 추가 검토, `remove` 제외 검토)은 "사용자가 이 초안에서 무엇을 하려는가. AI가 정답으로 지정하지 않는다"로 정의되어 있다. SYSTEM_CONTRACT §1은 "소비자가 '추가 가입하지 않겠다'고 판단해도 정상 성과"라고 한다. 중심 원칙 후보와 같은 방향이다.

### 3.6 3차 토의: 세 가지 다듬기와 결과의 공통 구조 (사용자 제시)

**합의된 제품 방향(사용자):** 점수로 정답을 대신 정하지 않고, 소비자가 선택할 근거와 득실을 이해하게 한다. 정렬 순서와 자료 확보 편향도 소비자의 판단에 영향을 주므로 설계에 넣는다. ADR 반영은 전체 구조를 정리할 때 묶어서 한다.

**다듬은 세 가지**

1. **확보율은 상품 평가와 분리한다.** 자료가 많은 상품이 더 좋은 상품처럼 보이면 안 된다. 화면에는 다음을 나눠 보인다.
   - 비교 범위: 이번에 어떤 회사·상품까지 비교했는가
   - 상품별 확인 상태: 보장 조건·가격·계산 중 무엇을 확인했는가
   - 빠진 후보: 무엇을 비교하지 못했고 이유는 무엇인가

   분모도 모르는데 확보율을 퍼센트로 만들면 또 다른 가짜 점수가 된다. 첫 화면은 짧게 알리고 세부 범위는 펼쳐 보게 한다.
2. **사용자에게 확인받을 것은 사용자의 사실과 의도다.** "갑상선암을 유사암으로 분류해도 될까요?"라고 묻는 것은 약관 해석 책임을 사용자에게 넘기는 일이다. 사용자에게는 진단 내용·날짜·서류에서 읽은 내용을 확인받는다. 그 진단을 해당 계약에서 어떻게 분류하는지는 보험 지식과 규칙이 근거를 갖고 처리한다. 자료가 부족하면 필요한 자료를 알려 준다.
3. **AI도 판단을 도울 수 있지만, 확정 권한은 구분한다.** AI는 질문을 고르고, 사용자 선호를 해석하고, 설명과 후보 비교를 구성할 수 있다. 약관 사실·가격·지급액을 임의로 확정하거나 모르는 조건을 채워 넣으면 안 된다. 모든 대화를 고정 규칙으로만 처리하려고 하면 직관적인 경험을 만들기 어렵다.

**첫 화면 원칙(사용자):** 처음부터 과한 정보를 주지 않는다. 처음에는 깔끔하게 정리된 필요 최소한의 정보만, 아주 읽기 쉬운 형태로 전달한다.

**판단 결과의 공통 구조(사용자 제안):**

| 결과 구성 | 담을 내용 |
|---|---|
| 기준선 | 현재 계약·현재 상황, 또는 가입하지 않은 상태 |
| 후보·선택 | 추가 가입·유지·보류 등 검토할 선택 |
| 이유와 차이 | 어떤 입력 때문에 제시됐고, 선택하면 무엇이 달라지는지 |
| 근거 | 약관 사실·사용자 입력·판단 기준·계산 결과의 구분 |
| 불확실성 | 무엇을 모르며, 확인하면 어떤 결론이 바뀔 수 있는지 |
| 다음 행동 | 비교 조건 변경, 추가 질문, 서류 확인, 근거 열기 |

화면은 이 정보를 한꺼번에 보여 주지 않는다. 사용자의 현재 질문에 맞춰 필요한 부분부터 보여 준다. 이렇게 연결하면 데이터·판단 기능·AI·UX가 각각 무엇을 책임지는지가 선명해진다.

## 4. 구현자 의견 (합의 전)

### 4.1 동의하는 부분

- 세 가지 정정에 동의한다. 1차 분석의 해당 부분(정확성 기준 표, "같은 엔진" 관찰, "약관을 확보하면 비교 가능")은 이 절로 대체한다.
- 보험 지식과 판단 기준을 나누는 데 동의한다. 이 구분은 데이터 모델 토의 보완안의 원칙("출처가 보여 준 사실과 우리가 내린 판단을 따로 기록한다")과 같은 방향이다. 지식 기반 안에서도 관측과 판단이 나뉘고, 그 위에 판단 기준이라는 또 다른 종류의 판단이 있다.

### 4.2 이 구조에서 더 살펴볼 점

1. **비교 항목의 대응도 판단이고, 지식 기반에 남아야 한다.** 정정 3에 따르면 "A의 암진단비와 B의 암진단비는 같은 비교 항목이다"는 해석과 확인을 거친 결론이다. 조회할 때마다 계산하는 것이 아니라, 근거·검수 상태·판을 가진 판단으로 지식 기반에 두는 것이 맞아 보인다. 대응이 확인되지 않은 항목은 비교 화면에서 "차이 없음"이 아니라 "대응 미확인"으로 보여야 한다.
2. **결과 안의 주장 종류를 구분해서 넘겨야 한다.** 앱이 "약관 사실"과 "판단 기준에 따른 제안"을 같은 사실처럼 보이지 않으려면, 판단 기능이 넘기는 결과의 각 문장·숫자에 종류가 붙어 있어야 한다. 종류 후보는 약관·공시에서 확인한 사실, 판단 기준에 따른 평가, 사용자가 명시한 가정, 규칙 계산 결과, 미확인이다.
3. **"결론을 바꿀 때만 추가로 묻기"는 판단 기능이 알려 줘야 한다.** 어떤 미확인 입력이 결론을 바꿀 수 있는지는 판단 기능만 안다. 사건 계산 쪽은 기존 엔진의 3값 판정과 빠진 입력 목록이 이에 대응한다. 필요성 분석도 "이 입력에 따라 결론이 달라진다"를 결과에 담아야 AI가 그 질문을 고를 수 있다. AI는 질문을 고르고 다듬을 뿐, 어떤 입력이 결론을 바꾸는지를 스스로 판단하지 않는다.
4. **(3차에서 정정, §3.6-2)** ~~AI가 사용자 말을 구조화한 결과는 사용자에게 되돌려 확인받아야 한다. "갑상선암"을 유사암으로 볼지 확인받는다.~~ 확인받을 것은 사용자의 사실과 의도이고, 분류는 지식과 규칙이 근거를 갖고 한다. 남는 의견: AI 설명문이 결과에 없는 숫자·기간·예외를 말하면 막는다. 기존 DATA_PIPELINE_CONTRACT §6의 릴리스 검사를 대화 중 설명에도 적용하는 셈이다.
5. **점수가 없어도 순서와 후보 선정은 유도가 될 수 있다.** 목록의 첫 번째 자리는 그 자체로 추천처럼 읽힌다. 그래서 정렬은 사용자가 고른 조건에 따라야 하고, 그 기준을 화면에 보여야 한다. 또 **후보가 어떤 범위에서 나왔는지**를 밝혀야 한다. 조사 결과 자료 확보가 회사마다 크게 다르다. 생보협회 비교공시는 robots 금지이고, 몇몇 회사는 문서 서버나 다운로드가 막혀 있다. 그러면 자료를 얻기 쉬운 회사의 상품만 후보에 자주 오르는, 의도하지 않은 유도가 생길 수 있다. 후보에는 "확보한 자료 범위에서"라는 한계가 따라붙어야 한다. **(3차에서 정정, §3.6-1)** 확보율을 퍼센트로 붙이자는 부분은 철회한다. 비교 범위·상품별 확인 상태·빠진 후보로 나눠 보인다.
6. **가정 계산과 실제 계약 계산의 정확성이 같으려면, 상품 쪽도 약관 판과 적용 범위가 확인되어 있어야 한다.** 가정이 명시되어 있어도, 상품 트윈의 약관 판이 모호하면(조사 사례 4·5처럼 판매기간 안의 약관 교체) 가상 비교의 결과도 그만큼 미확인이 된다. 가정은 사용자가 바꿀 수 있는 입력이고, 약관 판의 불확실성은 가정이 아니다. 둘을 화면에서 섞지 않아야 한다.
7. **"현재 유지"와 "보류"를 같은 무게로 보여 주려면 비교의 출발점이 현재 상태여야 한다.** 기존 계약이 있으면 현재 계약이 비교의 기준선이 되고, 추가·교체는 그 기준선 대비 득실로 보인다. 기존 계약이 없으면 "가입하지 않음"이 기준선이다. 이 기준선도 결과에 들어 있어야 한다.

### 4.3 판단 기능이 앱에 넘기는 결과에 들어갈 것(후보)

**(3차에서 §3.6의 공통 구조로 대체됨.** 아래는 2차 토의 때의 구현자 후보로, 이력으로 남긴다.**)** 사용자가 제시한 네 가지에, 위 관찰에서 나온 것을 더한 후보다. 형식은 정하지 않는다.

| 항목 | 내용 |
|---|---|
| 선택지 | 추가 검토·현재 유지·보류(또는 교체) 각각. 기준선 포함 |
| 후보 | 상품 후보와 그 후보가 나온 범위(자료 확보 범위, 판매 상태, 같은 조건 여부) |
| 제안 이유 | 어느 사용자 입력·선택과 어느 판단 기준(판)에서 나왔나 |
| 득실 | 조건별 차이(대응이 확인된 비교 항목만, 미확인 항목은 따로) |
| 확인되지 않은 것 | 결론을 바꿀 수 있는 입력이 먼저. 사용자 가정과 자료의 불확실성을 구분 |
| 근거 | 계약 조건·약관 위치·공시 행·사용자 입력·판단 기준의 판 |
| 주장 종류 | 사실 / 판단 기준에 따른 평가 / 사용자 가정 / 계산 결과 / 미확인 |
| 정렬 기준 | 사용자가 고른 조건. 우리가 매긴 점수가 아님 |

### 4.4 공통 결과 구조에 대한 구현자 의견 (3차, 합의 전)

**1) 첫 화면 최소 원칙에 동의한다. 조건이 하나 있다.** 최소 정보에도 결론을 뒤집는 조건은 들어가야 한다. 기존 SYSTEM_CONTRACT §3도 "금액을 뒤집는 제외·감액을 더보기로 숨기지 않는다"고 한다. 둘을 함께 지키려면, 판단 기능이 결과의 각 항목에 **결정적(지금 선택이나 금액을 바꿈) / 보조**를 표시해 넘기고, 화면은 결정적 항목만 첫 화면에 올리면 된다. 첫 화면의 최소 구성 후보는 다음과 같다: 결론 한 줄, 그 결론을 뒤집을 수 있는 조건 하나, 범위 한 줄, 다음 행동 하나.

**2) 공통 구조에 더하면 좋을 것(후보)**

| 후보 | 이유 |
|---|---|
| 범위(비교 범위·상품별 확인 상태·빠진 후보) | §3.6-1의 세 가지가 들어갈 자리다. "무엇을 모르나"(불확실성)와 "어디까지 봤나"(범위)는 다른 질문이라 나누는 편이 화면에서도 읽기 쉽다. 불확실성의 하위 항목으로 둘 수도 있다 |
| 근거 종류에 "공시 사실" | 가격·판매 상태·판매기간은 약관이 아니라 공시 목록에서 온다. 약관 사실과 출처·확인 방법이 다르다 |
| 판 참조(지식 릴리스·판단 기준의 판·규칙의 판) | 같은 결과를 다시 만들고, 판단이 정정되면 지난 결과를 쓴 사용자에게 알리기 위해 필요하다(기존 뷰모델의 `release_id`·`input_hash`와 같은 원리) |
| 항목별 결정성 표시 | 위 1)의 첫 화면 구성을 위해 |
| 다음 행동과 불확실성의 연결 | "서류 확인"이 어떤 불확실성을 줄이고, 확인 결과에 따라 결론이 어떻게 갈리는지가 이어져 있어야 사용자가 그 행동을 할 이유를 안다 |

**3) 세 기능에 채워 보기(예시, 합의 전)**

| 구성 | 필요성 분석 | 상품 비교 | 사건 계산 |
|---|---|---|---|
| 기준선 | 현재 계약이 덮는 범위, 또는 가입하지 않은 상태 | 현재 계약, 또는 가입하지 않은 상태 | 내 계약(판매 구성·적용 약관) |
| 후보·선택 | 살펴볼 보장, 추가 검토·유지·보류 | 상품 후보와 각각의 조건 | 받을 수 있는 담보와 그렇지 않은 담보 |
| 이유와 차이 | 어떤 입력(부양가족, 걱정하는 상황 등)이 이 보장을 보게 했나 | 대응이 확인된 비교 항목의 차이 | 어느 조건이 작동해 이 금액이 됐나 |
| 근거 | 판단 기준(판), 사용자 입력, 기존 계약의 약관 사실 | 약관 사실, 공시 사실(가격·판매 상태), 시나리오 계산 결과 | 약관 사실, 사용자 사실, 계산 결과 |
| 불확실성 | 답하지 않은 입력 중 결론을 바꾸는 것, 기존 보장의 미확인 부분 | 대응 미확인 항목, 가격 조건의 적용 여부 | 결론을 바꾸는 미확인 사실, 그 기간 약관 미확인 |
| 다음 행동 | 추가 질문, 비교로 이동 | 비교 조건 바꾸기, 사건 넣어 보기, 근거 열기 | 서류 확인, 날짜 바꿔 보기, 근거 열기 |

**4) 책임 나누기(후보)**

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 보험 지식 기반 | 약관 사실, 공시 사실, 비교 항목 대응, 확인 상태와 판을 제공한다 | 사람에 대한 판단 |
| 판단 기준 | 우선 고려 기준과 참고 통계를 판과 근거와 함께 제공한다 | 약관 사실 |
| 판단 기능 | 공통 구조를 채운다. 결정성과 결론을 바꾸는 미확인 입력을 표시한다 | 화면 문장 |
| AI | 사용자 말과 선호를 해석해 사용자 사실·의도로 확인받는다. 다음 질문을 고른다. 결과 구조 안의 내용으로 설명과 비교 화면을 구성한다 | 약관 사실·가격·지급액·분류를 확정, 모르는 조건을 채움, 결과 구조에 없는 숫자·기간·예외를 말함 |
| UX | 현재 질문에 맞춰 결정적 항목부터 보여 주고 나머지를 펼치게 한다 | 결과 구조에 없는 내용을 만들어 냄 |

**5) 사용자에게 확인받을 사실과 의도의 예(§3.6-2를 따른 것)**

- 사건 계산에서 확인받는 사용자 사실: 진단서에 적힌 진단명, 진단서에 질병분류코드가 있으면 그 코드, 진단일, 입원·수술 날짜. 그 진단이 이 계약에서 어느 담보에 해당하는지는 지식과 규칙이 정한다. 자료가 부족하면 "진단서의 질병분류코드가 필요해요"처럼 필요한 서류를 알린다.
- 상품 비교에서 확인받는 사용자 의도: AI가 해석한 선호를 되묻는다(예: "매달 보험료보다 보장 범위를 더 중요하게 보시는 거죠?"). 그 선호로 비교를 다시 구성한다.

**6) 첫 화면 예시(상품 비교, 조사에서 나온 실제 값 사용)**

현대해상 굿앤굿1540(Hi2607)은 손보협회 비교공시에 심사 유형별로 두 행이 있고, 담보 6개와 금액은 같다([보완안](데이터모델_토의_보완안.md) §4). 공통 구조로 채우면 첫 화면은 이 정도가 된다.

> 같은 상품도 심사 방식에 따라 보험료가 달라요.
> 건강고지Ⅰ 37,820원 · 일반심사 55,480원 (남자 40세, 100세만기 20년납 기준)
> 어느 쪽이 적용될지는 확인이 필요해요. [확인하기] [근거 보기]

여기서 "확인이 필요해요"는 불확실성, [확인하기]는 다음 행동, [근거 보기]는 근거(협회 공시행)다. 심사 유형별 가입 조건의 내용은 조사하지 않았으므로 이 예시에서도 지어내지 않았다.
