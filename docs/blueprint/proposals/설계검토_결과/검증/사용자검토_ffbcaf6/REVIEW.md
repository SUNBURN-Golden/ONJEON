## F07 · 높음: 데몬의 대기·병합 후 상태에서 재개 경로가 빠졌다

위치:
- daemon_rules.json:113–115,251–269
- 04_자동개발명세.md §2
- 05_VM실행준비.md M4·M5·M7

- merge_wait에서 정의된 전이는 merged 관측뿐이다. 리뷰어/감리 복구 뒤 재배정하는 전이가 없다.
- HEAD 변경 시 재리뷰는 review_approved에만 있다. merge_wait나 audit_pending에서 바뀌면 승인 무효화·CI 재검사가 정의돼 있지 않다.
- 선행 완료는 state==merged로 검사하지만 구현 PR은 곧 audit_queued, 이후 done으로 이동한다. 그 뒤 확인하는 후속 작업은 선행이 완료됐는데도 조건을 만족하지 못한다.

- 일반적인 대기/중복 이벤트를 뜻하는 명시적 no-op이 없다. 전이표 밖 모든 조건을 returned로 보내면 정상적인 CI 대기나 중복 알림과 오류의 경계도 모호하다.

수정·수락:
작업 생명주기와 불변 완료 사실, 리뷰·감리 유효성, 병합 관측을 분리한다. 모든 활성 상태에서 HEAD/검사 변경을 처리하고, 대기 복구·중복·순서 뒤바뀐 이벤트·문서 PR·11번째 PR을 모의 시험한다. 잘못 병합된 사실은 기록하되 정상 완료로 승격하지 않는다.

## F09 · 높음: 일반 stderr/HTTP 오류를 모델 사용량 제한으로 오인할 수 있다

위치:
- daemon_rules.json:281–313
- 04_자동개발명세.md §3

http_status==429, 일반 stderr의 quota/rate limit, 모든 401/403/5xx를 전환 신호로 쓴다. 어느 제공자의 어떤 호출에서 발생했는지 조건이 없다. 테스트가 의도적으로 출력한 429, 보험사 수집 실패, GitHub 권한 오류도 모델 전환 사유로 읽힐 여지가 있다. 시험 실패로 전환하지 않는다는 규칙과 충돌한다.

수정·수락:
실행기 어댑터가 자기 모델 호출에서 관측한 구조화된 오류만 전환 신호로 발행한다. 출처·attempt·호출 ID를 검증하고, 작업 내용·테스트 출력·제3자 HTTP 오류는 전환하지 않는 음성 시험을 둔다. 원시 stderr 정규식은 제공자별 확인된 출력 채널 안에서만 보조로 사용한다.

tasks의 prereq_decisions는 병합을 막는 필드라고 정의했지만 데몬은 결정이 없으면 queued로 보내지 않는다. D-02 미정일 때 모의 제공자로 검수 코드를 작성할 수 있다는 보고와 다른 실행 결과가 된다. VM 가동 전 점검표는 R2 토큰 폐기를 전역 필수로 두어, R2 작업만 막는다는 README 차단 표와도 어긋난다.

수정·수락:
착수·실데이터 접근·병합·출시 조건을 서로 다른 필드로 나눈다. D-02 미정 상태에서 모의 구현은 실행 가능하고 실제 검수 승인만 차단되는지, R2 관련 조건 미충족 상태에서 로컬 작업은 가능한지 시험한다.

## F11 · 설계 보완 필요: 필요성 판단이 관심 담보 조회로 축소돼 있다

위치:
- 01_코드설계.md:55
- 02_구현계약.md §1.3·§2
- tasks.json T-MB-04의 blocked_by

대조:
- 전체_구조_1차_정리.md:70–74
- 통합안 X-04·D-08

원래 방향은 자기 상황에서 무엇을 고려해야 하는지 이유·득실을 보여 주고 유지·추가 없음·보류도 선택하게 하는 것이다. 새 설계는 필요성 탐색을 CoverageConcept·라벨·선택 가족력과 /v1/products로 배정한다. 판단 기준 관리, 그 판, 판단 결과와 의존성의 계약·작업은 구체화하지 않았다. D-08은 남아 있지만 작업에서는 기본 필요액 표시만 막는다고 좁혔다.

이 기능은 기본 필요액 숫자를 만드는 것보다 넓다. D-08 채택 여부가 미정이라면 구현을 확정할 필요는 없지만, 제품에서 사라지지 않도록 별도 작업과 선택에 따른 영향을 남겨야 한다.

또 01 §1의 "자유 생성은 없다(불변 원칙 7)"는 지급 조건·금액의 결정과 근거에 충실한 대화·질문 표현을 구분해야 한다. 원칙 7은 AI가 지급 조건과 금액을 결정하지 못하게 한 규칙이다.

수정·수락:
판단 기준 관리와 필요성 기능의 계약·담당 모듈·작업을 명시하거나 범위에서 제외할지 사용자에게 구체적으로 제시한다. 점수 없이 이유를 제공하고, 현재 유지·추가 없음·보류와 미확인을 보여 주는 실제 흐름을 완료 시험으로 연결한다.

## F12 · 구현 전 정합성 보완: 제약·근거·승격 상태의 정의가 서로 다르다

위치:
- 02_구현계약.md §1.2·§8
- 06_검토사항_점검.md §4.3
- T-KN-01·T-KN-02·T-OP-02

- 06은 K14~K16 보강을 말하지만 K16 정의가 없다. K14에는 코드 그래프 순환과 문서 구간 충돌이라는 다른 성질을 함께 넣었다. tasks의 검사기 산출물은 여전히 K1~K13이다.
- 새 규칙은 fixture 주장이 accepted일 수 없다고 하면서, 가정 accepted로 작성한 기존 r25가 위반 0인 골든 결과를 요구한다. 역사적 시험 프로필과 서비스 적합성 프로필을 나누지 않으면 기대값이 모순된다.
- B3/P6은 accepted 없이는 규칙을 만들지 못하게 한다. 반면 T-OP-02는 D-02가 비어 있어도 실제 상품 숫자→화면 관통을 요구하고 candidate라고 표시하면 된다고 한다. 코드 개발 가능과 실제 데이터 관문 통과를 분리해야 한다.
- basis는 약관만 허용한다고 모든 assertion 형식에 적었다. C0 지급 조건, 사업방법서의 가입 구성 제약, 공시 가격·판매 상태 등 주장 종류별 근거 정책으로 좁혀야 한다.
- 가격 조건·기준일 없으면 저장 거부라는 계약과, 공백이 있는 가격 관측을 보존하되 비교하지 않는 흐름의 관계가 불명확하다. 원시 관측 보존과 비교 자격을 분리해야 한다.

수정·수락:
제약의 단일 목록과 프로필을 만들고 문서·T-box·작업·시험이 같은 버전을 참조하게 한다. 시험용 성공, 서비스 거부, 실제 지식 승격을 따로 보고한다.

## 유지할 설계와 검증 수준 정정

유지할 수 있는 방향은 명확하다. 개인 영역 분리, 공통 엔진 재사용, 온톨로지 입력 판정과 수치 계산 분리, 주장별 근거·정정, 정보 공백과 확보 작업 분리, 이종 작성 계열을 제외한 리뷰, 시험 실패를 모델 교체 사유로 삼지 않는 원칙, 자동 병합 없음은 제품 방향과 맞는다.

B1~B8은 대부분 앞으로 구현할 명세다. 현재 코드에서 확인한 것은 rule.rs의 publication_state 허용값 및 non-fixture의 release_id/evidence_refs 필수 검사다. 이것이 실제 검수·R2 보존·서비스 승격 전체를 검증하는 것은 아니다. 문서 §9에도 C-25 상태는 "없음"으로 적혀 있다.

현재 .github/workflows/ci.yml은 기존 어휘·validation·Python·Rust 검사를 실행한다. 새 tasks/daemon 의미 검증이나 별도 workspace인 ontology runner를 실행하는 단계는 없다. CI 성공은 이번 설계 묶음의 실행 가능성을 검증한 결과가 아니다.

기계적으로 확인한 정상 항목도 있다. 작업 ID는 56개이며 미존재 선행 참조와 명시적 DAG 순환은 없다. 기존 구현계획의 실제 WP 행은 40개이고 replaces_wp에 모두 대응된다. WP01~WP54라는 번호 범위를 54개 작업으로 센 보고는 부정확하지만, 번호가 비어 있다는 이유로 기능이 누락됐다고 판단하지 않았다.

## 빌더에게 전달할 다음 작업
