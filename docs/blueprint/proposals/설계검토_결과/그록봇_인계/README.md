# 그록봇(Grokbot) 인계 준비 묶음

작성 2026-10-13 | 작성: 구현자(이 세션) | 지위: **인계 준비 자료다. 자동 개발 가동 승인이 아니다.** 가동은 이 묶음의 단계 0~3을 통과한 뒤 사용자가 결정한다. 자동 병합 권한은 없다.

## 1. 그록봇의 역할 (사용자 결정 2026-10-12)

- 그록봇은 **전령**이다. 자기 VM의 데몬으로 다음 일을 한다.
  - 지시 봉투와 결과 봉투를 전달한다.
  - 상태를 기록한다.
  - 정해진 규칙(`daemon_rules.json`)에 따라 빌더를 부르고 인계한다.
- 제품·설계·리뷰 판단은 하지 않는다. 규칙에 없는 일은 반송 코드(R-xx)를 붙여 담당자에게 돌려보낸다.
- 역할 순서는 [daemon_rules.json](../daemon_rules.json)의 `roles`를 따른다.
  - 설계·감리: Fable(백업 GPT Astra)
  - 빌더: Sonnet → Cursor CLI(Grok 4.7) → grokbuild CLI(Grok 4.7) → Devin CLI(SWE2) → Claude Code(GLM 5.3) → 모두 쓸 수 없으면 작업을 보존하고 대기
  - 리뷰: 작성한 계열을 제외한다
  - 감리: 병합 10개마다 한 번, 그리고 즉시 감리 대상

## 3. 가동 전 단계 (순서대로, 각 단계는 앞 단계 통과가 조건)

| 단계 | 할 일 | 통과 기준 | 하는 사람 |
|---|---|---|---|
| 0 VM 환경 확인 | 05 §1a 절차로 CLI마다 설치, 버전, 인증, 모델 지정을 확인한다. 05 §1b 종료 코드·구조화 오류 표를 채운다 | 05 §2 증거 기준(자기 보고는 증거가 아님)으로 "확인됨". 빌더 1개 이상, **작성 계열 밖 리뷰어 1개 이상** | 사용자(VM 계정) + 그록봇 기록 |
| 1 모의 코어 재실행 | VM에서 `tools/daemon/dry_run.py`와 `tools/tests/test_daemon_dry_run.py`를 실행한다 | 이 세션의 결과와 같다 | 그록봇 |
| 2 모의 코어 완성 | T-OP-00의 나머지 시나리오(M1~M44 중 이번에 구현하지 않은 것)를 빌더가 구현한다 | 05 §5 M1~M44 보고서 통과 | 빌더 → 독립 리뷰 |
| 3 실제 실행기 검증 | T-OP-09 R1~R22를 실행한다. 대상은 실제 CLI 프로세스, 격리 작업 트리, 시험용 원격(보호 브랜치·단기 자격)이다. 늦은 쓰기 차단, 정지 확인, 보존 실패 복구, 재시작 복구, 중복·재시도를 확인한다 | 05 §6 보고서 통과 | 빌더 → 독립 리뷰 → 감리 |

| T-CT-02 | 어휘 정본 확장 | 정본 변경 과제. 지시 봉투에 `canon_change_approval`(사용자 결정 참조)이 없으면 거부(R-13) |
| T-OP-01 | 로컬 Compose | — |
| T-TW-02 | rule-0.2 연산 7개 | 계산 의미 변경이라 즉시 감리 |

## 5. 사용자가 정하거나 준비할 것

**가동 전에 필요한 것(단계 4의 조건):**
- 한도 수치(05 §3): 과제당 비용 단위, 월 총비용 상한, 그리고 기본값을 쓸지 정하는 항목들(임대 TTL 3600초, 하트비트 300초, 동시 임대 2, 정지 확인 window_s 5초, 인계 실패 재시도 한도 사건별 3/3/0/2/3/1).
- 모델 계열 해석: Fable과 Sonnet을 같은 claude 계열로 볼지. 리뷰에서 제외할 계열이 이 해석으로 정해진다.
- VM 준비(사람): 보호 브랜치, 데몬 보존 전용 자격(preserve_credential), 빌더별 단기 쓰기 자격, 작업 트리 쓰기 금지 격리 방법, 자동 병합 끄기.
- GPT Astra(설계·감리 백업) 경로: 확인하거나 "미확인"으로 기록.

**가동을 막지 않는 것:**
- A-01(정본 문구) 정본 반영
- D-08 범위
- K17 후보
- PR #3 병합(통합할 때 처리)
- R2 토큰 폐기(T-OP-04 등 R2 단계만 막음)

## 6. 독립 리뷰 경로

이 세션의 설계 담당(Fable), 빌더(Sonnet), 구현자는 모두 claude 계열이다. 그래서 지금까지는 작성 계열 밖의 리뷰가 없었다. VM에서 Grok 4.7(Cursor CLI·grokbuild)이나 SWE2가 "확인됨"이 되면 claude 계열이 작성한 PR을 그 계열이 리뷰할 수 있다. 이것이 처음으로 생기는 독립 리뷰 경로다. 단계 0에서 이 경로를 먼저 확인한다.

## 7. 멈추는 조건 (그록봇이 판단하지 않고 멈추는 경우)

- 규칙에 없는 조건이 생기면 → 반송(return_codes).
- 비밀값 패턴이 검출되면 → 즉시 중단(R-10).
- 예산을 다 쓰면 → 새 임대를 발급하지 않는다.
- 상태가 손상되면 → 반송(R-08). 사람이 해소 기록을 남기기 전에는 재개하지 않는다.
- 인계 실패가 재시도 한도를 넘으면 → handoff_blocked. 사람의 복구 결정을 기다린다.

## 8. 아직 확인되지 않은 것

- VM 쪽 CLI, 인증, 모델, 한도 상태는 전부 미확인이다. 05 §1b 종료 코드 표도 비어 있다.
- 모의 코어는 일부 시나리오만 구현됐다. 범위는 [모의 코어 결과](#9-모의-코어-결과)에 적는다.
- 실제 실행기(T-OP-09)는 없다. 실제 프로세스 종료, 쓰기 금지 격리, 자격 회수, Git·네트워크 동작은 증명되지 않았다.
- 설계 묶음의 최신 독립 재검토(대상 12c1726 이후 수정분)는 아직 받지 않았다.

## 9. 모의 코어 결과 (빌더 Sonnet 구현, 구현자 재실행 2026-10-13)

실행 기록: [../검증/실행로그_dry_run.txt](../검증/실행로그_dry_run.txt)

- `python3 -I tools/daemon/dry_run.py --rules …/daemon_rules.json --tasks tools/daemon/mock_tasks.json --scenario all`: 종료 코드 0. 검사 278건 중 실패 0건, 명세 공백 표시 19건.
- `python3 -m unittest discover -s tools/tests`: 120개 통과(건너뜀 6). 기존 CI의 Python 시험 단계에서 자동으로 실행된다.
- 코어는 표준 라이브러리만 쓴다. I/O는 어댑터 인터페이스(`tools/daemon/core/ports.py`)로 분리했고, 모의 어댑터만 있다.
- 코어는 규칙 파일의 구조화 필드만 읽는다. 다음 세 가지로 이를 확인했다.

  - 설명 키 변경 검사: 설명 키를 바꿔도 결과가 같다.
  - 구현자 반증 검사: 재발송 조건을 줄이거나 만료 전이의 목적지를 바꾼 규칙 파일로 돌리면 시나리오가 실패한다(종료 코드 1).

**단계 2 전에 설계 담당이 고칠 명세 공백(28건, `tools/daemon/spec_gaps.py`).** 코어는 추측하지 않고 좁게 해석했으며, 해석 내용을 기록해 두었다. 주요 공백은 다음과 같다.
- 수치 필드가 "[사용자 결정 필요] 기본 N" 같은 문장이다(TTL, window_s, grace_s, max_attempts, 동시 임대 수). 숫자 필드가 필요하다.
- 전이의 side_effects와 반송 코드가 문장이라 구조화가 필요하다.
- 손상 판정과 handoff_blocked의 경계가 겹친다.
- 같은 세대의 둘째 switch_signal, 재임대 뒤 첫 하트비트, 중복 lease_granted를 받는 전이가 없다.
- 이전 세대 재전송을 "중복"으로 볼지 "늦은 봉투"로 볼지 검사 순서가 충돌한다.
- 푸시·PR 갱신의 펜싱 검사 연산이 없다.
- 사건 이름의 정본 목록이 둘로 갈려 있다.

**이 모의 검증이 증명하지 않는 것:**
- 실제 프로세스, 파일 시스템(잠금·rename·fsync), Git·원격 푸시, 네트워크, CLI, 모델 호출
- 다중 프로세스 경쟁(스레드 8개로만 시험)
- 예산 예약, 하드 스톱, 전환 신호 분류, 리뷰·감리 흐름

모두 단계 3(T-OP-09)에서 확인할 대상이다.
