# 온전 ONJEON 마스터플랜 v0.4
# 제3부. 앱·사이트 구현 계획

v0.4 추가 | 2026-10-08 | 제1부(1~21절)·제2부(22~41절)의 구현 계획

이 제3부는 v0.3의 요구사항을 "무엇으로, 누가, 어떤 순서로" 만들지로 바꾼다. 기술 선택은 전부 제안이며 `docs/decisions/`의 ADR 승인으로 확정한다. 아직 코드·크롤러·데이터베이스·배포는 없다. 규제·사업 구조 검토는 이 문서의 범위 밖이다.

제1·2부와 충돌하면 제2부 → 제3부 → 제1부 순서로 적용한다. 불변 원칙(§1)은 세 부 모두에 우선한다. 단 §56의 사용자 결정은 이 순서보다 우선하며, 아래 항목은 v0.3의 해당 부분을 대체한다.

- 첫 보험군을 정액형 진단 담보·3개 보험사로 가정한 부분(v0.3 §18, §39)은 대상 범위 전체로 바뀐다(§43).
- 증권·설계안 촬영 입력(v0.3 §3.1)은 PDF 업로드로 바뀐다(§47.2).
- 접근성을 초기부터 포함한다는 부분(v0.3 §5, §17)은 목표에서 제외한다(§51.4).
- 사람 검수·사람 정답셋을 전제한 부분(v0.3 §8, §17, §22, §30~§32, §34.2)은 AI 검수로 바뀐다(§57).
- 단계별 출시(v0.3 §18의 E~G 단계)는 단일 출시로 바뀐다. 첫 출시의 범위는 담보 데이터 수집·라벨링·디지털 트윈으로 소비자가 필요한 담보를 파악하는 것이다. 상담 연결·설계사 포털·개인 견적은 스켈레톤만 두고 뺀다(§43, §58).
- 내 설계 탭은 첨부 시안(`docs/design/내설계_기준화면.png`)을 주 기준으로 고정한다. 월 예산 슬라이더·현재 유지/보완안·담보 목록을 살린다(§44.4, `docs/design/화면_조작_설계서.md`).
- 가격은 첫 출시의 수집·비교 대상이다. 보험료는 가입 조건·특약 구성·기준일과 함께 저장한다(§47.1, `docs/masterplan/가격_수집_명세.md`).
- 체험판 웹은 만들지 않는다(§42).

## 42. 제품군: 무엇을 만드는가

하나의 앱이 아니라 세 개의 표면이다. 모두 같은 검증 릴리스 API를 쓰며 첫 출시 범위(§43.4)가 한 번에 출시된다.

| 표면 | 사용자 | 형태 | 비고 |
|---|---|---|---|
| 소비자 앱 | 소비자 | Flutter 앱(iOS·Android) | 홈·만약에·내 설계·내 정보 4탭 |
| 공개 웹 | 방문자·설계사·언론 | 정적 웹 + 일부 동적 페이지 | 소개, 작동 원리, 데이터 커버리지(소스별 일일 확인 현황), 법적 고지, 지원 |
| 관제 콘솔 | 내부 운영자 | 웹앱(인증 필수) | §14 7개 화면 + AI 검수 감사·정책 설정(§57) |

설계사 포털은 스켈레톤이다(§58). 체험판 웹과 소비자용 웹앱 전체판은 만들지 않는다. 계약·건강 정보를 다루는 흐름은 앱에만 둔다. 앱 안의 '예시로 둘러보기'는 첫 진입점(v0.3 §3.1)으로 유지한다. 별도 체험판이 아니라 앱 기능이다(가정, §56).

## 43. 대상 범위와 출시

### 43.1 대상 범위 (사용자 결정, 2026-10-08)

- **보험사:** 국내에서 보험을 판매하는 모든 보험사를 대상으로 하며 하나도 빠뜨리지 않는 것을 목표로 한다. 보험사로 분류되지 않는 공제·우체국보험 등은 분모 조사(§23, §57.6)에서 목록을 만든 뒤 포함 여부를 확정한다.
- **상품:** 모든 보험의 모든 주계약과 모든 특약. 정액형(진단·수술·입원·사망·상해·후유장해), 실손의료비(모든 세대·단체·유병자), 간병·치매·장기요양(간병인 지원 포함), 운전자·배상책임·재물·여행·자동차, 저축·연금·변액 등 종류를 가리지 않는다.
- **판매 상태:** 현재 판매 상품과 판매 중지 상품. 판매 중지 상품은 사용자가 올린 기존 계약을 상품 버전에 맞추는 데 필요하므로 포함한다(가정, §56).
- 이 결정은 v0.3의 "첫 보험군은 정액형 진단 담보, 3개 보험사" 가정을 대체한다.

### 43.2 단일 출시와 계산 가능 상태 (사용자 결정, 2026-10-08)

- 출시는 한 번이다. 첫 출시 범위(§43.4)가 완성된 상태로 나온다. MVP·베타·기능별 단계 공개는 없다. 상담 연결·설계사 포털·개인 견적 등은 스켈레톤만 두고 뺀다(§58). DNA는 설계 동결이다.
- 완성은 첫 출시 범위 기능의 완성을 뜻한다. 담보별 계산은 불변 원칙 3·5·7에 따라 AI 검수(§57)를 통과한 담보부터 켜지며, 통과하지 못한 담보는 원문 보기까지만 제공하고 "아직 계산하지 않아요"로 표시한다. 출시 게이트에 "전 담보 계산 가능"은 넣지 않는다(가정, §56).
- 수집·색인·원문 연결은 대상 전체에 적용한다. 출시 시점의 확보율을 `/coverage`에 공개하며 출시 후에도 계속 오른다. 이는 단계 출시가 아니라 검증 상태에 따른 결과다.
- 검증되지 않은 담보를 추정 금액이나 0원으로 계산하지 않는다.
- "빠짐없이"는 분모로 증명한다. 보험사·상품군·버전·문서의 기대 목록을 AI 에이전트가 먼저 만들고(§57.6) 층별 확보율을 공개한다. 분모가 완전하다는 증거가 없으면 "전수"라고 표시하지 않는다.

### 43.3 두 트랙의 병렬화

v0.3 로드맵 A~H는 순차로 읽힌다. 실제로는 두 트랙을 병렬로 간다.

- **데이터 트랙**: §39 작업 1~5. 전 보험사·전 상품 분모 조사(AI 에이전트, §57.6), 수집, 추출, AI 검수(§57).
- **제품 트랙**: 합성 픽스처로 앱·엔진·API·관제를 끝까지 동작시킨다.

제품 트랙은 데이터 트랙의 산출물을 기다리지 않는다. 합성 상품 3개(§34.1 수준의 테스트 약관을 확장)로 홈 → 만약에 → 내 설계 → 두 안 비교 → 증거 보기까지 연결한다. 데이터 트랙이 AI 검수를 통과한 릴리스를 내면 픽스처를 실데이터로 교체한다. 교체 시 화면·엔진 코드는 바뀌지 않아야 한다. 이것이 ADR-0002다.

### 43.4 출시 범위 (L1)

첫 출시의 목적은 하나다. 소비자가 자신에게 필요한 담보를 한눈에 파악하게 한다. 가장 많이 투자할 것은 네 가지다.

1. 철저한 크롤링과 일일 갱신(§59)
2. 담보 데이터 라벨링과 AI 검수(§28, §57)
3. 디지털 트윈(§10, §34)
4. 읽지 않아도 되는 직관적 UX(§60)

범위는 다음과 같다.

- **소비자 앱(Flutter):** 세 진입점(예시로 둘러보기, 처음부터 준비하기, 가입내역 PDF 올리기), 홈(보장 지도), 만약에(상황별 필요한 돈과 받을 수 있는 돈), 내 설계(첨부 시안 기준: 월 예산 슬라이더, 현재 유지/보완안, 담보 목록, 두 안 비교, 담보 비교), 계약 상세, 증거 보기, 내 정보(프로필·가입내역·동의).
- **엔진:** 규칙 DSL, 3값 논리, 미확인 전파, 재현성 스냅샷. 전 상품군(§54.4)을 계산할 수 있는 연산을 갖춘다.
- **데이터:** 금융당국 공공데이터와 모든 보험사 공시 사이트를 매일 크롤링해 갱신한다. 보험료는 가입 조건·특약 구성·기준일과 함께 수집한다(가격 수집 명세). AI 검수를 통과한 담보부터 계산·비교하고 나머지는 원문 보기와 "아직 계산하지 않아요".
- **관제 콘솔:** §14 7개 화면과 AI 검수 감사. **공개 웹:** §45.1.

### 43.5 출시 범위 밖

- **스켈레톤(§58):** 상담 연결, 설계사 포털, 개인 견적(견적서 제출·견적 연계), 설계 검증, 콘텐츠·광고·구독, 가족력 입력, 가족 초대·연결. 데이터 모델·API 경로·플래그만 미리 두고 화면에는 없다.
- **DNA 연계(§12):** 설계 동결. 구현·출시하지 않는다. `genetic_private` 민감도 라벨과 저장 영역 분리만 미리 둔다.
- **만들지 않기로 한 것:** 카메라 촬영 입력, 통합조회·마이데이터 연계(§47.2), 체험판 웹, 소비자 웹앱 전체판, 푸시 알림.

## 44. 소비자 앱 정보 구조

### 44.1 탭과 화면

첨부 시안의 4탭을 기준으로 한다.

| 탭 | 화면 | 핵심 질문 | 주요 행동 |
|---|---|---|---|
| 홈 | 보장 지도 | 내가 가진 보장과 확인할 항목은? | 보장 살펴보기 |
| 홈 | 계약 상세 | 이 계약은 어떤 역할인가? | 조건 확인, 원문 보기 |
| 만약에 | 상황 선택 | 어떤 상황을 볼 것인가? | 상황 고르기 |
| 만약에 | 상황 결과 | 이 상황에서 받을 수 있는 것과 생활비 공백은? | 조건 바꾸기 |
| 내 설계 | 예산·안 비교(기준 화면) | 예산에 따라 보장과 불이익이 어떻게 달라지는가? | 예산 조절, 현재 유지/보완안, 두 안 비교하기 |
| 내 설계 | 전후 비교 | 더 얻는 것·잃는 것·확인할 것은? | 선택 보관 |
| 내 설계 | 담보 비교 | 같은 담보가 보험사마다 어떻게 다른가? | 조건 차이 보기, 원문 보기 |
| 내 정보 | 프로필(본인·가족) / 가입내역 / 동의·권한 | 내 데이터는 어디에 어떻게 쓰이는가? | PDF 올리기, 동의 관리, 삭제 |
| 공통 | 증거 보기 | 이 숫자는 어디서 왔는가? | 원문 페이지·조항·버전 |

### 44.2 공통 화면 상태

모든 데이터 화면은 다음 상태를 반드시 구현한다. 디자인 시안은 상태별로 한 장씩 있어야 한다.

| 상태 | 조건 | 화면 규칙 |
|---|---|---|
| 로딩 | 요청 중 | 골격 화면. 2초 초과 시 문구 안내 |
| 비어 있음 | 가입내역 없음(건너뜀·보험 없음·모름) | '가입내역 없이 보기'로 동작. 프로필의 가입내역 상태(§47.2)를 화면에 표시 |
| 부분 | 일부 담보 미확인 | 아는 부분만 표시. 합계 금액 표시 금지(§36). "확인 필요 n건" 배지 |
| 판단 불가 | 핵심 입력 없음 | 추가 질문 1개 또는 범위 표시. 금액 크게 표시 금지(§10) |
| 오래됨 | 릴리스 기준일이 정책 기한 초과 | 최신성 경고 띠. 결과는 유지 |
| 오류 | 서버·네트워크 실패 | 마지막 성공 결과 + 실패 사실. 재시도 |
| 변경됨 | 새 릴리스로 결과가 바뀜 | 이전·이후 차이와 원인(원문 변경/처리기 변경) |

### 44.3 상태 어휘

첨부 시안의 '유지·추가 검토·조건 확인'을 포함해 다음 enum을 디자인·API·엔진이 공유한다. 소비자 화면 문구와 내부 코드를 함께 고정한다.

| 코드 | 화면 문구 | 엔진 조건 |
|---|---|---|
| `keep` | 유지 | 현재 보장이 선택 상황·예산에서 공백 없음 |
| `review_add` | 추가 검토 | 확인된 보장 공백이 있고 예산 내 대안 후보가 존재 |
| `review_reduce` | 축소 검토 | 중복·초과 보장이 확인되고 유지 비용이 큼 |
| `confirm_input` | 조건 확인 | 미확인 입력 때문에 판단 불가. 추가 질문 존재 |
| `unverified` | 미확인 | 원문·계약에서 조건을 찾지 못함. 0원 아님 |
| `hold` | 판단 보류 | 근거 충돌·AI 검수 보류(§57). 추천 생성 중단 |
| `not_applicable` | 해당 없음 | 상황·피보험자 조건상 적용 대상 아님 |

`unverified`와 `confirm_input`의 차이: 전자는 데이터 쪽 부재, 후자는 사용자 입력 부재다. 전자는 사용자가 해결할 수 없으므로 "증권에서 확인하지 못했어요"로, 후자는 질문으로 안내한다.

### 44.4 내 설계 화면 사양 (첨부 시안 기준 고정)

상세 사양은 `docs/design/화면_조작_설계서.md`가 정한다. 요약은 다음과 같다.

1. 시안 `docs/design/내설계_기준화면.png`가 주 기준이다. 월 예산 슬라이더(5~30만 원, 1만 원 단위), `현재 유지 | 보완안` 세그먼트, 담보 목록(진단 보장·입원·수술·생활비 대비·무엇이 달라지나요?), 주요 행동 "두 안 비교하기", 하단 4탭을 그대로 쓴다.
2. 시안 대비 변경은 설계서 §2의 C1~C6만 허용한다. 최소 추가 요소는 P0 시안 검토에서 사용자가 승인한다.
3. 월 예산 초기값은 입력한 월 예산, 없으면 현재 월 보험료, 없으면 범위 중앙값(예시값)이다.
4. 금액에는 가격 종류 라벨(공개 가격·내 계약·개인 견적·추정 범위·가격 미확인)과 기준일이 붙는다. 공개 가격은 개인 견적이 아니다.
5. 보장과 불이익을 함께 비교한다. 추가되는 것뿐 아니라 사라지는 보장·면책·감액을 같은 비중으로 보여준다(설계서 §7).
6. 가격 미확인 상품도 숨기지 않는다. 예산 합계에서 제외하고 건수를 표시하며 0원으로 합산하지 않는다.
7. 보완안은 예산, 실제 가입 조합 제약, 근거 최신성, 보장 목표, 사용자 선호를 만족하는 구성이다. 광고비·수수료·가입 전환율은 입력이 아니다(§11). 후보가 없으면 "지금 예산에서는 유지가 적절해요"가 결과다.
8. 보완안은 추가형·교체형·축소형으로 구분하며 교체형에는 보장 공백, 면책 재시작, 인수 불확실성, 해지 손실을 반영한다.

### 44.5 "필요한 돈" (만약에 탭과 담보 상태의 근거)

- 필요한 돈은 상황 모델(§10)의 비용 항목의 합이다. 치료로 본인이 부담하는 비용, 소득 중단 기간 × 월 필요 생활비, 간병·돌봄 비용 등이다.
- 각 항목은 사용자가 조절하는 가정이다. 기본값에는 출처와 기준일을 붙이고 `estimated`로 표시한다. 기본값의 출처는 공공 통계 등에서 AI 조사로 후보를 모으고(§57.6) P2에서 확정한다.
- 근거 없는 평균이나 확률을 개인의 예측처럼 보여주지 않는다(v0.3 §12).
- 받을 수 있는 돈은 가입내역 PDF에서 확인된 계약을 디지털 트윈에 넣은 결과다. 가입내역이 없으면 받을 수 있는 돈은 미확인(점선)이다.
- 내 설계의 담보 상태(`review_add` 등)는 이 공백과 가격, 예산 조건을 함께 보고 정한다.

`/coverage`는 브랜드 자산이다. 관제 콘솔의 범위 지도와 같은 API를 쓰되 공개용은 집계만 노출한다. 누락을 숨기지 않는다는 원칙(§23.4)을 외부에 보여주는 첫 화면이다. 소스별 마지막 확인·성공 시각과 층별 확보율, 가격 확보율을 보여준다(§59.3~4). 검증 표기는 'AI 검증'이며 '전문가 검수' 같은 표현은 쓰지 않는다(§57.4).

### 45.2 관제 콘솔·AI 검수 감사

- 인증: 내부 SSO 또는 초대 기반 계정, 2단계 인증 필수. 역할은 운영자·정책 소유자·읽기로 나눈다.
- 화면: §14의 7개 전부.
- AI 검수 감사: 에이전트별 판정, 근거, 코드 검사 결과, 레드팀 반례, 보류 사유를 원문 페이지(bbox)와 나란히 읽기 전용으로 보여준다. 정책 임계값(§57.3)과 서킷 브레이커 상태(§57.5)를 보고 설정한다.
- 감사 로그: 모든 AI 결정·릴리스·롤백에 어떤 에이전트(모델·프롬프트 버전)가·언제·무엇을·왜 했는지 남긴다. 개인 민감정보 원문은 남기지 않는다(§15).

### 45.3 설계사 포털 (스켈레톤, 첫 출시 제외)

첫 출시에는 포털·상담·후기·구독이 없다(§58). 아래는 후속 설계 메모로 보존한다.

- 등록: 설계사·GA가 가입하고 소속과 취급 범위(보험사·상품군)를 등록한다. 공개 등록 정보와 제출 자료를 AI가 대조하고 불일치는 보류한다.
- 상담: 요청을 받으면 설계안 요약과 사용자가 고른 자료만 본다. 예약을 잡고, 상담 후 제안서 PDF를 제출하면 앱에서 실제 설계안 검증(§47.1 2단계)이 이루어진다.
- 후기: 상담 완료 후기와 가입 여부를 분리한다(v0.3 §16). 허위·보복 평가 탐지는 AI가 1차로 수행한다.
- 노출 순서: 광고비·수수료·가입 전환율은 순위에 반영하지 않는다(불변 원칙 1). 구독료는 도구 사용권이다.
- 과금: 구독과 명시적 광고만 만든다. 성사 수수료·리드 과금은 만들지 않는 것을 기본값으로 둔다(v0.3 §16의 유보, 가정).
- 데이터 경계: `genetic_private`는 포털 API 전체에서 차단한다(§12.6). 가족력 등 `private_health`는 사용자가 항목별로 고른 것만 공유하며 기본은 공유하지 않는다(가정).

### 45.4 콘텐츠·광고·구독 (스켈레톤, 첫 출시 제외)

첫 출시에는 없다(§58). 아래는 후속 설계 메모로 보존한다.

- 콘텐츠: 근거 연결 아티클. 모든 사실 문장은 원문 또는 검증 규칙에 연결하고(§35) AI가 근거 지지를 검증한다.
- 광고: 별도 영역에 "광고"로 표시한다. 자연 순위·추천·후기에 영향을 주지 않는다. 건강·가족력 정보를 광고 타기팅에 쓰지 않는다(불변 원칙 8).
- 구독: 설계사 도구 구독. 소비자 앱은 광고가 추천 목적함수에 들어가지 않는 구조를 유지한다.

## 46. 계정·인증·가족·동의

### 46.1 계정 단계

| 단계 | 시점 | 저장 |
|---|---|---|
| 익명 | 예시로 둘러보기, 처음부터 준비하기 | 기기 로컬만. 서버 저장 없음 |
| 계정 | 저장·동기화·계약 업로드 시 제안 | 이메일 또는 소셜 로그인 + 기기 인증 |
| 본인확인 | 가족 프로필 연결 | 휴대폰 본인확인. 주민번호 저장 안 함 |

익명에서 계정으로 전환할 때 로컬 데이터를 가져올지 사용자가 선택한다. 전환 전 민감정보(건강)는 서버로 보내지 않는다.

### 46.2 프로필: 본인과 가족

- 한 계정에 프로필을 여러 개 둔다. 본인과 가족(부모·배우자·자녀 등)이다. 이름 대신 관계 라벨과 출생 연도만 받는다.
- 부모나 자녀의 보험을 대신 살펴보려는 사용자를 지원한다. 대신 보는 사람은 상대의 가입 내용을 모를 수 있으므로 프로필마다 가입내역 상태를 둔다(§47.2).
- 대리 프로필에도 PDF를 올릴 수 있다. 그 문서는 해당 프로필 안에만 저장하며 다른 계정과 공유하지 않는다.
- 건강·가족력·DNA는 본인 프로필에서만 입력한다. 다른 성인 프로필에는 열지 않는다(불변 원칙 8, v0.3 §3.2 유지).
- 가족이 자기 계정을 만들어 연결하는 초대는 스켈레톤이다(§58).
- 아동 프로필은 보호자가 관리하며 건강 정보 입력은 열지 않는다.

### 46.3 동의 모델

`Consent`(§9)를 목적별로 분리한다: 서비스 필수, 계약 문서 처리, 외부 AI 처리, 가족 연결. 건강 정보 처리·상담 공유·DNA 관련 동의는 스켈레톤 또는 출시 범위 밖이다(§58). 동의 화면은 한 화면에 한 목적. 철회는 설정에서 즉시 가능하고 철회 시 영향(어떤 기능이 꺼지는지)을 미리 보여준다.

### 46.4 삭제·내보내기

- 계정 삭제: 즉시 접근 차단, 유예 기간 후 영구 삭제. 유예 중 복구 가능.
- 데이터 내보내기: 사용자 계약·입력·결과를 기계 판독 형식(JSON)과 사람용(PDF)으로 제공.
- 개념 API에 추가: `POST /auth/*`, `GET/DELETE /me`, `GET /me/export`, `POST /consents`, `DELETE /consents/{id}`.

## 47. 핵심 외부 의존의 대안 설계

### 47.1 가격: 첫 출시 수집·비교 대상 (사용자 결정)

가격 데이터도 첫 출시의 수집·비교 대상이다. 상세는 `docs/masterplan/가격_수집_명세.md`가 정한다.

- 보험료는 가입 조건, 특약 구성, 기준일과 함께 한 레코드로 저장한다. 조건 없는 가격은 저장하지 않는다.
- 가격 종류는 다섯 가지이며 섞지 않는다.

| 종류 | 의미 | 첫 출시 |
|---|---|---|
| 공개 가격 | 공시된 표준 조건의 보험료. 견적이 아니다 | 수집·표시 |
| 내 계약 보험료 | 가입내역 PDF에서 확인된 내 실제 보험료 | 수집·표시 |
| 개인 견적 | 특정 개인 조건·시점의 견적(제출 견적서, 견적 연계). 만료가 있다 | 스켈레톤 |
| 추정 범위 | 공시 조건 사이를 잇는 파생 범위 | 계산해 표시 |
| 미확인 | 가격을 확인하지 못함. 사유를 붙인다 | 표시 |

- 가격 미확인 상품도 숨기지 않는다. 미확인은 0원이 아니며 예산 합계에서 제외하고 건수를 표시한다(불변 원칙 3).
- 공개 가격과 개인 견적은 화면에서 다른 칩 모양과 아이콘으로 구분한다.
- 개인 견적은 스키마·라벨·플래그만 있고 입력 경로가 없다(§58).

### 47.2 계약 가져오기: PDF 업로드 단일 경로 (사용자 결정)

- 경로는 하나다. 사용자가 보험사 앱·웹에서 직접 받은 가입내역·증권 PDF를 올린다. 카메라 촬영, 사진 입력, 통합조회·마이데이터 연계는 만들지 않는다.
- 올리는 일은 사용자 몫이다. 앱이 대신 가져오지 않고, 알림으로 재촉하지 않는다.
- 올리지 않아도 된다. 건너뛰어도 만약에·내 설계는 '가입내역 없이 보기'로 동작한다.

프로필마다 가입내역 상태를 하나 가진다.

| 상태 | 뜻 | 계산과 화면 |
|---|---|---|
| `uploaded` | PDF를 올리고 사용자가 확인함 | 확인된 계약으로 계산 |
| `none` | 사용자가 '보험 없음'이라고 답함 | 가입 보장 없음으로 계산하되 "본인 답변 기준"이라고 표시 |
| `unknown` | 모름. 부모·자녀 것을 대신 볼 때 흔함 | 보유 보장 미확인. 0원으로 계산하지 않는다(불변 원칙 3). 필요한 보장 규모만 보여주고 유지·보완 판단은 만들지 않는다 |
| `skipped` | 지금은 안 올림 | `unknown`과 같은 방식. 언제든 올릴 수 있다 |

- 형식은 PDF만 받는다. 이미지 파일은 받지 않는다.
- 비밀번호로 잠긴 PDF는 사용자가 비밀번호를 입력해 연다. 비밀번호는 저장하지 않고 로그에도 남기지 않으며 처리 직후 폐기한다.
- 이미지로 된 PDF는 페이지 단위 OCR(§26)로 처리한다. 모든 PDF는 추출 뒤 사용자 확인을 거친다.
- 확인 화면은 "AI가 읽은 내용"과 "원본 영역"을 나란히 보여주고 한 항목씩 확인한다. 확인 전에는 `unconfirmed`이며 계산에 쓰지 않는다.
- 한 PDF에 계약이 여러 개면 계약별로 나눈다.
- 상품 버전에 맞출 수 없는 계약(미수집·과거 상품)은 `unverified`로 두고 원본 PDF를 보관하되 계산에서 제외한다.

### 47.3 AI 제공자

- AI 게이트웨이(§13)를 자체 모듈로 둔다. 제공자 SDK를 앱·엔진 코드에서 직접 호출하지 않는다.
- 호출마다 `provider, model_version, prompt_version, schema_version, cost, latency`를 기록한다.
- 독립 검증(§57.2)을 위해 서로 다른 모델 계열 2개 이상을 호출할 수 있어야 한다. 단일 제공자에 의존하지 않는다.
- 구조화 출력은 JSON Schema로 검증하고 실패 시 재시도 한도 후 `unresolved`로 떨어뜨린다. 모델이 금액·날짜를 생성하면 코드가 원문 인용 일치를 검사한다(§29).
- 월 호출 비용 상한과 사용자당 일일 상한을 둔다. 상한 초과 시 기능 저하(캐시 결과·판단 보류)로 전환하고 숨기지 않는다.
- 평가 하네스: 정답셋(§32)을 모델·프롬프트 변경마다 자동 실행. C0 오류 1건이라도 늘면 배포 차단.
- 'AI에게 질문하기'(§12.4)는 검색 색인을 근거 탐색에 쓰되, 금액·지급 여부는 규칙 엔진 결과(§49.6)만 인용한다. 검색 결과 문장에서 금액을 만들지 않는다.
- 사용자 데이터로 모델 학습 금지, 보존 기간 최소화를 제공자 설정으로 강제하고 그 설정을 문서화한다.

## 48. 기술 아키텍처와 스택 후보

세부는 ADR-0001. 여기서는 선택 기준과 후보만 적는다.

### 48.1 선택 기준

1. 백엔드와 규칙 엔진은 Rust로 한다(사용자 결정, 2026-10-08). 문서 복원·OCR처럼 Python 생태계가 필요한 부분만 격리된 Python 워커로 두고 큐로만 연결한다.
2. 모바일은 두 플랫폼을 한 코드로 만들고 시각 표현의 자유도가 높아야 한다. 파일 선택·보안 저장소 접근이 필요하다.
3. 공개 웹·관제 콘솔은 같은 웹 프레임워크로 묶는다.
4. 규칙 엔진은 **한 구현만** 존재한다(ADR-0003). 클라이언트 포팅 금지. 결과는 서버가 계산하고 앱은 표시한다.
5. 특정 클라우드 종속을 피한다. 로컬 개발 환경을 Docker Compose로 전부 띄울 수 있어야 한다.

### 48.2 후보 스택

| 계층 | 1순위 후보 | 대안 | 비고 |
|---|---|---|---|
| 모바일 | Flutter(Dart) | - | 사용자 결정. 시각 표현 우선 |
| 공개 웹·관제 콘솔 | Next.js + TypeScript | SvelteKit | 검색 노출과 PDF 대조 화면이 필요 |

| 규칙 엔진 | Rust 크레이트(순수, 의존성 최소) | - | 결정적, 부동소수점 금지, 정수·유리수 연산 |

## 49. 규칙 DSL v0.1 형식 명세

§34를 구현 가능한 수준으로 고정한다. 전체 JSON Schema는 `packages/schemas/rule-0.1.schema.json`으로 작성한다(후속 작업).

### 49.1 타입

| 타입 | 표현 | 비고 |
|---|---|---|
| `bool3` | `true / false / unknown` | 3값 논리 |
| `money` | `{currency:"KRW", minor:int}` | 정수 원. 부동소수점 금지 |
| `rate` | `{num:int, den:int, printed:"50%"}` | 유리수 + 원문 표기 |
| `int`, `decimal(문자열)` | | |
| `date` | `YYYY-MM-DD` + 달력 | 시간대는 규칙 메타의 `calendar` |
| `duration` | `{value:int, unit:"day"\|"calendar_month"\|"calendar_year"}` | 1년≠365일 |
| `enum`, `set`, `code_ref` | KCD 등 `{scheme, edition, code}` | |

모든 변수는 `source: contract | event | product | derived` 중 하나를 가진다. 서로 다른 source의 변수를 같은 이름으로 쓸 수 없다.

### 49.2 연산자

논리: `all, any, not`. 비교: `eq, ne, lt, lte, gt, gte, in_set, between(포함 여부 명시)`. 날짜: `date_add(date, duration), days_between(a, b, inclusive_start, inclusive_end), date_compare`. 금액: `multiply_rate(money, rate, rounding), add, min, max, apply_cap(money, cap), apply_floor`. 상환형: `subtract_deductible(money, deductible)`, `coinsurance(money, rate)`, `pro_rata(money, shares[])`(타 보험과의 비례보상), `cumulative_cap(state_key, money, cap, period_basis)`. 제어: `if/then/else`, `first_match(cases)`. 조회: `input(name)`, `const`.

허용 목록 밖의 연산자는 스키마 검증에서 거부한다. 사용자 정의 함수·코드 실행 없음.

### 49.3 3값 논리

| a | b | all(a,b) | any(a,b) | not(a) |
|---|---|---|---|---|
| T | T | T | T | F |
| T | F | F | T | F |
| T | U | U | T | F |
| F | F | F | F | T |
| F | U | F | U | T |
| U | U | U | U | U |

비교 연산자는 피연산자 하나라도 `unknown`이면 `unknown`을 돌려준다. 금액 연산은 피연산자가 `unknown`이면 결과를 `unknown`으로 두고 `missing_inputs`에 이름을 추가한다.

### 49.4 시간 의미론

- 규칙 메타에 `calendar: "Asia/Seoul"`, `day_boundary: "00:00"`을 명시한다. 날짜만 다루며 시각은 입력에서 날짜로 정규화한 뒤 쓴다.
- 기산점·포함 여부는 변수가 아니라 규칙에 적는다: `{"days_between": ["coverage_start", "event_date", {"inclusive_start": true, "inclusive_end": false}]}`.
- 보험연도·역년·계약기념일은 `period_basis` enum으로 구분하고 원문 근거를 붙인다.

### 49.5 금액과 반올림

`multiply_rate`는 `rounding: "floor" | "ceil" | "half_up" | "half_even"`과 `unit: 1 | 10 | 1000`을 필수로 받는다. 원문에 반올림 규칙이 없으면 `rounding: "unspecified"`로 두고 결과를 범위(floor~ceil)로 돌려준다. 임의 기본값 금지.

### 49.6 평가기 출력

```text
EvaluationResult
  rule_id / rule_version / engine_version / release_id
  eligibility: bool3
  amount: money | {min: money, max: money} | unknown
  missing_inputs[]        # confirm_input 으로 이어짐
  unresolved_refs[]       # unverified 로 이어짐
  trace[]                 # 평가한 노드, 입력값, 중간 결과, evidence_ref
  input_snapshot_hash
```

같은 입력 스냅샷·규칙 버전·엔진 버전이면 바이트 단위로 같은 결과를 낸다. 이를 CI에서 검사한다.

### 49.7 테스트

- §34.1 경계표를 첫 골든 테스트로 넣는다.
- 속성 기반 테스트: 임의 날짜 ±1일, 금액 단위 변경, 입력 하나를 unknown으로 바꾸면 결과가 unknown 또는 범위로 바뀌는지.
- 변이 테스트(§34.2): 부정어 삭제, 경계 포함 반전, 단위 변경을 규칙에 주입해 골든 테스트가 실패하는지.
- 순차 시나리오: 청구 이력·한도 소진·계약 변경을 순서대로 적용.

## 50. 데이터 모델의 구현 메모

§9의 엔터티를 PostgreSQL로 옮길 때 지킬 것.

- 모든 권위 테이블에 `valid_from, valid_to, recorded_at, superseded_at`. 갱신은 삽입이다. 물리 삭제는 사용자 삭제 요청 처리 외에 없다.
- `FieldAssertion`(§29)은 별도 테이블. 값은 `typed_value JSONB` + `value_state` enum(§28.3). `value_state`가 `observed`가 아니면 `typed_value`는 null 허용, 그 외에는 null 금지(제약으로 강제).
- 민감도 라벨(§28)은 행 단위 컬럼이자 스키마(별도 데이터베이스 스키마 또는 별도 DB)다. `private_health`·`genetic_private`는 공시 데이터와 같은 스키마에 두지 않는다.
- 릴리스는 불변 매니페스트(§37)이며 서비스는 항상 특정 `release_id`를 가리킨다. 롤백은 포인터 변경이다.
- 사용자 결과(`Simulation`, `Recommendation`)는 `release_id, engine_version, input_snapshot_hash`를 저장해 재현한다(§10).

| 화면 | 상태별 화면(§44.2) | 스토리북형 상태 카탈로그, 스냅샷 | 상태 하나당 시안·구현 1:1 |

### 51.2 CI

PR마다: 린트·타입 검사, 단위·계약 테스트, 스키마 호환성 검사, 규칙 엔진 재현성 검사, 민감도 라벨 누출 정적 검사(§52.3), 불변 원칙 체크리스트(PR 템플릿). 기본 브랜치 보호: 코드 리뷰 1인 이상. 규칙·라벨 사전 변경은 AI 승인 정책(§57.3)을 통과해야 병합된다.

### 51.3 릴리스

- 앱: 내부 테스트 → 출시 리허설 → 출시. 기능은 첫 출시 범위(§43.4)를 완성 상태로 한 번에 낸다. 서버 기능 플래그는 기능의 단계 공개가 아니라 담보별 계산 가능 여부를 데이터 이용 등급에 맞춰 켜고 끄는 용도다. 기능 플래그는 §36의 공개 기능 상태(`explanation_enabled` 등)와 1:1로 연결한다. 데이터가 허용하지 않는 기능은 플래그로도 켤 수 없다.
- 서버: 데이터 릴리스와 코드 릴리스를 분리한다. 코드 배포는 현재 데이터 릴리스를 바꾸지 않는다.
- 데이터: §36·§37 승격 절차. 배포함에서 AI 승인(§57): 작성 에이전트≠승인 에이전트, 서로 다른 모델 계열.
- 롤백: 코드·데이터 각각 독립. 롤백 후에도 사용자에게 보여준 기록은 보존(§10).

### 51.4 접근성: 목표 아님 (사용자 결정)

접근성 준수는 목표도 출시 게이트도 아니다. 시각 완성도와 사용감을 최우선으로 한다. 접근성 요구가 있던 v0.3 §5·§17의 항목은 이 결정으로 대체한다. 위험은 고령 사용자 이탈이며 R12에 기록한다.

### 51.5 사용성 시험

§17의 "5초·30초" 기준을 각 마일스톤 종료 조건으로 쓴다. 가상 계약으로만 시험하며 참가자 개인 계약을 받지 않는다. 잘못 이해한 비율을 핵심 지표로 기록한다.

## 52. 관측·계측·개인정보 경계

### 52.1 제품 분석

- 이벤트는 허용 목록(allowlist)만 전송한다. 목록은 `packages/schemas/analytics-events.yaml`에 두고 PR 리뷰 대상이다.
- 전송 금지 필드: 계약 금액, 담보 명, 건강·가족력·DNA 관련 모든 값, 자유 입력 텍스트, 문서 내용. 전송 가능: 화면 ID, 상태 코드(§44.3), 소요 시간, 오류 종류.
- 세션 녹화·히트맵 SDK는 쓰지 않는다.
- 분석 수집은 자체 호스팅을 기본으로 하고, 외부 SDK를 쓰면 전송 전 필드 검증 계층을 둔다.

### 52.2 크래시·로그

- 크래시 보고에 화면 상태 덤프를 넣지 않는다. 브레드크럼은 화면 ID와 상태 코드만.
- 서버 로그는 구조화하고 `private_health`·`genetic_private` 데이터는 로그 직렬화기에서 자동 마스킹한다.
- AI 게이트웨이 로그는 프롬프트 템플릿 ID·스키마·비용만 저장한다. 사용자 문서 본문은 저장하지 않는다.

### 52.3 누출 정적 검사

CI에서 다음을 검사한다: 분석 이벤트 스키마 밖 필드 전송 코드, 민감도 라벨 테이블을 공개 API 직렬화기에서 참조하는 코드, 설계사·상담 모듈이 `genetic_private` 스키마를 import하는 코드. 발견 시 빌드 실패.

### 52.4 운영 지표

§19 외에 추가: 앱 크래시율, 화면별 판단 불가 비율, "확인 필요" 해소율, 증거 보기 진입률, AI 호출 비용/사용자, AI 검수 보류율, 표본 재추출 불일치율, 서킷 브레이커 발동 수.

| 공시 원문 처리 | 악성 PDF, 프롬프트 주입 | 파서 샌드박스(격리 컨테이너, 네트워크 차단), 지시문 무시 규칙, 모델에 도구 권한 없음 |
| 규칙·릴리스 | 무단 변경, 잘못된 승인 | 2인 승인, 서명된 매니페스트, 감사 로그 |
| 앱 클라이언트 | 토큰 탈취, 변조 | 짧은 토큰, 기기 보안 저장소, 인증서 고정 검토, 루팅·탈옥 시 민감 기능 제한 |
| AI 제공자 | 데이터 보존·학습 | 계약·설정 확인, 원본 유전체 파일 전송 금지 |
| 수집 | 출처 과부하, 접근 규칙 위반 | rate_policy, circuit breaker, 허용 호스트 |

### 53.2 기본 통제

전송 구간 TLS, 저장 암호화, 비밀은 비밀 관리자, 의존성 취약점 자동 검사, 서명된 빌드, 역할 기반 접근 제어, 관리자 2단계 인증, 백업 암호화와 복구 연습.

### 53.3 사고·지원 흐름

- 사용자 문의 채널(앱 내·웹 `/support`)과 지원 큐. 삭제 요청은 접수 즉시 접근 차단, 처리 결과 통지.
- 잘못된 계산 발견 시 §15 절차: 신규 추천 중단 → 영향 범위 → 수정 릴리스 → 사용자 안내 → 정정 이력. 각 단계의 담당과 시한을 런북(`docs/runbooks/`)으로 작성한다.
- 침해 사고 대응 런북: 탐지, 격리, 영향 평가, 통지, 사후 검토.

### 54.3 인력·AI 처리량 가정

사람의 건별 검수가 없으므로 병목은 인력이 아니라 AI 호출 비용·지연·평가 체계다.

- AI 검수 비용 = 담보 발생본 수 × (추출 호출 수 + 검증 호출 수 + 레드팀 호출 수 + 표본 재추출) × 호출당 비용. 호출 수와 비용은 P2에서 상품 수십 개로 파일럿을 돌려 실측하기 전에는 수치를 쓰지 않는다.
- 비용을 줄이는 방법은 변경분만 재처리(§37), 표준약관을 공유하는 상품은 한 번 추출·검증하고 상품별 버전 바인딩만 다시 확인하는 방식이다. 확인도 AI가 한다.
- 역할 가설: 데이터·AI 운영 2~3, AI 평가·검증 시스템 2, 백엔드·엔진(Rust) 2~3, 모바일(Flutter) 1~2, 웹·관제 2, 디자인 1~2(시각 최우선이라 비중을 키운다), 정책 소유자 1(§57.5). 분모 조사 후 재산정한다.
- 비용 산식(§18)에서 "검수 시간×인력 단가" 항은 "AI 검수 호출 비용"으로 대체한다.

### 54.4 엔진·데이터 구축 순서 (출시 순서 아님)

대상은 모든 상품이며 출시는 한 번이다. 아래는 엔진 능력과 데이터 구축을 어떤 순서로 쌓을지의 제안이다. 상품군마다 계산 구조가 다르다.

## 56. 결정 기록 v0.4와 열린 질문

### 확정(이 문서 범위)

- 표면 네 개(§42). 체험판 웹과 소비자 웹앱 전체판은 없다.
- 두 트랙 병렬, 합성 픽스처 우선(ADR-0002).
- 규칙 엔진 단일 구현, 서버 계산(ADR-0003).
- 상태 어휘(§44.3, 설계서 §6)와 가격 종류 5종(가격 수집 명세 §2).
- 내 설계 초기값은 현재 월 보험료. 축소 영역 허용.
- 분석 이벤트 허용 목록 방식.

### 사용자 결정 완료 (2026-10-08)

- 백엔드는 Rust. 문서 복원·OCR만 격리된 Python 워커.
- 모바일은 Flutter.
- 계약 가져오기는 PDF 업로드 단일 경로. 올리지 않아도 되며 '보험 없음'·'모름'을 허용한다.
- 접근성은 목표가 아니다. 시각 완성도 우선.
- 범위는 모든 보험사의 모든 보험(실손·간병 포함, 모든 특약).
- 체험판 웹은 만들지 않는다.
- 출시는 한 번이며 첫 출시 범위(§43.4)가 완성된 상태로 나온다. DNA는 제외.
- 검수는 AI가 한다. 사람은 건별 검수를 하지 않는다.
- 분모 조사는 AI가 한다.
- 상담 연결·설계사 포털·개인 견적 단계는 스켈레톤만 남기고 첫 앱에서 뺀다.
- 첨부 이미지를 내 설계 탭의 주 기준으로 고정한다. 월 예산 슬라이더·현재 유지/보완안·담보 목록을 살린다.
- 가격 데이터도 첫 출시의 수집·비교 대상이다. 보험료는 가입 조건·특약 구성·기준일과 함께 저장한다.
- 보장과 불이익을 함께 비교한다. 사라지는 보장·면책·감액도 보여준다.
- 공개 가격과 개인 견적을 구분하고 가격 미확인 상품도 숨기지 않는다.
- 첫 앱의 초점은 철저한 크롤링·데이터셋·라벨링·디지털 트윈과 읽지 않아도 되는 직관적 UX다.
- 금융당국 공공데이터와 보험사 공시 사이트를 전부 매일 크롤링해 갱신한다.
- 판단 기준은 소비자 이익이다.

### 가정 (이의가 없으면 유지)

- 판매 중지 상품을 포함한다. 기존 계약 PDF를 상품 버전에 맞추는 데 필요하다.
- 공제·우체국보험 등은 분모 조사 후 목록을 보고 포함 여부를 확정한다.
- 완성본은 기능의 완성이다. 담보별 계산은 AI 검수 통과분부터 켜지고 나머지는 "아직 계산하지 않아요"로 표시한다. 출시 게이트에 "전 담보 계산 가능"은 넣지 않는다.
- 콘텐츠·광고·구독, 가족력 입력, 설계 검증, 가족 초대는 설계사 포털·개인 견적에 딸려 있거나 담보 파악 밖이므로 함께 스켈레톤으로 뺀다(범위를 더 좁힌 해석).
- 첫 출시의 개인 가격은 가입내역 PDF의 내 계약 보험료뿐이다. 개인 견적은 스켈레톤이다.
- 시안 대비 최소 추가 요소 C1~C4(설계서 §2)는 P0 시안 검토에서 사용자가 승인한다.
- 보완안은 추가형·교체형·축소형이며 교체형에는 보장 공백·면책 재시작·인수 불확실성·해지 손실을 반영한다.
- 앱 안의 '예시로 둘러보기'는 유지한다. 웹 체험판이 아니라 앱 기능이다.
- 사람은 건별 검수를 하지 않는다. 정책 소유자 1인이 AI 승인 임계값·모델 구성·사고 시 중단/재개를 정책 수준에서 결정한다.
- 대리 프로필에 부모 등의 PDF를 올릴 수 있다. 건강·가족력·DNA는 본인 프로필에서만 입력한다.

### 남은 결정

1. 공제·우체국보험 등의 포함 여부(분모 조사 후).
2. 공개 웹 도메인·가칭 명칭(개발을 막지는 않음).
3. "필요한 돈" 기본값의 공공 통계 출처(P2에서 AI 조사 후 확정).

### 이번 산출물의 범위

제3부 문서, 평가서, ADR 8건. 코드·픽스처·스키마 파일은 P0 백로그이며 아직 만들지 않았다.

## 57. AI 검수와 AI 분모 조사 (사용자 결정)

### 57.1 결정과 영향

검수는 AI가 하고 사람은 건별 검수를 하지 않는다. 분모 조사도 AI가 한다. 사람 검수를 전제한 아래 부분은 이 절로 대체한다.

| 대체되는 부분 | 바뀌는 내용 |
|---|---|
| v0.3 §8 "도메인 전문가 검수로 보완" | AI 승인 정책(§57.3) |
| v0.3 §17 "전문가 승인 테스트" | AI 검수와 합성·변이 평가셋(§57.4) |
| v0.3 §22 독립 검수자, 작성자≠승인자 | 작성 에이전트≠승인 에이전트, 서로 다른 모델 계열 |
| v0.3 §31 검수 작업대, C0·C1 전수 사람 승인 | C0·C1 전수 AI 승인. 사람 화면은 읽기 전용 감사(§45.2) |
| v0.3 §32 전문가 라벨 정답셋 | AI 평가셋(§57.4) |
| v0.3 §34.2 전문가 승인 기대 결과 | 문서 예시·합성 규칙·교차 문서 판정으로 고정 |
| v0.3 §23 분모 조사 담당 | AI 조사 에이전트(§57.6) |

불변 원칙은 모두 유지한다. v0.3 §30.2의 "모델끼리 일치해도 독립 증거가 아니다"도 유지한다. 그래서 독립성은 모델 수가 아니라 실패 방식의 다양성으로 확보한다.

### 57.2 독립성 설계

1. 작성(추출)·승인(검증)·레드팀은 서로 다른 모델 계열이며 가능하면 제공자도 다르다.
2. 입력 표현을 달리한다: 텍스트 추출, 페이지 이미지, 표 구조.
3. LLM이 아닌 코드 검사를 결합한다: `exact_quote` 원문 일치, 타입·단위, 참조 그래프, 3값 논리·경계값 테스트, 이상/초과·이하/미만·부정어 토큰 대조(§26.3).
4. 교차 문서 검증: 약관·사업방법서·요약서·공시 예시 지급 사례. 충돌은 §33.2로 처리한다.
5. 레드팀 에이전트가 승인 후보의 반례·누락 예외·경계·누락 별표를 찾는다. 찾으면 `hold`다.
6. 에이전트 사이의 불일치는 다수결로 통과시키지 않고 `hold`로 둔다(§36).
7. 에이전트에는 외부 도구·저장소·개인정보 API 권한이 없고 문서 속 지시를 따르지 않는다(§30.1).

### 57.3 AI 승인 정책

| 중요도 | 승인 조건 |
|---|---|
| C0: 지급 여부·금액·면책·감액·기산일·진단 정의·한도·특약 적용·계약 연결 | 서로 다른 모델 계열의 추출 2개 이상 일치 + 검증 에이전트 통과 + 레드팀 반례 0 + 모든 코드 검사 통과 + 교차 문서 충돌 없음. 하나라도 실패하면 `hold` |
| C1: 담보 관계·가입 조합·갱신·납입·계약 교체 영향 | 추출 일치 + 검증 통과 + 코드 검사 통과 |
| C2: 제목·탐색 태그·서식 | 코드 검사 + 검증 에이전트. 계층별 무작위 표본은 감사 에이전트가 재추출 |

- 일치 개수와 표본 비율은 제안값이며 P2 파일럿 측정으로 정한다.
- 단순 메타데이터라도 상품 버전을 바꾸는 필드는 C0다(v0.3 §31.2 유지).
- 승인은 담보 발생본 단위로 이용 등급(§28)을 올린다. 등급이 높을수록 조건이 늘어난다. 예를 들어 `simulatable`은 C0 전수 통과와 경계값 테스트 전부 통과를 요구한다.

### 57.4 사람 정답 없이 품질을 재는 방법

정답을 줄 사람이 없으므로 AI의 판정과 AI의 판정이 일치하는지를 재지 않고, 정답이 설계상 알려진 대조군으로 잰다.

- **합성 약관과 변이 주입(§34.2):** 정답이 설계상 알려진다. 부정어 삭제·경계 반전·단위 변경을 주입해 파이프라인이 잡는지 본다.
- **공시 예시 재현:** 상품요약서·사업방법서에 보험금 산출 예시가 있으면 규칙 엔진으로 재현한다. 불일치는 `hold`다.
- **교차 문서 일치율**과 **시간 홀드아웃**(같은 상품의 개정 전후 차이 탐지 재현).
- **표본 재추출 감사:** 공개된 담보 중 무작위 표본을 감사 에이전트가 처음부터 독립 재추출해 대조한다. 불일치율이 임계를 넘으면 해당 보험사·상품군의 승인을 중단한다. §32.4의 3/n 상한은 감사가 파이프라인과 독립일 때만 의미가 있으므로 이종 모델·이종 입력을 쓰고 상관 오류 가능성을 명시한다.
- **환류:** 사용자 오류 신고(증거 보기 화면의 "틀린 것 같아요"), 사용자가 올린 가입내역 PDF의 실제 조건과 규칙 결과의 대조.

한계: 이 측정치는 실제 오류율의 보증이 아니다. 모든 에이전트가 같은 방향으로 틀리면 감지되지 않는다(R14). 그래서 화면·웹 어디에도 "전문가 검수"·"검수 완료" 같은 표현을 쓰지 않고 "AI 검증"으로 표기하며, 증거 보기와 오류 신고를 항상 제공한다.

### 57.5 자동 안전장치와 사람의 역할

- **서킷 브레이커:** (a) 표본 재추출 불일치율 임계 초과, (b) 같은 규칙에 대한 사용자 오류 신고 임계 초과, (c) 가입내역 PDF 대조 불일치 임계 초과 중 하나가 발생하면 해당 규칙(또는 보험사·상품군)의 계산을 자동 중단하고 `hold`로 바꾸며 영향 사용자에게 안내한다(§15).
- **배포 차단:** 후보 릴리스가 그림자 비교(§37)에서 원인 설명 없는 금액 변경을 보이면 자동으로 배포를 막는다.
- **사람:** 건별 검수는 없다. 정책 소유자 1인이 임계값·모델 구성·사고 시 중단과 재개를 정책 수준에서 결정한다(가정, §56).
- 모든 AI 결정은 모델·프롬프트·입력 해시와 함께 감사 로그에 남긴다.

### 57.6 AI 분모 조사

- **에이전트:** 조사 에이전트 A(감독기관·협회 목록 경로), 조사 에이전트 B(보험사 공시실·상품 목록 경로), 대조 에이전트. A와 B는 모델 계열·검색 경로·시작 소스를 다르게 한다.
- **단계:** ① 보험사 목록(감독 목록과 협회 회원사 대조, 상호 변경 이력, 공제·우체국 후보는 별도 표시) ② 회사별 상품 목록(판매 상태·채널·기간 필터 전수, `query_matrix` §23.2) ③ 상품별 기대 문서(§23.3) ④ 본문 참조를 따라간 문서 확인.
- **완전성 추정:** A와 B가 독립 조사한 항목 수를 n_A, n_B, 공통 항목 수를 m, 합집합 크기를 u라 하면 누락 추정은 n_A×n_B/m − u다. 두 조사가 같은 소스를 공유하면 누락이 과소 추정되므로 경로를 일부러 다르게 한다. 새로 발견되는 항목이 0이 되고 추정 누락이 임계 이하가 될 때까지 반복한다.
- **기록:** 항목마다 발견 경로·시각·증거를 SourceRegistry와 ExpectedDocument(§6, §23.3)에 남긴다. 추정치는 추정으로 표시하며 "전수"는 쓰지 않는다(§43.2).
- **접근 규칙:** 허용 호스트·요청 제한·robots 확인을 따르고 인증을 우회하지 않는다(§24).
- **재조사:** 주 1회 전체 재대조(§25)도 같은 에이전트가 수행한다.
- **환류:** 사용자가 올린 PDF에서 분모에 없는 상품이 나오면 분모 누락 신호로 기록하고 자동 재조사를 건다.
- **한계:** AI가 놓친 항목은 AI 조사만으로는 드러나지 않을 수 있다.

## 58. 스켈레톤: 첫 출시에서 뺀 기능 (사용자 결정)

### 58.1 스켈레톤의 뜻

미리 정해 두는 것은 데이터 모델(테이블·enum), API 경로와 권한 이름, 기능 플래그, 문서다. 구현·화면·노출은 없다.

- 화면·내비게이션·웹 페이지·광고 어디에도 노출하지 않는다. 죽은 UI를 만들지 않는다.
- API 경로는 비활성이다. 플래그는 기본 off이며 켜려면 해당 기능의 게이트를 먼저 통과해야 한다.
- 나중에 마이그레이션이 필요 없도록 스키마만 미리 둔다. 사용자 데이터는 수집하지 않는다.
- 민감도 경계 테스트(§52.3, v0.3 §12.6)는 스켈레톤에도 적용한다.
- 스켈레톤을 켜는 것은 별도 결정이다.

### 58.2 목록

| 기능 | 미리 두는 것 | 두지 않는 것 | 켜는 조건 |
|---|---|---|---|
| 상담 연결 | `Agent`, `AgentScope`, `ConsultationRequest`, `AccessGrant`, `consultation_enabled` 플래그, 비활성 `POST /consultation-requests` | 화면, 설계사 목록, 예약 | 설계사 포털과 함께(§45.3 메모) |
| 설계사 포털 | `/agent` 라우트 예약, 설계사 역할 | 로그인, 화면 | 별도 결정 |
| 개인 견적 | `personal_quote` 가격 종류, 만료 시각 필드, `quotes_enabled` 플래그 | 견적서 업로드 경로, 견적 연계, 화면 | 가격 수집 명세 §14 |
| 설계 검증 | `PolicyImport`의 제안서 유형 슬롯 | 화면 | 개인 견적과 함께 |
| 콘텐츠·광고·구독 | 광고 슬롯 enum, 구독 플랜 테이블 | 화면, 결제 | 설계사 포털과 함께 |
| 가족력 | `private_health` 라벨, 입력 필드 스키마 | 입력 화면 | 별도 결정 |
| 가족 초대·연결 | 프로필 연결 관계 테이블 | 초대 화면 | 별도 결정 |
| DNA 연계 | `genetic_private` 라벨, 저장 영역 분리 | 구현 일체(설계 동결, v0.3 §12) | 별도 게이트 |

### 58.3 첫 앱이 채우는 것

개인 견적이 없으므로 앱은 "내 정확한 보험료"에는 답하지 않는다. 대신 다음에 답한다.

- 내게 필요한 담보와 지금 비어 있는 곳
- 같은 담보가 보험사마다 어떻게 다른지, 공개 가격과 함께
- 보장과 불이익을 함께 본 전후 차이(얻는 것·잃는 것·확인할 것)
- 소비자에게 불리하게 작용할 수 있는 조건(§59.6)

## 59. 철저한 크롤링과 일일 갱신 (사용자 결정)

### 59.1 기준: 소비자 편에서 읽는다

상품 설명이 판매 쪽 관점으로 이루어지는 정보 비대칭 구조에서, 앱은 원문 조건을 빠짐없이 읽어 보여준다. 소비자에게 유리한 조건과 불리하게 작용할 수 있는 조건을 모두 다룬다. 판단 기준은 소비자 이익이며 광고비·수수료와 독립이다(불변 원칙 1). 불리한 조건은 평가어가 아니라 근거가 연결된 사실로 표시한다(불변 원칙 5·7).

### 59.2 크롤링 대상 소스

아래는 후보 계층이며 실제 목록은 AI 분모 조사(§57.6)가 확정한다.

| 계층 | 대상 | 가져올 것 |
|---|---|---|
| 금융당국·공공데이터 | 금융위원회 개방 데이터(생명보험 금융통계 등, v0.3 §21), 금융감독원의 보험 관련 공시·통계 | 보험사 목록, 영업 통계, 제도 용어·분류 |
| 협회 비교공시 | 생명보험협회·손해보험협회 상품 비교공시 | 상품 목록, 판매 상태, 보험료, 보험사 공시실 진입점 |
| 보험사 공식 상품공시실 | 모든 보험사(분모 조사로 확정) | 약관, 사업방법서, 상품요약서, 특약, 별표, 공시 예시(보험료 포함), 개정 이력, 판매 중지 목록 |
| 보험사 공지 | 약관 개정·판매 중단 공지 | 변경 시점과 내용 |

- API가 있으면 API를 먼저 쓴다(v0.3 §6).
- 가격은 `docs/masterplan/가격_수집_명세.md`를 따른다. 보험료는 가입 조건·특약 구성·기준일과 함께 수집한다.
- 협회 목록과 보험사 목록을 대조해 한쪽에만 있는 상품을 차이 목록으로 만든다(§23.1).
- 수집은 공개 경로로만 한다. 로그인·접근 제한·차단을 우회하지 않고 요청 제한을 지킨다(§24). 이 범위 안에서 최대한 철저히 한다.

### 59.3 매일 갱신

- 등록된 모든 소스를 매일 확인한다. 소스별 "마지막 확인이 24시간 이내" 달성률을 지표로 둔다.
- 변경이 잦은 소스는 허용 요청량 안에서 시간 단위로 확인한다.
- 전체 목록 재대조, 전체 바이트 대조, 과거 문서 정합성 점검의 주기는 v0.3 §25를 따른다.
- 새 문서와 변경 문서는 우선 큐에서 원문을 먼저 보존하고, 의미가 바뀐 부분만 재추출·재검증하며, 영향받는 디지털 트윈 조각만 재컴파일한다(§37).
- 크롤링에 실패한 날은 실패 이유를 기록하고 마지막 검증 데이터를 유지하며 화면에 최신성 경고를 띄운다. 데이터 부재·수집 실패·판매 중단은 구분한다(불변 원칙 10).
- 소스별 마지막 확인·성공 시각을 `/coverage`에 공개한다.
- 일일 확인은 24시간 안에 모든 변경을 안다는 뜻이 아니다. 게시 시각을 알 수 없으면 최초 관측 구간만 말한다(v0.3 §25).

### 59.4 철저함의 측정

v0.3 §23.4의 여섯 지표를 보험사·상품군·문서 형식별로 `/coverage`와 관제 콘솔에 공개한다. 목록 조회율, 원문 확보율, 조항 처리율, 참조 해결률, 실행 가능률, 최신성 충족률이다. 다음을 추가한다.

- 소스 수 대비 어댑터 보유율
- 일일 확인 달성률
- 분모 추정 누락률(§57.6)
- 담보 이용 등급 분포(`indexed_only` → `explained` → `simulatable` → `comparable`, §28)
- 가격 확보율·최신성·조건 완전성(가격 수집 명세 §11)

하나의 완전성 숫자로 합치지 않는다.

### 59.5 크롤링에서 디지털 트윈까지

크롤 → 원문 보존(해시) → 복원(§26) → 다축 라벨링(§28) → 근거 단위 필드(§29) → AI 검수(§57) → 규칙 컴파일(§34) → 검증 릴리스(§36~37) → 앱. 매일 갱신분은 후보 릴리스로 쌓이고 그림자 비교를 통과하면 서비스에 반영된다. 이 흐름이 제품의 핵심 자산이다(v0.3 §1).

### 59.6 소비자에게 불리하게 작용할 수 있는 조건의 라벨

담보 발생본마다 다음을 사실 라벨로 추출해 근거를 연결한다. 평가어는 쓰지 않는다.

| 라벨 | 예 |
|---|---|
| 면책·감액 | 면책기간, 감액기간과 감액률 |
| 제외 | 제외 질환·사고, 제외 별표 |
| 갱신 구조 | 갱신형 여부, 갱신 주기, 갱신 시 보험료 변동 가능 |
| 종료 | 보장 종료 나이·시점, 만기 후 보장 공백 |
| 지급 한도 | 횟수·기간·누적 한도, 1회 한도 |
| 환급 구조 | 해지환급금 유무와 구조(무해지환급형 등) |
| 종속 | 주계약 해지·소멸 시 특약 소멸, 필수 동시 가입 |
| 중복 | 내 다른 계약과 같은 지급 사유가 겹치는지 |
| 정의 차이 | 담보명이 같아도 질병 정의·진단 기준이 다름 |

화면에서는 "확인할 조건" 칩으로 보여준다. 칩은 사용자의 선택 상황에서 지급에 영향을 주는 순서로 정렬한다. 개수 상한으로 숨기지 않으며, 지급에 영향을 주는 조건은 개수와 상관없이 첫 층에 보인다(불변 원칙 9, §35).

## 60. 읽지 않는 UX 규칙 (사용자 결정)

사람들은 읽지 않는다. 읽어야 이해되는 화면은 실패다. 시각 완성도와 사용감이 최우선이다(§51.4).

### 60.1 규칙

1. 한 화면에 메시지 하나, 큰 숫자 하나, 주요 행동 하나.
2. 읽기 전에 보이는 것을 먼저 둔다. 큰 숫자, 막대·게이지, 아이콘, 상태 칩이 먼저이고 문장은 그다음이다.
3. 텍스트 예산(제안값, 사용성 시험으로 조정): 제목은 한 줄 약 12자, 보조 문장은 한 줄, 담보 행 설명은 한 줄, 화면당 본문 합계 약 80자 안팎. 넘는 내용은 접거나 한 탭 뒤로 보낸다.
4. 직접 조작한다. 슬라이더·스와이프·탭으로 가정을 바꾸면 150~250ms 안에 숫자와 막대가 바뀐다.
5. 한 줄 결론은 문장 템플릿에 숫자를 넣어 만든다. 자유 생성 문장은 쓰지 않는다(불변 원칙 7). 예: "암 진단 때 필요한 돈의 40%만 채워져 있어요."
6. 미확인은 점선·물음표로 구분한다(§44.3). 0원처럼 보이게 하지 않는다.
7. 세 층(선택 → 이유 → 증거)을 유지한다. 증거는 원문 페이지 이미지에 해당 문장을 하이라이트해 한 번에 보여주며 긴 약관 문장을 그대로 읽게 하지 않는다.
8. 카드로 채우지 않는다. 타이포·정렬·간격으로 구분하고(v0.3 §5) 테라코타 포인트 색으로 시선을 모은다.
9. 숫자 카운트업, 부드러운 전환, 촉각 피드백으로 감각적인 완성도를 만들되 정보 전달을 방해하지 않는다.

### 60.2 홈: 보장 지도

홈의 중심은 격자 아이콘이다. 칸은 암·뇌·심장·입원·수술·소득 중단·간병·사망 같은 상황이며 실제 칸은 담보 분류(§28)에서 정한다. 각 칸의 채움은 확인된 보장을 가정한 필요 금액으로 나눈 값이다. 미확인 칸은 점선이다. 한눈에 구멍이 어디인지 보인다.

```text
[한 줄 결론]  암 진단 땐 필요한 돈의 40%만 채워져 있어요
[암 ▓▓░░] [뇌 ▓▓▓▓] [심장 ░░░░] [입원 ▓▓▓░]
[수술 ▓▓░░] [소득중단 ┄┄] [간병 ┄┄] [사망 ▓▓▓▓]
확인 필요 3건 ›                    [내 설계 보기]
```

칸을 탭하면 해당 상황의 만약에 화면과 내 설계로 이어진다.

### 60.3 UX 지표

- 5초 안에 화면 목적을 파악, 30초 안에 두 안의 가장 큰 차이를 설명(v0.3 §17).
- 잘못 이해한 비율.
- 첫 화면 본문 글자 수와 화면당 읽기 행동(스크롤·확대) 횟수.
- 증거 보기 진입률. 너무 낮으면 신뢰 근거가 안 보이는지, 너무 높으면 첫 층이 불명확한지 점검한다.
