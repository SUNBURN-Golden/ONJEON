**[설계 담당 결정(감리 대상)] 구역 경계 세 가지 보강.**

1. **설명 템플릿은 knowledge가 만들고 api는 렌더링만 한다.** DATA_PIPELINE_CONTRACT §6 "하나의 근거, 두 표현"에 따라 사람용 문장 템플릿은 DSL과 같은 릴리스에서 같은 `evidence_refs`로 만들어지고 대조 검사를 통과해야 릴리스된다. api는 템플릿에 엔진 결과값과 주장 값을 채운다. 불변 원칙 7의 뜻은 **AI의 자유 문장이 지급 조건·금액을 결정하지 못한다**는 것이다. 지급 조건·금액·판정은 엔진 결과와 accepted 주장에서만 오고 템플릿으로 표현한다. 근거에 충실한 대화·질문 표현(다음 질문 고르기·다듬기, 결론을 바꾸는 입력의 설명)은 원칙 7이 금지하는 것이 아니며, 그 문장은 `statement_kind`로 사실·판단·가정·계산·미확인을 구분해 표시한다(02 §1.5, D-13: 자유 대화 화면은 첫 출시에 없음). 구현계획 §12에는 이 모듈이 없었다.
2. **`packages/ontology/`는 knowledge 소유의 순수 라이브러리다.** T-box JSON 자체는 contracts(`packages/schemas/ontology/tbox.json`)에 둔다. 라이브러리는 T-box 적재, 제약 검사기 K1~K16, 집합 연산, 범위 관계 계산, 입력 단계용 소속 판정 함수를 제공한다. twin-runtime은 이 라이브러리를 **릴리스된 A-box 스냅샷**에만 적용한다(온톨로지 설계안 §11, ADR-0014 §4). 구현계획 §12는 `packages/ontology`를 contracts로 분류했는데, 코드(검사기)와 계약(T-box)을 나눈다.
3. **personal은 docproc의 "개인용 배포"만 부른다.** 같은 코드, 다른 컨테이너, 다른 자격 증명, 네트워크 차단. 공시용 docproc은 R2 파생 버킷에 쓰고, 개인용 docproc은 개인 저장소에만 쓴다(BLUEPRINT §9.4 경계 원칙 2·4).

## 4. 핵심 흐름: 질문 → 지식 조회 → 입력 단계 → 엔진 → 설명·근거

온톨로지 검증(검증/ontology_check.py `resolve()`·`explain()`)이 실제로 수행한 단계를 서비스 설계로 옮긴 것이다. 단계마다 어느 구역이 맡는지와 검증에서 확인된 사례를 붙였다.

| 단계 | 구역·모듈 | 입력 | 출력 | 검증 결과와의 대조 |
|---|---|---|---|---|

## 5. 디지털 트윈(U-02)이 걸리는 모듈

**[사용자 결정 2026-10-12]** 디지털 트윈을 주요 기능으로 적극 활용한다. 통합안 §2.9의 표를 모듈로 옮기면 다음과 같다.

| 트윈 종류(ADR-0018 §2) | 구성 | 사는 곳 | 실행 경로 |
|---|---|---|---|
| 상품 트윈 | 판매본 + 담보 C0 주장 + 실행 규칙 + 입력 단계 판정 함수 + 설명 템플릿 | 지식 릴리스(공개) | `twin-runtime::product_twin(release, sales_config, coverage)` |
| 개인 계약 트윈 | 계약 스냅샷(사용자 확인 필드) + 적용 약관 이력(근거로 확인한 판매본·문서 판) + 특약·가입금액 + 특별조건 + 누적 사용량 | 개인 DB(비공개). 공개 노드는 릴리스 고정 ID로만 참조 | `twin-runtime::contract_twin(snapshot, release_pin)` |
| 시나리오 계산 | 사건·가정·확인된 사실 → 입력 단계 → 엔진 | 호출 시점에만 존재. 결과는 요청자 영역에 저장 | `twin-runtime::evaluate(twin, scenario)` |

트윈 축 과제(03_작업명세 ★): T-TW-01 twin-runtime 골격·입력 단계, T-TW-02 rule-0.2, T-TW-03 컴파일러(K9), T-TW-04 W2~W4, T-TW-05 여러 계약·두 안 차이·W5·W6, T-API-03 scenarios, T-API-05 evaluations·plans, T-PS-02 개인 계약 트윈, T-MB-02·T-MB-04 화면. S1부터 상품 트윈 결과가 화면까지 가도록 T-TW-01 → T-API-03 → T-MB-02 순서를 고정한다.

**적극 활용의 경계(변하지 않음):** `simulate` capability가 enabled인 담보에서만 트윈 결과를 보인다. 승인 없이 결과를 켜지 않는다. K11이 이를 릴리스 단계에서 강제하고 api가 다시 검사한다.

|---|---|---|
| 약관 판 | 문서 판 = 원본 해시 + 문서 역할 | 원본(관측) → 문서 구획(판단, 지문) → 약관 본문 판(판단, ReviewDecision으로만 accepted) → 계열. 본문이 같아도 참조 별표·정의·적용 범위가 다르면 다른 판 |
| 릴리스 | 주장 해시 하나 | 구성원 목록(주장·노드·조항·구획·판·공백·가격·기준 릴리스 참조) + 규칙 파일 해시 + 내용 해시. 재현과 사용 제한은 다른 장치 |
| 개인 계산 보류 | 판 불명확 → 개인 계산 전체 보류 | 결론별 의존 기록. 미확인과 겹치는 결론만 보류, 독립 결과 유지, 합산은 포함하지 못한 계약을 밝힘 |
| 필요성 탐색 | 관심 담보·상품 조회 | 판단 기준 관리(영역 C) + 결과(유지·추가 없음·보류·추가 검토)와 이유. 서비스 적용은 별도 승인 관문(D-08) |

## 8. 저장소 분리 준비 (BP-D-15)

data를 첫 분리 대상으로 둔다. 분리 조건(독립 빌드·배포·버전 고정·호환성 검사·통합 재현)은 03_작업명세 T-CT-04(계약 패키지 버전 고정)와 T-DT-05(data 독립 빌드)로 준비한다. 이 묶음에서 분리를 실행하지 않는다.

## 9. 이 설계가 정하지 않는 것

- 클라우드·배포 공급자(D-03), AI 검수 모델 계열(D-02), 정책 소유자.
- 수치 임계값(D-19).
- 규제 검토 대상(추천·가격 비교·상담 적용 요건 D-18, 원문 발췌 재배포 D-12). 이 문서는 판단하지 않는다.
