# 공개 보험 지식 모델 1차 토의 정리 (데이터 모델 묶음 1)

상태: **토의 자료. 미확정.** 2026-10-11 | 정리 대상: [공개 보험 지식 모델 토의 초안](공개지식_모델_토의초안.md) §0~§11, [가입 구성 검증 사례](가입구성_사례_굿앤굿1540.md), [실제 사례로 본 식별 표현](사례_표현_검토.md), [데이터 모델 토의 보완안](데이터모델_토의_보완안.md), 조사 기록 A~H

> **표기:** **토의상 제안(사용자)** = 사용자가 토의에서 제시했으나 "이 방향으로 확정해서 반영하라"는 지시가 없는 사항. **검토 의견(구현자)** = 구현자의 초안·의견. **진행 지시(사용자)** = 토의 순서·방식에 대한 지시이며 설계 결정이 아니다. 이 문서에 확정된 설계 결정은 없다.

**진행 지시(사용자):** 묶음 1의 1차 토의를 정리하고 묶음 2(개인 계약)로 넘어간다. 정리는 설계 확정이나 구현 승인이 아니다. 정본(BLUEPRINT, SYSTEM_CONTRACT, DATA_PIPELINE_CONTRACT, PREMIUM_DATA_CONTRACT, DECISIONS, VOCABULARY)은 고치지 않았다. ADR 반영은 전체 구조가 확정될 때 묶어서 한다.

## 1. 토의에서 모인 구조 (토의상 제안·사용자)

| 층 | 무엇인가 | 핵심 규칙 |
|---|---|---|
| 상품·계열 | 소비자가 찾고 개정 흐름을 이해하는 단위 | 탐색용. 적용 약관이나 계산을 확정하는 근거로 쓰지 않는다. 개인 계약 연결에서는 후보를 찾는 단서까지만 |
| 판매 구성의 틀 | 특정 시기에 제시된 가입 조건과 구성의 틀 | 가격이 다르다는 사실만으로 나누지 않는다. 먼저 무엇 때문에 달라졌는지를 구분한다 |
| 구성 요소와 제약 | 종·형·심사 유형·가입금액·특약·기간 등과, 그 사이의 종속·동시 가입·금지·성별·한도 같은 제약 | 요소마다 정해지는 방식을 붙인다(① 사용자 선택 ② 고지·심사에 따른 결정 ③ 필수 부가 ④ 다른 구성에 따른 종속 ⑤ 계약 중 사건에 따른 변경). 둘 이상 붙을 수 있다 |
| 가입 구성 후보 | 틀 안에서 표현할 수 있는 조합 | 확인 수준을 나눈다: 약관에 존재함 / 공개 가입 규칙에 부합함 / 특정인에게 가입 가능함. 앞의 수준이 뒤의 수준을 뜻하지 않는다 |

여기에 다음 관측과 판단을 연결한다.

| 연결 대상 | 핵심 규칙 |
|---|---|
| 약관 | 세 수준을 잇는다: 원본 파일·구획(근거가 어디 있나) / 약관·특약의 판(어떤 내용과 적용 범위인가) / 조항·조건의 버전별 연결(무엇이 바뀌고 어떤 규칙에 영향을 주나). 조항은 번호가 아니라 내용으로 대응시킨다. 참조하는 정의·별표·보통약관 조항을 함께 연결한다 |
| 담보 | 이름이나 정의 하나로 동일성을 판정하지 않는다. 지급 사건·제외·기간·횟수·한도·금액 산식 등 비교 축별로 대응한다 |
| 가격 | 독립된 관측으로 보존하고 출처·기준일·산출 조건·구성 내역과 연결한다. 구성의 속성으로 바로 붙이지 않는다. 다른 조건이 같다고 확인하지 않았으면 차이의 원인을 단정하지 않는다. 다른 구성에 적용하지 않는다 |
| 미확인 후보 | 출처에서 발견한 대상을 추적한다. 상품·특약·구성 묶음 중 무엇인지 모르면 유형을 억지로 정하지 않는다 |

**공통 원칙(토의상 제안·사용자, [보완안](데이터모델_토의_보완안.md) §2):** 출처가 보여 준 사실은 그대로 보존하고, 우리가 내린 동일성·적용 관계 판단은 따로 기록한다. 판단이 바뀌어도 원래 개체와 과거 결과를 잃지 않는다.

**표현 원칙(토의상 제안·사용자, 12차):**
- 모델링 제안과 관측을 구분한다.
- 상태를 하나의 목록으로 섞지 않는다. 주장마다 근거, 확인한 것, 가정, 남은 것을 나눈다.
- 규칙은 확인한 문서·조항의 범위 안에서만 기록한다. 한 상품에서 본 규칙을 공통 규칙으로 올리지 않는다.

## 3. 정정된 것 (이력)

| 처음 안·기록 | 바뀐 것 | 출처 |
|---|---|---|
| 약관 판 ID = 원본 해시 | 원본·구획·판·계열·적용 관계를 나눔 | 보완안 §3.1 |
| 보조 출처는 판매 구성을 만들지 않음, `unlinked` | 어느 출처든 후보를 만든다. 다만 유형을 억지로 정하지 않는다 | 보완안 §3.2, 초안 §10.4 |
| 약관 해시가 같으면 `same_as` 승인 | 문서 동일성은 근거 하나일 뿐 | 보완안 §3.3 |
| 되돌릴 때 새 ID | 이미 있던 둘의 잘못된 병합은 원래 ID를 복원 | 보완안 §3.4 |
| 조항은 판 안의 위치 | 조항·조건의 버전별 연결과 참조 연결 | 초안 §10.2 |
| 선택 요소, 유효한 가입 구성 | 구성 요소(정해지는 방식), 가입 구성 후보(확인 수준) | 초안 §11 |
| 현대 LO-5/LO-6 = 두 심사 유형(추정) | 약관·사업방법서가 바이트 단위로 같아 맞지 않음 | H §2.1 |
| 협회 가격 차이 = 심사 유형 탓 | 공시된 조건 표기의 차이만 말할 수 있음 | 가입 구성 사례 §6.3 |

## 4. 열린 쟁점 (묶음 1에 남김)

| 쟁점 | 종류 |

## 5. 묶음 2·3으로 넘기는 것

- **묶음 2(개인 계약):**
  - 개인 계약은 공개 쪽 "가입 구성 후보"가 아니라, 그 계약에 **실제로 적용된 구성**을 기록한다.
  - 판매 구성·특약·적용 본문 판으로의 연결은 원래 ID로 기록한다.
  - 특정인 가입 가능 여부와 인수 결과는 공개 자료로 알 수 없다. 개인 모델이 추론하지 않는다.
- **묶음 3(판단과 결과):**
  - 결과마다 어떤 사실·조항·답변에 의존했는지 의존 기록을 남긴다.
  - 공개 쪽 판단이 정정되면(병합 취소, 조항 대응 변경, 담보 대응 보류) 영향 범위를 찾을 수 있어야 한다.

## 6. 나중에 정본에 반영할 때 볼 것 (지금은 고치지 않음)

- SYSTEM_CONTRACT §5 `ProductVersion`("상품 계보·개정판·채널·적용 기간")을 상품·계열 / 판매 구성의 틀 / 구성 요소로 나눌지
- `CoverageOccurrence`의 "공통 개념"을 비교 축별 대응으로 바꿀지
- PREMIUM_DATA_CONTRACT의 `package_binding`·`condition_sources`를 가격 관측의 연결 상태와 맞출지
