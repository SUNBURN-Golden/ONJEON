# Decision: should M1 product tasks (T-CT-01, T-CT-02, T-DT-*) start alongside T-OP-09's VM verification, instead of all bot cycles going to daemon and meta-work?

Decided by Claude Sonnet 5.5 xhigh (ONJEON autoloop, 2026-11-10 20:35 KST); reversible.

**Decision:** The daemon is not a product gate, but it is also not what currently blocks M1. The handoff README §3 stage 2·3 sentence `제품 과제(T-CT-01 등)는 임대하지 않는다` is historical and is superseded by the dated `[상태 기록 2026-10-26]` note in the same section; the remaining T-OP-09 PARTIALs (R6, R7, R9, R11, R21) and G47/G51~G57 are dev-tool follow-ups. `tasks.json` lists T-OP-00 or T-OP-09 as prerequisites only for the final release audit T-OP-08, where they are an axis-5 release-reporting dependency, not a start gate on any product task. Therefore the residual daemon work does not freeze product tasks. **However, this does not authorize starting M1 now.** The binding start gate is the V1 milestone: BLUEPRINT §9.2 records V1 as `설계 탐색 완료(2026-10-09), 관문 미통과` with `완전 재현 8/14`; §9.5 says satisfying task prerequisites, decision gates, `done_criteria`, `required_test_ids` and `tests` does not omit the §9.2 milestone gates; §10 rule 6 says `마일스톤 관문을 건너뛰지 않는다`; ADR-0013 §5 says `M1은 V1의 관문을 통과한 뒤 시작한다`; and [audit4-v1-gate-closure](audit4-v1-gate-closure.md) keeps `V1 미통과와 M1 진입 차단`. `tasks.json` is a subordinate contract (BLUEPRINT 하위 계약; ADR-0019 limited adoption; its own `_status` says `상위 계약을 우선한다`), so the empty `prereq_tasks`/`decision_gates` on T-CT-01/T-CT-02 cannot waive the V1 gate. **Do not lease or start any remaining unmerged product task** — the M1/S0 contracts work (T-CT-*) or the downstream T-DT-* tasks — until V1 is judged passed with the evidence audit4-v1-gate-closure requires and BLUEPRINT §9.2/§11 are updated. Once V1 passes, the remaining unmerged M1 tasks may be leased only as their own product prerequisites clear. Tasks already merged are not re-leased: T-CT-01 (#102), T-CT-02 (#118), T-DT-01 (#139) and T-DT-02 (#172) are `MERGED` in the supervisor state. T-CT-02's `DEC-CANON-T-CT-02` "병합 미승인" wording is a separate canon-change authorization note; it is not an open start gate and does not reopen the merged task. If bot cycles are going to daemon or meta-work while M1 is blocked, that is expected until V1 closes: redirect those cycles to V1 closure work, not to leasing M1. This record agrees with, and does not override, the concurrent `audit5-v1-gate-before-m1` decision from the same round: do not lease/start T-CT-* until V1 is judged passed.

**Why:** (1) The daemon half of the finding is already settled in the tree. The `[상태 기록 2026-10-26]` note in [그록봇_인계 README §3](../../docs/blueprint/proposals/설계검토_결과/그록봇_인계/README.md) replaces the stage 2·3 restriction, records T-OP-09 as merged (#98) with PASS 17/PARTIAL 5/FAIL 0, and states `남은 데몬 후속 과제는 제품 과제를 막지 않는다. 데몬 작업과 제품 과제는 병행한다`; the only exception is T-OP-08, whose release report cites the daemon records. (2) `tasks.json` gives T-CT-01 and T-CT-02 `prereq_tasks=[]` and empty start gates, and T-OP-09 appears in exactly one prerequisite list, T-OP-08's. `tools/tests/test_pr_policy.py::SerialDaemonPrerequisite` enforces that no product task other than T-OP-08 depends on T-OP-00/T-OP-09. (3) 09 §5 and the T-OP-09 task note say the daemon is a development tool, not part of the shipped product. (4) The V1 half is the governing constraint that the earlier draft of this record missed. BLUEPRINT §9.2 (line 276) and §11 (line 359) still record V1 unpassed at 8/14 complete reproduction, with cross-family review and S1/S6 open; §9.5 (line 329) and §10 rule 6 (line 340) forbid skipping a milestone gate; ADR-0013 §5 (line 20, `상태: 확정(사용자 결정)`) puts V1 before M1; [audit4-v1-gate-closure](audit4-v1-gate-closure.md) (line 5) keeps the M1 entry block. (5) ADR-0019 adopts `tasks.json` only as a BLUEPRINT sub-contract, and `tasks.json` line 2 itself says `상위 계약을 우선한다`, so the absence of a dependency in the subordinate file is a bundle defect (tracked by the concurrent `audit5-v1-gate-before-m1` node), not a waiver. (6) Earlier decisions already rank the work this way: [audit3-pause-daemon-for-product](audit3-pause-daemon-for-product.md) freezes daemon expansion so V1 → M1 → M2 can proceed, and [audit4-build-phase-freeze](audit4-build-phase-freeze.md) keeps the V1 remaining evidence ahead of product implementation. (7) The as-run supervisor state confirms the real blockers are product-side and V1-side, not daemon-side: T-CT-01/T-CT-02/T-DT-01/T-DT-02 are merged; T-DT-03/05/06 are skipped on parked T-OP-02/T-DT-04; T-DT-04 is parked on review rounds (D-04 since resolved). The new regression test [tools/tests/test_audit5_product_freeze_vs_daemon_gate.py](../../tools/tests/test_audit5_product_freeze_vs_daemon_gate.py) pins both halves of this policy and was run in this fix round.
