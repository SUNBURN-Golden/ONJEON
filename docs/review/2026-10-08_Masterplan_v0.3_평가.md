# 마스터플랜 v0.3 평가

평가일 2026-10-08 | 대상 `docs/masterplan/ONJEON_Masterplan_v0.3.md` (41절, 990행) | 첨부 화면: 내 설계 탭 시안

## 0. 한 줄 판정

디벨롭 가능하다. 설계 사상(불변 원칙·근거 추적·결정적 계산·3값 논리·유전정보 경계)과 제2부의 데이터 방법론은 이미 상용 수준의 요구사항이다. 다만 **"앱·사이트 개발 계획"으로서는** 네 가지가 비어 있다.

1. 앱·사이트의 구현 설계가 없다. 기술 스택, 저장소 구조, 환경, CI/CD, 테스트 전략, 모바일 릴리스 절차가 모두 미정이다.
2. 일정과 병렬화가 없다. 로드맵 A~H는 순차 나열이며, 데이터 파이프라인이 끝나야 앱이 시작되는 구조로 읽힌다.
3. 핵심 외부 의존(실견적, 계약 가져오기, AI 제공자)에 대한 대안 설계가 없다. 특히 실견적이 없으면 첨부 화면(내 설계)이 성립하지 않는다.
4. 사이트(공개 웹·관제 콘솔·검수 작업대) 계획이 없다.

규제·사업 구조 검토는 이 평가의 범위에서 제외한다. 이 네 가지를 채운 것이 `docs/masterplan/ONJEON_Masterplan_v0.4_제3부_구현계획.md`다.

## 2. 구조적 문제

### 2.1 분량 불균형

대략 데이터 파이프라인 60%, 소비자 앱 20%, 디지털 트윈 10%, 사이트 0%다. "독립 모바일 앱 + AI API"가 제품인데 앱의 화면 상태·내비게이션·계정·오류 처리·릴리스가 없다. 웹은 §5의 한 문장("태블릿·웹에서는 동일한 정보 구조를 확장한다")뿐이다.

### 2.2 결정 유보의 분류가 없다

§20은 "구현 전 결정할 항목"을 나열하지만, 어떤 유보가 개발 착수를 막고 어떤 유보가 막지 않는지 구분하지 않는다. 예를 들어 가칭 명칭은 개발을 막지 않는다. 실견적 확보 방식은 내 설계 탭의 화면 사양을 바꾸므로 막는다. 유보마다 **기본값 + 전환 조건**을 적어야 한다.

### 2.3 중복과 교차 참조 부재

- §7(크롤링과 변경 처리) ↔ §25(스케줄) ↔ §24.4(고장 탐지)가 같은 주제를 세 번 다룬다.
- §17(검증 계획) ↔ §32(정답셋) ↔ §34.2(규칙 테스트)가 겹친다.
- §14(관제 화면) ↔ §39 작업 7이 겹친다.
- §18 로드맵 단계와 §39 작업 1~7의 대응 관계가 없다.

제1부와 제2부가 충돌하면 제2부가 우선한다는 규칙(§22 머리말)은 있으나, 어디가 충돌하는지 표시가 없다. v0.4부터는 문서를 주제별로 분할하고 각 문서에 소유자·상태·상위 문서를 붙이는 편이 낫다.

### 2.4 DNA 절의 비중

§12는 단계 H(마지막)인데 분량은 제1부에서 가장 길다. 설계를 지금 고정하는 취지는 타당하나, 초기 팀의 주의가 분산된다. "설계 동결, 구현 금지, 게이트 통과 전 활성화 불가"를 문서 머리에 명시하고 별도 파일로 분리할 것을 권한다.

## 4. 세부 지적

- §3.1 "기존 대화 기록을 가져오는 ChatGPT 로그인에 의존하지 않으며" — 대화 과정의 결정 흔적이 제품 문서에 남았다. 결정 기록(§20)으로 옮기고 본문에서 삭제한다.
- §5 "사용자가 선택한 3번째 화면 구성을 기준으로 한다" — 문서 밖 참조다. 첨부 화면을 `docs/design/`에 저장하고 파일명으로 참조한다.
- §12.4 "세 화면을 기본으로 한다"고 하면서 네 단계를 나열한다.
- §13 개념 API에 인증, 동의 철회, 계정 삭제, 데이터 내보내기 엔드포인트가 없다. 열람·정정·삭제 요청을 처리할 경로가 API에 보여야 한다.
- §7 운영 목표 "공개된 계산 규칙 원문 연결 100%", "전문가 승인 테스트 전부 통과" — 분모와 측정 주기를 §23.4 방식으로 정의해야 측정 가능하다.
- §13 "검색 결과를 계산의 권위 데이터로 쓰지 않는다"는 원칙은 좋다. 그러나 RAG 방식의 AI 질문 기능(§12.4 'AI에게 질문하기')과의 관계가 없다. 질문 기능이 검색 색인을 쓰되 금액은 규칙 엔진 결과만 인용하도록 §47.3에 명시했다.
- §16 사업 모델은 "구독 + 명시적 광고"가 기본값이고 "성사 수수료·리드 과금"은 유보다. 구현 관점에서는 두 모델이 데이터 구조(상담 요청·과금 이벤트)를 다르게 요구하므로, 유보 상태에서도 '리드 과금 없음'을 코드의 기본값으로 두고 전환 조건을 결정 기록에 남긴다.
- §34.1 JSON 예시에 기준 시각(as_of)과 시간대가 없다. 날짜 경계 테스트(-1/0/179/180)는 KST 자정 기준인지 명시해야 한다.
- §32.4 "3/n" 규칙은 적절하다. 다만 군집 상관 언급만 있고 상품 단위 표본 설계가 없다.
- 용어: '디지털 트윈', '트윈'을 소비자 화면에서는 쓰지 않는다는 규칙(§4 "구현 용어는 숨긴다")과 §10 제목이 충돌하지 않도록 내부 용어로 한정한다.

## 6. 우선순위 권고

1. **합성 픽스처 우선 수직 슬라이스**(ADR-0002). 데이터 파이프라인 완성을 기다리지 않고 합성 상품 3개로 홈→만약에→내 설계→비교를 끝까지 동작시킨다. UX·규칙 엔진·API 계약을 먼저 검증한다.
2. **실견적 3단계 전략**(§47.1)을 확정한다. 1단계 공시 예시 보험료, 2단계 사용자 제출 견적 대조, 3단계 제휴 견적 API. 1단계만으로 출시 가능한 화면 사양을 쓴다.
3. **계약 가져오기 경로를 4개로 확장**(§47.2)하고 마이데이터 허가 또는 제휴 여부를 사업 결정 항목에 올린다.
4. **기술 스택 ADR**(ADR-0001)을 2주 안에 확정한다. 후보는 제안했다.
5. **규칙 DSL v0.1**(§49)을 JSON Schema와 참조 평가기로 구현하고 §34.1 표를 첫 테스트로 넣는다.
6. **화면 상태 어휘**(§44.3)를 디자인·API·엔진이 공유하는 enum으로 고정한다.
7. **사이트 정보 구조**(§45)를 확정하고 커버리지 투명성 페이지를 관제 데이터와 같은 API로 묶는다.
8. 문서를 분할한다. 불변 원칙은 `docs/PRINCIPLES.md`로 독립시키고 PR 체크리스트에 연결한다.
9. DNA 절은 `docs/masterplan/` 하위 별도 파일로 분리하고 머리에 "설계 동결·구현 금지"를 명시한다.
10. 일정은 날짜가 아니라 게이트로 관리하되, 채용·예산을 위해 주 단위 가설(§54)을 둔다.

## 7. 결론

v0.3은 "무엇을, 왜, 어떤 품질로"에 대한 답이다. v0.4 제3부는 "무엇으로, 누가, 어떤 순서로"에 대한 답을 더한다. 두 문서를 합쳐야 개발 계획이 된다. 제3부의 기술 선택은 전부 제안 상태이며 ADR 승인으로 확정한다.

## 8. 평가 이후 결정 (2026-10-08)

이 평가서의 권고 일부는 사용자 결정으로 바뀌었다. 최신 내용은 제3부 §56을 따른다.

- 계약 가져오기: 4경로 권고(§6-3) 대신 PDF 업로드 단일 경로, 선택 사항(ADR-0005).
- 접근성: 평가서 G12의 기준 마련 권고는 채택하지 않는다. 목표에서 제외(제3부 §51.4).
- 범위: 첫 보험군 3개 보험사 권고 대신 전 보험사·전 상품(ADR-0004).
- 스택: 백엔드 Rust, 모바일 Flutter(ADR-0001).
- 출시: MVP·단계 출시 권고 대신 DNA를 제외한 전 기능의 단일 출시, 체험판 웹 없음(ADR-0007).
- 검수: 도메인 전문가 검수 권고 대신 AI 검수와 AI 분모 조사(ADR-0006). 이 결정으로 v0.3 §22·§31·§32의 사람 검수 전제가 대체되며, 공통 모드 오류가 새 핵심 위험이다.
- 범위 조정: 상담 연결·설계사 포털·실견적은 스켈레톤으로 빼고 담보 데이터·디지털 트윈·읽지 않는 UX에 집중(ADR-0008). 평가서 G1(실견적)·§5의 예산 슬라이더 보완안은 첫 앱에서는 적용하지 않고 시나리오 가정 슬라이더로 대체했다.

## 9. 원구상 복원과 견본 보완 (2026-10-09)

- 문서 밖 첨부 참조를 `docs/design/`의 원본·네 화면 견본·상태별 명세로 보완했다. 승인된 무드와 새 작업 초안을 구분한다.
- 가족력 선택 입력을 복원했다. 상담·실견적을 연기한 결정이 가족력까지 제외한다는 뜻은 아니다.
- 필요액·충족률·유지/추가/축소 상태의 근거 없는 판단을 제거하고 담보 조건·근거·입력 상태 중심으로 수정했다.
- 변경 문서의 정의·별표·각주·역참조까지 재처리한다. 세부 계약은 `docs/data/DATA_PIPELINE_CONTRACT.md`다.
- §4의 3/n 평가를 정정한다. AI 재추출 감사는 독립적인 참 정답 판정기가 아니므로 실제 약관 오류율 상한을 보증하지 못한다.
- 본 평가는 문서 검토다. 크롤러·앱 구현, 실제 소스 수집, 보험 정확도 시험을 수행한 결과가 아니다.
