# 온전 ONJEON 마스터플랜 v0.4
# 제3부. 앱·사이트 구현 계획

v0.4 추가 | 2026-10-08 | 제1부(1~21절)·제2부(22~41절)의 구현 계획

이 제3부는 v0.3의 요구사항을 "무엇으로, 누가, 어떤 순서로" 만들지로 바꾼다. 기술 선택은 전부 제안이며 `docs/decisions/`의 ADR 승인으로 확정한다. 아직 코드·크롤러·데이터베이스·배포는 없다. 규제·사업 구조 검토는 이 문서의 범위 밖이다.

제1·2부와 충돌하면 제2부 → 제3부 → 제1부 순서로 적용한다. 불변 원칙(§1)은 세 부 모두에 우선한다.

## 42. 제품군: 무엇을 만드는가

하나의 앱이 아니라 여섯 개의 표면이다. 모두 같은 검증 릴리스 API를 쓴다.

| 표면 | 사용자 | 형태 | 시점 | 비고 |
|---|---|---|---|---|
| 소비자 앱 | 소비자 | iOS·Android 네이티브 앱 | MVP | 홈·만약에·내 설계·내 정보 4탭 |
| 공개 웹 | 방문자·설계사·언론 | 정적 웹 + 일부 동적 페이지 | MVP | 소개, 작동 원리, 데이터 커버리지, 법적 고지, 지원 |
| 웹 체험판 | 비로그인 방문자 | 웹앱(앱과 코드 공유) | MVP 직후 | '예시로 둘러보기'만 웹에서 제공. 개인정보 입력 없음 |
| 관제 콘솔 | 내부 운영자 | 웹앱(인증 필수) | MVP 필수 | §14 7개 화면 |
| 검수 작업대 | 보험 도메인 검수자 | 웹앱(관제 콘솔 내부 모듈) | MVP 필수 | §31.1 3단 화면 |
| 설계사 포털 | 등록 설계사 | 웹앱 | 후속(단계 E) | 취급 범위 등록, 예약, 제안서 제출 |

소비자용 웹앱 전체판은 만들지 않는다. 계약·건강 정보를 다루는 흐름은 앱에 둔다. 웹 체험판은 전환 깔때기이며 저장 기능이 없다.

## 43. MVP 범위와 수직 슬라이스

### 43.1 두 트랙의 병렬화

v0.3 로드맵 A~H는 순차로 읽힌다. 실제로는 두 트랙을 병렬로 간다.

- **데이터 트랙**: §39 작업 1~5. 3개 보험사, 정액형 진단 담보, 실제 공시 수집.
- **제품 트랙**: 합성 픽스처로 앱·엔진·API·관제를 끝까지 동작시킨다.

제품 트랙은 데이터 트랙의 산출물을 기다리지 않는다. 합성 상품 3개(§34.1 수준의 테스트 약관을 확장)로 홈 → 만약에 → 내 설계 → 두 안 비교 → 증거 보기까지 연결한다. 데이터 트랙이 첫 검증 릴리스를 내면 픽스처를 실데이터로 교체한다. 교체 시 화면·엔진 코드는 바뀌지 않아야 한다. 이것이 ADR-0002다.

### 43.2 MVP 포함

- 소비자 앱: 예시로 둘러보기, 처음부터 준비하기(4문항), 내 보험 살펴보기(증권 촬영·업로드·사용자 확인), 홈, 만약에(상황 3종: 진단·입원수술·소득 중단), 내 설계(유지안·보완안 비교), 전후 비교, 계약 상세, 증거 보기, 내 정보(계약·가족·동의·권한).
- 엔진: 규칙 DSL v0.1, 3값 논리, 정액형 진단 담보 계산, 미확인 전파, 재현성 스냅샷.
- 데이터: 3개 보험사 정액형 진단 담보 검증 릴리스 1개 이상.
- 관제: 범위 지도, 소스 상태, 검토함, 배포함, 품질 화면(§14 중 5개).
- 공개 웹: 소개, 작동 원리, 커버리지 투명성, 고지, 지원.

### 43.3 MVP 제외

상담 연결, 설계사 포털, 콘텐츠·광고, 가족력·건강 위험, DNA 연계, 실견적 제휴 API, 소비자 웹앱 전체판, 푸시 마케팅.

DNA 연계(§12)는 설계 동결 상태다. MVP 기간에 구현하지 않으며, 데이터 모델에는 `genetic_private` 민감도 라벨과 저장 영역 분리만 미리 둔다.

## 44. 소비자 앱 정보 구조

### 44.1 탭과 화면

첨부 시안의 4탭을 기준으로 한다.

| 탭 | 화면 | 핵심 질문 | 주요 행동 |
|---|---|---|---|
| 홈 | 보장 지도 | 내가 가진 보장과 확인할 항목은? | 보장 살펴보기 |
| 홈 | 계약 상세 | 이 계약은 어떤 역할인가? | 조건 확인, 원문 보기 |
| 만약에 | 상황 선택 | 어떤 상황을 볼 것인가? | 상황 고르기 |
| 만약에 | 상황 결과 | 이 상황에서 받을 수 있는 것과 생활비 공백은? | 조건 바꾸기 |
| 내 설계 | 예산·안 비교 | 예산에 따라 무엇이 달라지는가? | 두 안 비교하기 |
| 내 설계 | 전후 비교 | 더 얻는 것·잃는 것·확인할 것은? | 선택 보관 |
| 내 정보 | 계약 / 가족 / 동의·권한 / 본인 전용 분석 | 내 데이터는 어디에 어떻게 쓰이는가? | 가져오기, 동의 관리, 삭제 |
| 공통 | 증거 보기 | 이 숫자는 어디서 왔는가? | 원문 페이지·조항·버전 |

### 44.2 공통 화면 상태

모든 데이터 화면은 다음 상태를 반드시 구현한다. 디자인 시안은 상태별로 한 장씩 있어야 한다.

| 상태 | 조건 | 화면 규칙 |
|---|---|---|
| 로딩 | 요청 중 | 골격 화면. 2초 초과 시 문구 안내 |
| 비어 있음 | 계약 없음·입력 없음 | 세 진입점(§3.1) 재노출 |
| 부분 | 일부 담보 미확인 | 아는 부분만 표시. 합계 금액 표시 금지(§36). "확인 필요 n건" 배지 |
| 판단 불가 | 핵심 입력 없음 | 추가 질문 1개 또는 범위 표시. 금액 크게 표시 금지(§10) |
| 오래됨 | 릴리스 기준일이 정책 기한 초과 | 최신성 경고 띠. 결과는 유지 |
| 오류 | 서버·네트워크 실패 | 마지막 성공 결과 + 실패 사실. 재시도 |
| 변경됨 | 새 릴리스로 결과가 바뀜 | 이전·이후 차이와 원인(원문 변경/처리기 변경) |

### 44.3 상태 어휘

첨부 시안의 '유지·추가 검토·조건 확인'을 포함해 다음 enum을 디자인·API·엔진이 공유한다. 소비자 화면 문구와 내부 코드를 함께 고정한다.

| 코드 | 화면 문구 | 엔진 조건 |
|---|---|---|
| `keep` | 유지 | 현재 보장이 선택 상황·예산에서 공백 없음 |
| `review_add` | 추가 검토 | 확인된 보장 공백이 있고 예산 내 대안 후보가 존재 |
| `review_reduce` | 축소 검토 | 중복·초과 보장이 확인되고 유지 비용이 큼 |
| `confirm_input` | 조건 확인 | 미확인 입력 때문에 판단 불가. 추가 질문 존재 |
| `unverified` | 미확인 | 원문·계약에서 조건을 찾지 못함. 0원 아님 |
| `hold` | 판단 보류 | 근거 충돌·검수 대기. 추천 생성 중단 |
| `not_applicable` | 해당 없음 | 상황·피보험자 조건상 적용 대상 아님 |

`unverified`와 `confirm_input`의 차이: 전자는 데이터 쪽 부재, 후자는 사용자 입력 부재다. 전자는 사용자가 해결할 수 없으므로 "증권에서 확인하지 못했어요"로, 후자는 질문으로 안내한다.

### 44.4 내 설계 화면 사양 (첨부 시안 기준)

1. 상단: 월 예산. 초기값은 **현재 월 보험료**다. 슬라이더 위에 현재 보험료 마커를 둔다. 범위 하한은 0원까지 열되, 현재보다 낮은 영역은 '줄이기' 영역으로 시각 구분한다. 상한은 가구 프로필에서 도출하고 "범위 기준" 설명을 둔다.
2. 입력 대안: 직접 입력(숫자 키패드)과 ±1만 원 스테퍼. 슬라이더만으로 조작하게 하지 않는다.
3. 금액 라벨: 각 안의 월 보험료에 `illustrative / quoted / estimated / unavailable`(§28 가격 근거) 라벨과 기준일을 붙인다. "실제 견적 아님" 고지는 금액 바로 아래 고정.
4. 안 선택: '현재 유지'와 '보완안'은 같은 크기. 보완안이 없으면 "지금 예산에서는 유지가 적절해요"를 결과로 보여준다. 억지 대안 생성 금지(§11).
5. 담보 목록: 상태 어휘(§44.3) + 한 줄 이유. 색과 텍스트를 함께 쓴다.
6. 확인 필요 배지: 안 선택 영역 아래에 "확인 필요 n건". 탭하면 `confirm_input`·`unverified` 항목만 모아 보여준다.
7. "무엇이 달라지나요?": 추가·제외 조건, 면책 재시작, 해지 손실을 비교 전에 노출한다.
8. 하단 고지: "데이터 기준 YYYY-MM-DD · 릴리스 r123 · 실제 견적 아님". 탭하면 증거 보기.
9. 주요 행동: "두 안 비교하기" 하나. 그 아래 본인 전용 잠금 안내.

## 45. 사이트 계획

### 45.1 공개 웹 정보 구조

| 경로 | 내용 | 데이터 |
|---|---|---|
| `/` | 한 문장 약속, 세 진입점 소개, 앱 설치, 체험판 | 정적 |
| `/how-it-works` | 세 층(선택·이유·증거), 원문 추적 예시(합성) | 정적 |
| `/principles` | 불변 원칙 10개 전문 | `docs/PRINCIPLES.md`에서 생성 |
| `/coverage` | 데이터 커버리지 투명성: 보험사·상품군·버전별 확보/누락/미확인, 최신성, 알려진 공백 | `GET /data-coverage` 실시간 |
| `/coverage/releases` | 릴리스 이력, 변경 요약, 정정 이력 | 릴리스 API |
| `/try` | 웹 체험판 | 합성 픽스처만 |
| `/agents` | 설계사 안내(후속) | 정적 |
| `/legal/*` | 이용약관, 개인정보처리방침, 광고 고지 | 정적, 버전 관리 |
| `/support` | 문의, 삭제 요청, 오류 신고 | 폼 → 지원 큐 |
| `/status` | 서비스 상태, 소스 장애 공개 | 상태 API |

`/coverage`는 브랜드 자산이다. 관제 콘솔의 범위 지도와 같은 API를 쓰되 공개용은 집계만 노출한다. 누락을 숨기지 않는다는 원칙(§23.4)을 외부에 보여주는 첫 화면이다.

### 45.2 관제 콘솔·검수 작업대

- 인증: 내부 SSO 또는 초대 기반 계정, 2단계 인증 필수, 역할(운영자/검수자/승인자/읽기)을 분리한다. 작성자와 승인자는 같은 계정일 수 없다(§22).
- 화면: §14의 7개. MVP는 범위 지도·소스 상태·검토함·배포함·품질 화면 5개.
- 검수 작업대: §31.1 3단 구성. 원문 PDF 페이지 렌더 + 강조 영역(bbox) + 추출 필드 + 충돌·테스트 결과. 결정(승인/수정/보류/참조요청)과 이유를 기록한다. 원문 전체 접근 없이 승인 불가.
- 감사 로그: 모든 결정·릴리스·롤백은 누가·언제·무엇을·왜. 개인 민감정보 원문은 로그에 남기지 않는다(§15).

### 45.3 설계사 포털(후속)

단계 E에서 설계한다. MVP에서는 데이터 모델에 `Agent`, `AgentScope`(취급 가능 보험사·상품군), `ConsultationRequest`만 예약해 둔다. DNA 파생 데이터는 포털 API 전체에서 차단한다(§12.6).

## 46. 계정·인증·가족·동의

### 46.1 계정 단계

| 단계 | 시점 | 저장 |
|---|---|---|
| 익명 | 예시로 둘러보기, 처음부터 준비하기 | 기기 로컬만. 서버 저장 없음 |
| 계정 | 저장·동기화·계약 업로드 시 제안 | 이메일 또는 소셜 로그인 + 기기 인증 |
| 본인확인 | 가족 프로필 연결, 상담 연결(후속) | 휴대폰 본인확인. 주민번호 저장 안 함 |

익명에서 계정으로 전환할 때 로컬 데이터를 가져올지 사용자가 선택한다. 전환 전 민감정보(건강)는 서버로 보내지 않는다.

### 46.2 가족 프로필

- 가족 구성원은 별도 `Profile`이다. 성인 가족의 문서·건강정보는 본인 계정에서만 추가한다(§3.2).
- 가족이 자신의 계정을 만들어 연결하는 "초대" 모델을 기본으로 한다. 초대 전에는 이름 없는 역할(배우자·자녀 1)과 출생 연도만 둔다.
- 아동 프로필은 보호자가 관리하며, 건강 정보 입력은 MVP에서 열지 않는다.

### 46.3 동의 모델

`Consent`(§9)를 목적별로 분리한다: 서비스 필수, 계약 문서 처리, 건강 정보 처리, 외부 AI 처리, 가족 연결, 상담 공유(후속), 본인 전용 분석(후속). 동의 화면은 한 화면에 한 목적. 철회는 설정에서 즉시 가능하고 철회 시 영향(어떤 기능이 꺼지는지)을 미리 보여준다.

### 46.4 삭제·내보내기

- 계정 삭제: 즉시 접근 차단, 유예 기간 후 영구 삭제. 유예 중 복구 가능.
- 데이터 내보내기: 사용자 계약·입력·결과를 기계 판독 형식(JSON)과 사람용(PDF)으로 제공.
- 개념 API에 추가: `POST /auth/*`, `GET/DELETE /me`, `GET /me/export`, `POST /consents`, `DELETE /consents/{id}`.

## 47. 핵심 외부 의존의 대안 설계

### 47.1 실견적: 3단계

| 단계 | 가격 근거 라벨 | 출처 | 화면 표시 |
|---|---|---|---|
| 1. 공시 예시 | `illustrative` | 상품요약서·공시 예시 보험료 | "예시 보험료(기준: 40세 남 표준체 등 조건 명시)" + 기준일 |
| 2. 사용자 제출 견적 | `quoted` | 사용자가 받은 설계안 업로드 | "제출한 견적(YYYY-MM-DD)" + 조건 대조 |
| 3. 제휴 견적 | `quoted` | 보험사·GA 견적 API(후속) | "실시간 견적" + 만료 시각 |

MVP는 1단계만으로 출시 가능해야 한다. 1단계에서는 보완안 월 보험료를 **범위**(예: 3.2만~4.1만 원)로 표시하고 범위 근거(조건 차이)를 두 번째 층에 둔다. 범위를 만들 수 없으면 `unavailable`로 표시하고 금액을 비운다.

### 47.2 계약 가져오기: 4경로

| 경로 | 정확도 | 사용자 부담 | MVP |
|---|---|---|---|
| A. 증권·설계안 촬영/업로드 + OCR + 사용자 확인 | 중 | 중 | 포함 |
| B. 보험사 앱·웹에서 받은 가입내역 PDF 업로드 | 중상 | 낮음 | 포함 |
| C. 통합 조회 서비스 결과 가져오기(사용자가 조회 화면을 캡처·내보내기) | 중상 | 낮음 | 조사 후 결정 |
| D. 마이데이터 연계 | 상 | 매우 낮음 | 후속. 사업 결정 항목 |

A·B는 같은 추출 파이프라인을 쓴다. 추출 결과는 사용자 확인 전까지 `extraction_status=unconfirmed`이며 계산에 쓰지 않는다. 확인 화면은 "AI가 읽은 내용"과 "원본 영역"을 나란히 보여주고 한 항목씩 확인한다.

### 47.3 AI 제공자

- AI 게이트웨이(§13)를 자체 모듈로 둔다. 제공자 SDK를 앱·엔진 코드에서 직접 호출하지 않는다.
- 호출마다 `provider, model_version, prompt_version, schema_version, cost, latency`를 기록한다.
- 구조화 출력은 JSON Schema로 검증하고 실패 시 재시도 한도 후 `unresolved`로 떨어뜨린다. 모델이 금액·날짜를 생성하면 코드가 원문 인용 일치를 검사한다(§29).
- 월 호출 비용 상한과 사용자당 일일 상한을 둔다. 상한 초과 시 기능 저하(캐시 결과·판단 보류)로 전환하고 숨기지 않는다.
- 평가 하네스: 정답셋(§32)을 모델·프롬프트 변경마다 자동 실행. C0 오류 1건이라도 늘면 배포 차단.
- 'AI에게 질문하기'(§12.4)는 검색 색인을 근거 탐색에 쓰되, 금액·지급 여부는 규칙 엔진 결과(§49.6)만 인용한다. 검색 결과 문장에서 금액을 만들지 않는다.
- 사용자 데이터로 모델 학습 금지, 보존 기간 최소화를 제공자 설정으로 강제하고 그 설정을 문서화한다.

## 48. 기술 아키텍처와 스택 후보

세부는 ADR-0001. 여기서는 선택 기준과 후보만 적는다.

### 48.1 선택 기준

1. 백엔드와 규칙 엔진은 Rust로 한다(사용자 결정, 2026-10-08). 문서 복원·OCR처럼 Python 생태계가 필요한 부분만 격리된 Python 워커로 두고 큐로만 연결한다.
2. 모바일은 두 플랫폼을 한 코드로 만들되, 카메라·파일·보안 저장소 네이티브 접근이 쉬워야 한다.
3. 공개 웹·체험판·관제 콘솔은 같은 웹 프레임워크로 묶는다.
4. 규칙 엔진은 **한 구현만** 존재한다(ADR-0003). 클라이언트 포팅 금지. 결과는 서버가 계산하고 앱은 표시한다.
5. 특정 클라우드 종속을 피한다. 로컬 개발 환경을 Docker Compose로 전부 띄울 수 있어야 한다.

### 48.2 후보 스택

| 계층 | 1순위 후보 | 대안 | 비고 |

## 49. 규칙 DSL v0.1 형식 명세

§34를 구현 가능한 수준으로 고정한다. 전체 JSON Schema는 `packages/schemas/rule-0.1.schema.json`으로 작성한다(후속 작업).

### 49.1 타입

| 타입 | 표현 | 비고 |
|---|---|---|
| `bool3` | `true / false / unknown` | 3값 논리 |
| `money` | `{currency:"KRW", minor:int}` | 정수 원. 부동소수점 금지 |
| `rate` | `{num:int, den:int, printed:"50%"}` | 유리수 + 원문 표기 |
| `int`, `decimal(문자열)` | | |
| `date` | `YYYY-MM-DD` + 달력 | 시간대는 규칙 메타의 `calendar` |
| `duration` | `{value:int, unit:"day"\|"calendar_month"\|"calendar_year"}` | 1년≠365일 |
| `enum`, `set`, `code_ref` | KCD 등 `{scheme, edition, code}` | |

모든 변수는 `source: contract | event | product | derived` 중 하나를 가진다. 서로 다른 source의 변수를 같은 이름으로 쓸 수 없다.

### 49.2 연산자

논리: `all, any, not`. 비교: `eq, ne, lt, lte, gt, gte, in_set, between(포함 여부 명시)`. 날짜: `date_add(date, duration), days_between(a, b, inclusive_start, inclusive_end), date_compare`. 금액: `multiply_rate(money, rate, rounding), add, min, max, apply_cap(money, cap), apply_floor`. 제어: `if/then/else`, `first_match(cases)`. 조회: `input(name)`, `const`.

허용 목록 밖의 연산자는 스키마 검증에서 거부한다. 사용자 정의 함수·코드 실행 없음.

### 49.3 3값 논리

| a | b | all(a,b) | any(a,b) | not(a) |
|---|---|---|---|---|
| T | T | T | T | F |
| T | F | F | T | F |
| T | U | U | T | F |
| F | F | F | F | T |
| F | U | F | U | T |
| U | U | U | U | U |

비교 연산자는 피연산자 하나라도 `unknown`이면 `unknown`을 돌려준다. 금액 연산은 피연산자가 `unknown`이면 결과를 `unknown`으로 두고 `missing_inputs`에 이름을 추가한다.

### 49.4 시간 의미론

- 규칙 메타에 `calendar: "Asia/Seoul"`, `day_boundary: "00:00"`을 명시한다. 날짜만 다루며 시각은 입력에서 날짜로 정규화한 뒤 쓴다.
- 기산점·포함 여부는 변수가 아니라 규칙에 적는다: `{"days_between": ["coverage_start", "event_date", {"inclusive_start": true, "inclusive_end": false}]}`.
- 보험연도·역년·계약기념일은 `period_basis` enum으로 구분하고 원문 근거를 붙인다.

### 49.5 금액과 반올림

`multiply_rate`는 `rounding: "floor" | "ceil" | "half_up" | "half_even"`과 `unit: 1 | 10 | 1000`을 필수로 받는다. 원문에 반올림 규칙이 없으면 `rounding: "unspecified"`로 두고 결과를 범위(floor~ceil)로 돌려준다. 임의 기본값 금지.

### 49.6 평가기 출력

```text
EvaluationResult
  rule_id / rule_version / engine_version / release_id
  eligibility: bool3
  amount: money | {min: money, max: money} | unknown
  missing_inputs[]        # confirm_input 으로 이어짐
  unresolved_refs[]       # unverified 로 이어짐
  trace[]                 # 평가한 노드, 입력값, 중간 결과, evidence_ref
  input_snapshot_hash
```

같은 입력 스냅샷·규칙 버전·엔진 버전이면 바이트 단위로 같은 결과를 낸다. 이를 CI에서 검사한다.

### 49.7 테스트

- §34.1 경계표를 첫 골든 테스트로 넣는다.
- 속성 기반 테스트: 임의 날짜 ±1일, 금액 단위 변경, 입력 하나를 unknown으로 바꾸면 결과가 unknown 또는 범위로 바뀌는지.
- 변이 테스트(§34.2): 부정어 삭제, 경계 포함 반전, 단위 변경을 규칙에 주입해 골든 테스트가 실패하는지.
- 순차 시나리오: 청구 이력·한도 소진·계약 변경을 순서대로 적용.

## 50. 데이터 모델의 구현 메모

§9의 엔터티를 PostgreSQL로 옮길 때 지킬 것.

- 모든 권위 테이블에 `valid_from, valid_to, recorded_at, superseded_at`. 갱신은 삽입이다. 물리 삭제는 사용자 삭제 요청 처리 외에 없다.
- `FieldAssertion`(§29)은 별도 테이블. 값은 `typed_value JSONB` + `value_state` enum(§28.3). `value_state`가 `observed`가 아니면 `typed_value`는 null 허용, 그 외에는 null 금지(제약으로 강제).
- 민감도 라벨(§28)은 행 단위 컬럼이자 스키마(별도 데이터베이스 스키마 또는 별도 DB)다. `private_health`·`genetic_private`는 공시 데이터와 같은 스키마에 두지 않는다.
- 릴리스는 불변 매니페스트(§37)이며 서비스는 항상 특정 `release_id`를 가리킨다. 롤백은 포인터 변경이다.
- 사용자 결과(`Simulation`, `Recommendation`)는 `release_id, engine_version, input_snapshot_hash`를 저장해 재현한다(§10).

## 51. 품질·테스트·CI/CD·릴리스

### 51.1 테스트 피라미드

| 계층 | 대상 | 도구 후보 | 게이트 |
|---|---|---|---|
| 단위 | 규칙 엔진, 타입·단위 파서, 상태 전이 | cargo test, proptest(Python 워커는 pytest) | 커버리지 수치보다 골든·변이 테스트 통과 |
| 계약 | API ↔ 앱·웹 | OpenAPI 스키마 검증, 생성 클라이언트 | 스키마 변경 시 양쪽 빌드 실패 |
| 통합 | 수집→복원→추출→검증→릴리스 | 표본 원문 + 합성 원문 | 작업 1~5 완료 기준 |
| 화면 | 상태별 화면(§44.2) | 스토리북형 상태 카탈로그, 스냅샷 | 상태 하나당 시안·구현 1:1 |
| E2E | 세 진입점 → 비교 → 증거 보기 | Detox/Maestro(앱), Playwright(웹) | 출시 핵심 시나리오 |
| 데이터 회귀 | 후보 릴리스 vs 현재 릴리스 | 그림자 비교(§37) | 원인 설명 없는 금액 변경 0건 |
| 접근성 | 앱·웹 | 자동 검사 + 스크린리더 수동 | §51.4 |

### 51.2 CI

PR마다: 린트·타입 검사, 단위·계약 테스트, 스키마 호환성 검사, 규칙 엔진 재현성 검사, 민감도 라벨 누출 정적 검사(§52.3), 불변 원칙 체크리스트(PR 템플릿). 기본 브랜치 보호: 리뷰 1인 이상, 규칙·라벨 사전 변경은 도메인 검수자 승인 필수.

### 51.3 릴리스

- 앱: 내부 테스트 → 비공개 베타 → 단계적 공개(1%→10%→100%). 서버 기능 플래그로 화면 기능을 끄고 켠다. 기능 플래그는 §36의 공개 기능 상태(`explanation_enabled` 등)와 1:1로 연결한다. 데이터가 허용하지 않는 기능은 플래그로도 켤 수 없다.
- 서버: 데이터 릴리스와 코드 릴리스를 분리한다. 코드 배포는 현재 데이터 릴리스를 바꾸지 않는다.
- 데이터: §36·§37 승격 절차. 배포함에서 승인 2인(작성자≠승인자).
- 롤백: 코드·데이터 각각 독립. 롤백 후에도 사용자에게 보여준 기록은 보존(§10).

### 51.4 접근성

- 기준: 한국형 웹 콘텐츠 접근성 지침(KWCAG) 최신판 + 모바일 앱 접근성 지침. 목표 수준은 ADR로 정한다.
- 필수 검사: 대비 4.5:1(본문), 터치 44×44, 스크린리더 읽기 순서, 동적 글자 크기 200%, 동작 줄이기, 색 외 수단.
- 슬라이더·차트는 반드시 대체 입력·대체 텍스트를 갖는다.
- 출시 전 스크린리더 사용자 2명 이상 사용성 시험.

### 51.5 사용성 시험

§17의 "5초·30초" 기준을 각 마일스톤 종료 조건으로 쓴다. 가상 계약으로만 시험하며 참가자 개인 계약을 받지 않는다. 잘못 이해한 비율을 핵심 지표로 기록한다.

## 52. 관측·계측·개인정보 경계

### 52.1 제품 분석

- 이벤트는 허용 목록(allowlist)만 전송한다. 목록은 `packages/schemas/analytics-events.yaml`에 두고 PR 리뷰 대상이다.
- 전송 금지 필드: 계약 금액, 담보 명, 건강·가족력·DNA 관련 모든 값, 자유 입력 텍스트, 문서 내용. 전송 가능: 화면 ID, 상태 코드(§44.3), 소요 시간, 오류 종류.
- 세션 녹화·히트맵 SDK는 쓰지 않는다.
- 분석 수집은 자체 호스팅을 기본으로 하고, 외부 SDK를 쓰면 전송 전 필드 검증 계층을 둔다.

### 52.2 크래시·로그

- 크래시 보고에 화면 상태 덤프를 넣지 않는다. 브레드크럼은 화면 ID와 상태 코드만.
- 서버 로그는 구조화하고 `private_health`·`genetic_private` 데이터는 로그 직렬화기에서 자동 마스킹한다.
- AI 게이트웨이 로그는 프롬프트 템플릿 ID·스키마·비용만 저장한다. 사용자 문서 본문은 저장하지 않는다.

### 52.3 누출 정적 검사

CI에서 다음을 검사한다: 분석 이벤트 스키마 밖 필드 전송 코드, 민감도 라벨 테이블을 공개 API 직렬화기에서 참조하는 코드, 설계사·상담 모듈이 `genetic_private` 스키마를 import하는 코드. 발견 시 빌드 실패.

### 52.4 운영 지표

§19 외에 추가: 앱 크래시율, 화면별 판단 불가 비율, "확인 필요" 해소율, 증거 보기 진입률, 체험판→앱 전환율, AI 호출 비용/사용자, 검수 적체 일수.

전송 구간 TLS, 저장 암호화, 비밀은 비밀 관리자, 의존성 취약점 자동 검사, 서명된 빌드, 역할 기반 접근 제어, 관리자 2단계 인증, 백업 암호화와 복구 연습.

### 53.3 사고·지원 흐름

- 사용자 문의 채널(앱 내·웹 `/support`)과 지원 큐. 삭제 요청은 접수 즉시 접근 차단, 처리 결과 통지.

- 침해 사고 대응 런북: 탐지, 격리, 영향 평가, 통지, 사후 검토.

## 54. 일정·마일스톤·게이트

기간은 인력 확보 전의 가설이다. 날짜가 아니라 게이트 통과로 진행하되, 채용·예산 계획을 위해 주 단위를 둔다. 핵심 인원 5~6명(§18 역할) 기준이다.

### 54.1 단계

| 단계 | 기간(가설) | 산출물 | 게이트 |
|---|---|---|---|
| P0 기반 | 1~4주 | 저장소·CI·환경, 스키마 v0, 상태 enum, 규칙 DSL v0.1 + 평가기 + §34.1 골든 테스트, 합성 픽스처 상품 3개, 디자인 토큰·상태별 시안, ADR-0001~0003 승인 | 평가기 재현성 CI 통과. 시안 상태 카탈로그 완료 |
| P1 수직 슬라이스 | 5~12주 | 소비자 앱 4탭(합성 데이터), API, 관제 5화면 최소판, 공개 웹 초판, 체험판 | 8~12명 사용성 시험: 5초·30초 기준. 불변 원칙 체크리스트 통과 |
| P2 데이터 트랙 (P1과 병렬) | 3~16주 | §39 작업 1~5: 3개 보험사 정액형 진단 담보, 어댑터, 복원 벤치마크, 라벨 사전, 정답셋, 추출·검증 | 작업별 완료 기준(§39). C0 미해결 0건 |

### 54.2 P0 상세 백로그

1. 저장소 구조(§48.3), Compose 로컬 환경, CI 골격.
2. `packages/schemas`: 상태 enum, 빈 값 상태, 가격 근거, 민감도 라벨, 규칙 스키마 v0.1.
3. `packages/rules-engine`: 타입, 3값 논리, 연산자, 평가기, trace, §34.1 골든 테스트, 변이 테스트.
4. `packages/fixtures`: 합성 보험사 2곳·상품 3개·담보 10개·계약 5건·시나리오 30개·정답표.
5. 디자인: 토큰(§40), 4탭 핵심 화면 × 상태 7종 시안, 증거 보기 화면.
6. API 초안(OpenAPI): §13 + §46.4 엔드포인트. 인증 설계.
7. 관제 콘솔 정보 구조와 검수 작업대 와이어프레임.
8. 공개 웹 정보 구조·카피 초안.
9. ADR-0001(스택), 0002(픽스처 우선), 0003(엔진 단일 구현) 승인.
10. `docs/PRINCIPLES.md` 분리와 PR 템플릿 체크리스트.

### 54.3 인력·검수 처리량 가정

- 역할: 데이터 수집·운영 1, 보험 도메인 검수 1~2, 백엔드·엔진 1~2, 모바일 1, 웹·관제 1, 디자인 1(겸임 가능).
- 검수 처리량 가설: C0 담보 발생본 1건당 검수 30~60분(원문 대조 포함). 300개 발생본·2인 독립 라벨링+조정이면 약 450~900시간. P2 기간에 검수 1.5 FTE가 필요하다. 실측 후 조정한다.
- 비용 산식(§18)의 변수 중 "변경 문서 수"와 "검수 시간"은 P2 종료 시 실측값으로 바꾼다.

## 56. 결정 기록 v0.4와 열린 질문

### 확정(이 문서 범위)

- 여섯 표면(§42). 소비자 웹앱 전체판 없음.
- 두 트랙 병렬, 합성 픽스처 우선(ADR-0002).
- 규칙 엔진 단일 구현, 서버 계산(ADR-0003).
- 상태 어휘 7종(§44.3). 금액 라벨은 §28 가격 근거 4종.
- 내 설계 초기값은 현재 월 보험료. 축소 영역 허용.
- 분석 이벤트 허용 목록 방식.

### 사용자 결정 완료

- 백엔드 언어: Rust (2026-10-08). 문서 복원·OCR만 격리된 Python 워커.
- 모바일 프레임워크: 최신 것으로 위임. React Native(Expo, New Architecture) 채택 제안. 이의가 없으면 확정(ADR-0001).

### 사용자 결정 필요

1. 계약 가져오기 경로 C·D 추진 여부와 시점. MVP는 A·B(§47.2).
2. 실견적 2단계(사용자 제출 견적)를 MVP에 넣을지. 권고는 MVP 이후 첫 확장(§47.1).
3. 접근성 목표 수준. 권고는 KWCAG AA 수준 + 큰 글씨 200%(§51.4).
4. 첫 보험군 확정. 권고는 정액형 진단 담보 유지(§43)와 3개 보험사 후보 조사.
5. 공개 웹 도메인·가칭 명칭(개발을 막지는 않음).
