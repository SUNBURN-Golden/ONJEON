# Audit 4 — 원장 100건 경계 시험과 추가 2건 설명

대상: `audit4-ledger-cap-test`, `tools/r2_budget.py::Ledger.read/append`, `Session.settle`.
연결: Blueprint A1·Q7·L1~L2·I1·M1, ADR-0017, 09 제품 목적 대응표 P02·P03.

## 확인 결과

발견 당시에는 `read`가 정확히 100건을 허용하고 정산 쓰기 검사가 없어 예약·정산이 101·102건으로 늘어날 수 있었다. 현재 작업 트리에는 Audit 2의 `>=` 읽기 거부와 공통 `append` 쓰기 검사, Audit 3의 체크포인트 선저장이 이미 반영되어 있다. 따라서 실행 로직·정책·해시는 바꾸지 않고 실제 HTTP 요청 경계의 회귀 시험과 설명을 보강했다.

상한은 가장 새 체크포인트 **뒤**의 `ledger/v1/` 기록 수다. 체크포인트가 없으면 전체 기록 수다.

| 시작 기록 수 | 일반 실행 결과 |
|---|---|
| 98 | 예약 99·정산 100, 총 100건 |
| 99 | 예약 100, 정산은 `settlement_failed: BudgetError`, 총 100건. 미정산 입장·예약 전액을 계속 계상하고 잠금을 해제한다 |
| 100 | 추가 원장 GET·예약 PUT 전에 거부, 총 100건. 선행 입장은 남아 비용에 계상된다 |

성공한 **체크포인트 복구**의 추가 2건은 위의 과거 결함과 구분한다. 기존 100건을 요약하는 체크포인트 PUT·확인 GET이 성공한 뒤 예약 101·정산 102를 쓴다. 보존 이력은 102건이고 새 체크포인트 뒤 기록은 2건이다. 원본 이력은 삭제·변경하지 않는다. 체크포인트 객체·입장 기록은 원장 기록 수에 포함하지 않으며 요청·바이트는 계량한다. 100건 상한을 102로 올리거나 뒤따르는 100건에 2건의 예외를 주지 않는다.

## 시험·완료 증거

[`test_r2_checkpoint.py`](../../../tools/tests/test_r2_checkpoint.py)의 루프백 S3 스텁 시험:

- `EndToEnd.test_ordinary_sessions_enforce_ledger_cap_before_http_writes`: 98·99·100건에 대해 실제 botocore 요청 로그의 원장 PUT 키를 정확히 대조한다. 100건에서 원장 GET 없음, 모든 경우 총 100건·기존 바이트 보존·입장 1건 유지·잠금 해제, 99건에서 모든 비용 축의 미정산 입장·예약 전액 계상을 검증한다.
- `EndToEnd.test_checkpoint_session_at_the_cap_stays_metered_and_clears_it`: 기존 복구 시험을 보강해 체크포인트 PUT → 확인 GET → 예약 PUT 순서, 정산의 예약 참조, 보존 이력 102건·새 기준점 뒤 2건·기존 100건 바이트 보존을 검증한다. 다음 일반 실행이 복구 2건과 자신의 예약 꼬리만 읽는지도 확인한다.
- 기존 `test_r2_budget.LedgerRecordCap`과 `test_r2_checkpoint.Reads/Lockout`은 직접 쓰기·체크포인트 상대 경계·경합 재검사·복구 실패 시 뒤받침 보존을 계속 검증한다.

실행 명령·결과·과거 결함 변이 검출은 [작업 증거](../../../tools/evidence/audit4-ledger-cap-test/README.md)에 기록한다. 임시 로컬 원장과 루프백 HTTP만 사용하며 실제 R2·자격 증명·과금·운영 설정을 사용하거나 변경하지 않는다.

이 증거는 보관 도구의 경계 회귀에 한정한다. 실제 공시 확보율·R2 관측 대조·소비자 화면·첫 출시 완료 증거를 대신하지 않으며 P02·P03을 완료 처리하지 않는다.
