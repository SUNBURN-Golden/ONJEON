### 1.2 주장(Assertion) 저장 형식 (C-20, C-05 통합) — [설계 담당 결정(감리 대상)]

**FieldAssertion과 관계 주장을 한 테이블 `assertion`으로 통합한다.** 속성 값 주장은 `predicate`가 속성 이름이고 `value`를 갖는다. 관계 주장은 `predicate`가 T-box 관계 ID이고 `object`를 갖는다. 근거·범위·시점·상태·정정 필드는 공통이다. 이유: K1~K15 검사가 한 집합을 본다. 릴리스가 주장 ID 집합 하나로 정의된다. 정본 FieldAssertion의 필드(raw·정규화 값, 단위, value_state, 근거, 적용 범위, 추출·검증 이력)는 모두 열로 남는다.

```text
assertion(
  id, subject, predicate, object | value{raw, normalized, unit, value_kind, amount_form},
  scope{document, sales_config, contract_kind[], component_conditions[], insured_conditions[]},
  time{valid_from, valid_to, recorded_at, observed_at, judged_as_of},
  evidence[{ref, role ∈ evidence_role}],       -- 1개 이상. basis는 약관 ClauseOccurrence만 허용
  criticality ∈ {c0,c1,c2}, value_state, review_status, hold_reason?,
  review_decision_id?,                          -- accepted이면 필수(§8)
  supersedes?, correction_reason?,
  extractor{tool, version, prompt_version?}, origin ∈ assertion_origin{pipeline, fixture},
  onto_version, created_by_run
)
```

구조 주장(onto-0.2): `segment_of`(구획 → 원본), `realizes`(구획 → 본문 판, n..1), `edition_of`(본문 판 → 계열), `in_edition`(담보 → 본문 판), `in_segment`(조항 → 구획), `uses_edition`(판매 구성 → 본문 판, 적용 기간 다대다), `disclosure_of`. 구조 주장은 **관측 근거**(공시 행·구획 관측)로 세우고, 내용 주장(C0)은 **약관 구획의 조항 basis**로 세운다(K1). 원본 해시 일치는 판 동일성의 근거가 아니다(K14).

DB 제약(스키마로 강제, I7·I12·K1·K8·K14·§8). **모두 설계(구현 예정, T-CT-05·T-KN-04).**

| 제약 | 내용 |
|---|---|
| `chk_accepted_needs_decision` | `review_status='accepted' ⇒ review_decision_id IS NOT NULL` |
| `chk_fixture_never_accepted` | `origin='fixture' ⇒ review_status <> 'accepted'` (픽스처는 pending·hold·rejected만) |
| `chk_c0_basis` | 내용 주장: `criticality='c0' AND review_status='accepted' ⇒ evidence에 role=basis인 ClauseOccurrence가 있고, 그 조항의 구획 doc_role ∈ {보통약관, 특약 약관, 별표} 이고, 그 구획에 accepted `realizes`가 있다`(K1). 구조 주장(`uses_edition`·`realizes`·`disclosure_of`)은 role=observation 근거 필수 |
| `chk_realizes_fingerprint` | `realizes`가 accepted이려면 구획에 `fingerprint{rule, sha256}`이 있고 그 구획이 observation 근거여야 한다(K14). 근거가 원본(`raw:`)뿐이면 거부 |
| `chk_no_private_ids` | 공개 스키마의 모든 텍스트 열에 `contract:|person:|upload:|del:|consent:|assume:` 접두어 금지(트리거) + 참조 열은 타입 있는 FK |

| `fk_segment_raw`, `fk_clause_segment` | 구획 → 원본, 조항 → 구획 FK |
| `fk_evidence_clause` | `evidence.ref`가 `clause:` 또는 `premium:`이면 해당 행이 존재하고, 그 조항의 구획이 가리키는 RawAsset.sha256이 **R2 관측 목록**(archive listing, Git 고정)에 있어야 함 — 릴리스 빌더 검사(DB FK가 아님) |

### 1.3 릴리스(C-10) — 구성원 목록 + 규칙 파일 해시 + 내용 해시로 고정(K15, F01)

```text
release_manifest(
  release_id, created_at, frozen_at,
  members{                         -- 구역별 구성원 ID 목록(정렬). 릴리스가 읽는 것은 이 목록뿐이다
    raw_assets[], segments[], terms_editions[], terms_lineages[], clauses[], nodes[],
    assertions[], conflicts[], gaps[], premium_observations[], criteria_release_ref },
  rule_files{ <rule_path>: sha256 }, -- 규칙 파일 바이트 해시
  content_sha256,                  -- members 가 가리키는 행 내용 + rule_files 를 정규화(JSON, 키 정렬)한 SHA-256
  onto_version, vocabulary_version, label_dictionary_version, schema_version(contracts semver),
  extractor_versions[], model_versions[]{provider_family_label, model_ref_hash, prompt_version},
  engine_version, rule_schema_versions[],
  capability_table_hash,           -- 담보별 capability 판정 결과(K11)의 해시
  explain_template_hash,
  shadow_compare_report_id,        -- 이전 릴리스와 같은 입력 비교 결과(원인 없는 차이 0건)
  constraint_report_id,            -- K1~K15 위반 0건 보고
  superseded_by?, withdrawn_at?, withdrawal_reason?
)
```

- `view(release)`는 **구성원 목록에 있는 행만** 돌려준다. 릴리스 뒤에 추가된 주장(정정 포함)은 과거 릴리스에 들어가지 않는다. 과거 결과는 과거 릴리스로 재현된다(온톨로지 검증 I1).
- 무결성(K15): 구성원이 저장소에 없거나(I3), 제자리에서 바뀌었거나(I2, 내용 해시 불일치), 규칙 파일이 바뀌면(I4) 위반이다. 주장 행은 불변이므로 제자리 변경은 저장소 오류이며 즉시 차단한다.
- 확보 작업(AcquisitionTask)은 운영 상태라 **릴리스 밖**이다. 공백(KnowledgeGap)은 릴리스 안이다.
- 판단 기준 릴리스(`criteria_release_ref`)는 별도 ID로 고정하고 지식 릴리스가 참조만 한다.
- 고정 범위는 주장·규칙만이 아니다. 참조 노드(범주·코드 집합·조건·판매 구성), 구획·본문 판·계열, 조항, 공백, 가격 관측, 판단 기준 릴리스 참조가 모두 구성원이다. 코드 집합이나 적용 관계(`uses_edition`·`realizes`)가 나중에 바뀌어도 과거 릴리스의 구성원과 내용 해시는 그대로이므로 과거 결과와 근거 사슬이 재현된다.
- **재현과 사용 제한은 다른 장치다.** (a) `view(release)`는 철회·오류 확인과 무관하게 항상 같은 내용을 돌려준다(과거 결과 재현, I18). (b) 오류가 확인된 릴리스는 `withdrawn_at`·`withdrawal_reason`과 영향 범위(의존 기록 §1.6)로 **사용을 제한**한다: 새 계산은 그 릴리스로 하지 않고, 저장된 결과는 `result_state.usage_restriction ∈ {hold, circuit_breaker}`·`knowledge_freshness=withdrawn`으로 표시하되 `reproducible=true`를 유지한다. 화면은 "이 결과는 r-xxx로 계산되었고 그 판은 정정되었다. 다시 계산하려면…"으로 보인다(§2.5). 철회는 manifest를 지우지 않는다.
- 불변(I16). 캐시 키·개인 초안·평가 결과는 모두 `release_id`를 포함한다. 철회는 `withdrawn_at` 기록 + 이전 manifest 재지정이다.
- 이전 판(ffbcaf6)은 `assertion_ids_hash` 하나로 고정했고 사례 검증기는 제외 목록 방식이었다. 둘 다 나중 주장이 섞일 수 있어 폐기한다.
- 구현 상태: 설계. 사례 검증기(ontology_check.py I1~I4)가 같은 규칙을 토의 자료 수준에서 동작 검증했다. 서비스 릴리스 빌더는 T-KN-07(시험 ID release-frozen-members).

### 1.3a 약관 본문 판의 동일성 판단 (K14 보강)

- 본문 지문(`fingerprint`)은 **근거 중 하나**다. 지문 일치가 판 동일성을 자동으로 승인하지 않는다. 원본 해시 일치도 마찬가지다.
- `realizes`(구획 → 본문 판)와 `same_edition` 판단의 `accepted`는 **ReviewDecision으로만** 생긴다(§1.2 `chk_accepted_needs_decision`이 구조 주장에도 적용된다). 코드 검사는 지문·제목·개정 표기·참조 별표 집합의 일치 여부를 검수 입력으로 넘길 뿐이다.
- 본문이 같아도 **참조 별표·정의 조항·적용 범위(피보험자 조건·판매 구성 조건)가 다르면 다른 판**이다. 따라서 realizes 후보를 만들 때 구획의 본문 지문과 함께 그 구획이 참조하는 별표 구획 집합·정의 조항 집합의 지문을 `edition_signature{body_fp, annex_fps[], definition_fps[], scope_fp}`로 묶고, 어느 하나라도 다르면 같은 판 후보로 올리지 않는다.
- 시험: 온톨로지 자체 시험 D1(다른 원본·같은 판), D2(원본 해시만으로 판 확정 → K14), 구현자가 보강 중인 D3(본문 같고 별표 다름 → 다른 판)·D4(지문 일치만으로 accepted → 거부). 서비스 측은 T-KN-01 골든과 T-KN-04 적재 거부 시험에 같은 사례를 둔다.

| 정보 출처 | 새 축 `fact_source` | `pdf_extracted`, `user_stated`, `user_confirmed_extract`, `assumed`, `release_derived` |
| 확인 여부 | 기존 `policy_holdings_status`(계약 단위) + 필드 단위는 `value_state`·`display_status` 재사용 | 기존 값 |
| 실제·가정 | 새 축 `fact_kind` | `actual`, `hypothetical` |
| 확인 주체 | 새 축 `confirm_party` | `user`, `insurer`, `document`, `none` |
| 기준 시점 | 필드 `as_of`(날짜) + 기존 `freshness` | — |

결과 상태 네 축(토의 9차: 입력 최신성·지식 최신성·오류에 따른 사용 제한·재현 가능)은 `result_state{input_freshness ∈ freshness, knowledge_freshness ∈ {fresh, stale, withdrawn}, usage_restriction ∈ {none, hold, circuit_breaker}, reproducible: bool}`로 뷰모델 공통 필드가 된다. `knowledge_freshness.withdrawn`과 `usage_restriction` 값은 새 어휘 축이다.

  applied_editions[{ted_id, basis_evidence, from, to}],    -- 근거로 확인한 약관 본문 판 이력만. 최신 판 자동 적용 금지
  components[{cov_ref, insured_amount_krw, fact_source, confirm_party, as_of}],

### 1.5 판단 기준 관리와 필요성 판단 결과(C-27, F08) — [설계 담당 결정(감리 대상)]

"스스로 판단할 근거를 제공한다"는 약관 지식(무엇을 지급하나)과 **다른 종류의 판단**(무엇을 우선 살펴볼 만한가)을 필요로 한다(소비자_기능_필요정보 §4·§6, 전체_구조_1차_정리 영역 C). 둘을 같은 사실처럼 보이지 않게 하려고 저장·판·근거·표시를 나눈다. 기본 필요액을 자동으로 만들지 않는 것(O05)은 그대로다. 그것과 판단 기능을 설계하는 것은 별개다.

**[사용자 결정 2026-10-12]** 판단 기준 관리를 명시적인 책임 영역으로 설계한다(별도 서비스 배포가 아니라 모듈·책임 영역). 이 영역이 관리하는 것: 기준의 출처, 적용 범위, 가정, 버전, 정정 이력, 결과가 어떤 기준에 의존하는지. 별도 검토 대상으로 남기는 것: 어떤 기준을 실제 사용자에게 적용할지, 기본 필요액을 제공할지와 그 산출 근거. 설계 승인이 특정 판단 기준의 서비스 적용 승인은 아니다.

```text
criterion(id, kind ∈ {priority_rule, reference_stat, applicability_rule, question_rule}, label, scope{situations[], subjects[]})
criterion_version(id, criterion_id, version, valid_from, valid_to?,
  sources[{ref: raw:|clause:|url_observation, evidence_kind ∈ criterion_source_kind{public_statistic, statute, regulator_notice, terms_fact, editorial}}],
  rationale, recorded_at, supersedes?, correction_reason?, origin ∈ {pipeline, fixture})
criteria_release(id, members{criterion_versions[]}, content_sha256, frozen_at)    -- 불변. 지식 릴리스와 별도
criteria_application(id, criteria_release_id, applied_criterion_versions[], defaults_enabled, defaults_basis_ref?,
  approval_ref{decision_id(D-08 계열), approved_by, recorded_at})                  -- 서비스 적용 승인 관문. 없으면 기준 평가 이유를 싣지 않는다
need_result(id, release_id, criteria_release_id, input_hash,
  verdict ∈ need_verdict{keep, no_add, hold, review_add},
  reasons[{statement_kind ∈ {fact, criteria_eval, user_assumption, calc_result, unknown}, text_template_id,
           criterion_version_ref?, evidence[], user_assumption_ref?, assertion_refs[]}],
  decisive_inputs[{input, why_it_changes_verdict}],   -- 결론을 바꿀 때만 추가로 묻는다
  deps → conclusion_dependency)
```

| 규칙 | 내용 |
|---|---|
| 기준의 판 | 기준은 고치지 않는다. 정정은 새 판 + `supersedes`. 출처(`sources`)가 없는 판은 기준 릴리스에 들어가지 못한다 |
| 출처와 근거 종류 | 공공 통계·법령·감독 고시·약관 사실·편집 판단을 `evidence_kind`로 구분한다. 편집 판단(editorial)은 "참고 통계"가 아니라 "온전의 판단"으로 표시된다 |
| 적용 범위 | 기준마다 적용 상황·대상(연령대·계약 유무 등)을 적는다. 범위 밖이면 그 기준은 평가에 쓰지 않는다 |
| 기본값 | 기본 필요액·참고 통계 기본값 **후보**는 출처가 확정된 공공 통계만, 적용 대상·갱신 주기와 함께 적재한다(T-KN-13). 후보는 적용 승인(아래) 전에는 사용자에게 보이지 않는다. 기본값이 없으면 사용자 직접 가정만 쓴다 |
| **서비스 적용 승인 관문** | 설계 승인은 특정 판단 기준의 서비스 적용 승인이 아니다. 실제 사용자에게 **어떤 기준을 적용할지**, **기본 필요액을 제공할지와 그 산출 근거**는 별도 검토 대상이다. `criteria_application(id, criteria_release_id, applied_criterion_versions[], defaults_enabled, defaults_basis_ref, approval_ref{decision_id, approved_by, recorded_at})` 기록이 있는 기준 판만 서비스 모드에서 읽힌다. 기록이 없으면 필요성 판단은 사용자 가정 기반 결과만 내고 기준 평가 이유를 싣지 않는다. **D-08의 범위는 이 관문(적용 기준 목록·기본 필요액 제공 여부·산출 근거)이다.** 판단 기준 관리의 구조·판·출처·정정 이력·의존 기록(T-KN-12)과 사용자 가정 경로(T-AP-09)는 막지 않는다. 과제 T-KN-14 |
| 영역의 책임 | 판단 기준 관리는 명시적인 책임 영역(모듈)이다. 별도 서비스로 배포한다는 뜻은 아니다. 관리하는 것: 기준의 출처, 적용 범위, 가정, 버전, 정정 이력, 결과가 어떤 기준에 의존하는지 |
| 사용자 가정 | 개인 영역 `user_assumption`에 판으로 저장한다. 기본값이 있어도 사용자 가정이 우선하며 덮지 않는다 |
| 결과 | `keep`(유지), `no_add`(추가 가입 없음), `hold`(보류: 결론을 바꾸는 입력이 비어 있음), `review_add`(추가 검토). 네 결과 모두 정상 결과다(불변 원칙 2). 종합 점수·순위는 만들지 않는다 |
| 이유 | 이유마다 `statement_kind`가 붙고, 기준 평가 이유는 기준 판 참조와 그 출처에, 사실 이유는 주장 참조에, 가정 이유는 사용자 가정 판에 연결된다. 연결이 없는 이유는 결과에 실리지 않는다 |
| 결론을 바꾸는 입력 | 판단 기능이 `decisive_inputs`를 낸다. AI는 질문을 고르고 다듬을 뿐 어떤 입력이 결론을 바꾸는지 스스로 정하지 않는다 |
| 정정 영향 | 기준 판이 정정되면 `conclusion_dependency.deps.criteria`로 영향받은 결과를 찾아 `result_state.knowledge_freshness=stale`로 표시한다 |
| 가족력 | 가족력만으로 `review_add`가 나오지 않는다. 관심 담보·확인 질문까지만(ADR-0009) |

### 1.6 결론별 의존 기록과 부분 보류(C-28, F09) — [설계 담당 결정(감리 대상)]

토의 9차(불확실_상황_시험 §2)의 원칙: **불확실성이 영향을 주는 결론만 보류한다.** 이전 판은 판매 구성·약관 판이 불명확하면 개인 계산 전체를 보류했다. 그것은 너무 넓다. 반대로 근거 없이 "이 담보만"으로 좁히는 것은 너무 좁다.

```text
conclusion_dependency(conclusion_id,
  deps{ assertions[a:…], facts[fact:…(계약 사실·사용자 사실·가정)], rules[rule:…], criteria[crit:…@n] },
  unknown_overlap[{ref, state ∈ {not_found, hold, conflicting, ambiguous, input_missing}}],
  produced_by ∈ {engine_trace, compare, need_assessment, compose})
```

| 규칙 | 내용 | 예시 |
|---|---|---|
| D1 기록 | 결론(금액·비교 문장·필요성 결론·합산)마다 의존 집합을 **그 결론을 만든 기능**이 생성한다. 엔진은 trace와 judgements에서, 비교·필요성 기능은 자기 판단에서. 서비스 조합은 연결만 하고 추측해 채우지 않는다 | 계약 A의 암 진단 결론 deps = {A의 `uses_edition`, cov:A의 C0 주장들, rule:A, fact: 진단일·코드} |
| D2 보류 범위 | 미확인 항목 집합 U와 결론의 deps가 **겹치는 결론만** `held`. 겹치지 않으면 `kept` | 계약 B의 약관 판이 ambiguous → U = {B의 uses_edition}. A의 결론 deps에 B가 없으면 A는 kept |
| D3 독립 결과 | 계약별 독립 결론은 각각 판정한다. B가 held여도 A의 독립 결과는 응답에 그대로 실린다 | "A: 500만 원(약관 기준 계산). B: 판 확인 필요" |
| D4 합산 결론 | 여러 계약을 합친 결론은 `partial{excluded_contracts[]}`로 표시한다. 합산이 의미를 잃는 경우(실손 비례분담처럼 한 계약의 미확인이 다른 계약의 몫을 바꾸는 경우)는 `held` | "정액 합계(A만 포함, B 제외): 500만 원" / 실손 비례분담: 보류 |
| D5 영향 범위 미확인 | 값 미확인과 **영향 범위 미확인**을 구분한다. 의존 기록이 없는 결론은 "의존 미확인"으로 넓게 보류한다 | 의존 기록 없는 저장 결과는 관련 변경 시 전부 재검토 |
| D6 변경 시 | 정정·릴리스 철회·기준 판 정정이 오면 저장 결과의 deps와 대조해 **기대는 결과만** 다시 계산한다. 고정 묶음 전체를 버리지 않는다 | 조항 하나 정정 → 그 조항 주장에 기대는 결과만 stale |
| D7 행동 전 확인 | `held`가 아니더라도 기존 계약 변경 단계에서는 결론에 걸린 미확인을 다시 눈에 띄게 보인다(조건의 두 축) | 두 안 비교 저장 전 "B의 판 미확인" 재표시 |

뷰모델에는 결론마다 `dependency_state ∈ {kept, held, partial}`과 `excluded_contracts[]`, `unknown_overlap[]`을 싣는다(§2.4). 개인 계약 트윈의 버전 매핑이 `ambiguous`/`unmatched`인 계약은 그 계약에 기대는 결론만 보류하고 공개 비교는 제공한다(T-PS-02·T-TW-06).

비회원(D-11 결정 전): 개인 API는 계정 필수. `POST /v1/scenarios`(공개)는 개인 저장 없이 쓸 수 있다. D-11이 "서버 저장 없는 계산 허용"으로 정해지면 `POST /v1/evaluations`에 `ephemeral=true` 모드를 추가한다(로그·캐시 미보관).

### 2.3 관제 API (C-16) — 운영자·정책 소유자·읽기 역할, 2FA

`/console/v1/`: `sources`, `denominator`, `changes`, `review-queue`(검수 감사: 에이전트별 판정·근거·코드 검사·레드팀·bbox, 읽기 전용), `impact`, `releases`(후보·공개·철회·그림자 비교 보고), `quality`, `audit-log`, `policy`(임계값·서킷 브레이커 상태. 변경은 정책 소유자 역할만), `gaps`, `acquisition-tasks`(문의 초안 보기. **발송 기능 없음**), `deletion-jobs`(건수·상태만), `cost`(AI 호출·R2 원장 요약). 사용자 원본·건강정보는 어떤 관제 응답에도 없다.

### 2.5 상태·화면 매핑

`display_status`(파생, 저장 안 함)는 서버가 계산해 뷰모델에 넣는다. 매핑 규칙은 계약 시험으로 고정한다(SYSTEM_CONTRACT §10).

| 서버 상태 | display_status | 화면 상태(제3부 §44.2) |
|---|---|---|
| 모든 사실에 근거 사슬 완결, capability enabled | `confirmed` | 기준 |
| `missing_inputs` 비어 있지 않음 | `input_missing` | 판단 불가(질문 1개) |
| 주장 `not_found`/`unreadable` 또는 원문 미확보 | `data_missing` | 부분("확인 필요 n건") |
| `review_status=pending` | `under_review` | 부분 |
| `hold` 또는 미해소 Conflict 또는 서킷 브레이커 | `hold` | 부분 + 계산 없음 |
| 확인된 조건상 미적용 | `not_applicable` | 기준 |
| 릴리스 철회·오류 확인(사용 제한) | `result_state.usage_restriction ∈ {hold, circuit_breaker}` + `knowledge_freshness=withdrawn`, `reproducible=true` 유지 | 변경됨("r-xxx로 계산됨, 그 판은 정정됨, 다시 계산") — 과거 결과는 그 릴리스로 재현 가능하되 새 계산에는 쓰지 않음 |
| 결론이 미확인에 기댐(부분 보류) | `dependency_state=held` (다른 결론은 `kept`, 합산은 `partial`) | 부분("B 계약은 판 확인 필요", A 결과는 표시) |

## 6. 근거 계약 (C-02 보강)

### 6.1 evidence_ref 문법

```text
evidence_ref := clause_ref | segment_ref | edition_ref | premium_ref | assertion_ref | rule_ref | obs_ref | raw_ref | eval_ref | criterion_ref
segment_ref   := "seg:" raw_sha12 ":p" page_from "-" page_to ":" doc_role ":" seg_rule_ver     -- 문서 구획(관측 위치 + 판단)
clause_ref    := "clause:" segment_ref "/" path_slug "#p" page [ "@" x "," y "," w "," h ]    -- 조항은 구획 안에 있다
edition_ref   := "ted:" ulid                                                                    -- 약관 본문 판(판단). 파일 해시 아님
premium_ref   := "premium:" ulid
assertion_ref := "assertion:" ulid
rule_ref      := "rule:" rule_id "@" rule_version "#" content_hash12
obs_ref       := "obs:" source_id "/" rfc3339 "/" sha16
raw_ref       := "raw:sha256:" sha64
eval_ref      := "eval:" ulid
criterion_ref := "crit:" slug "@" version
```

- 근거 역할별 허용 참조: `basis` → `clause_ref`(구획 doc_role이 약관·별표이고 accepted `realizes`가 있는 것만), `cross_check` → `clause_ref`(요약서·안내 쪽 구획), `observation` → `obs_ref`·`segment_ref`·`raw_ref`·공시 행 `clause_ref`.
- `raw_sha12`는 원본 SHA-256 앞 12자(충돌 시 전체 길이로 확장, 릴리스 빌더가 검사). 어느 본문 판인지는 참조에 넣지 않고 `realizes` 주장으로 푼다. 같은 판을 여러 원본이 담을 수 있기 때문이다.
- 현재 픽스처의 `hana_2601_3d#c_2_1_art1_1`, `seg:hana_r2_1` 같은 ID는 **픽스처 지역 ID**이며 정식 문법이 아니다. 픽스처 적재기가 정식 형식으로 변환하되 `origin=fixture`는 유지한다.

### 6.2 사슬 끝까지

| 단계 | 포함해야 하는 참조 | 끊기면 |
|---|---|---|
| 화면 숫자·문장 | `amounts[].source`, `release_id`, `input_hash` | 사실로 표시 금지(I6). `display_status=data_missing` |
| 뷰모델 → EvaluationResult | `eval_ref` 또는 인라인 결과 + `rule_ref` | 금액 자리 비움 |
| EvaluationResult → Rule | `rule_ref`(id·판·해시) + `evidence_refs[]` + **노드별** `trace[].evidence_ref?`(R17, T-TW-05) | 노드별 근거 없으면 규칙 수준 근거로 표시하되 "조항별 설명 없음" 표시 |
| 입력 단계 판정 → 주장 | `judgements[].evidence_assertion_ids[]` | 판정값 unknown 처리 |
| Rule → 주장 | K9: 규칙 `evidence_refs ⊆` 담보 C0 accepted 주장의 basis | 릴리스 차단 |

| ClauseOccurrence → DocumentSegment → TermsEdition | `in_segment`, accepted `realizes`(지문 있는 구획, K14) | 그 조항은 약관 본문 판에 이어지지 않은 것이라 basis가 될 수 없다(K1) |

| RawAsset → SourceObservation → Source | `obs_ref`, URL, 관측 시각 | 릴리스 차단 |
| 필요성 결론 → 기준 판 | `reasons[].criterion_version_ref → criteria_release` | 그 이유는 결과에 실리지 않는다(§1.5) |
| 가격 | `premium_ref → clause_ref(표 셀) → raw` | compare_price blocked |

### 7.2 삭제 순서와 늦은 쓰기

원본 → 추출값 → 색인 → 캐시 → 파생 결과 → 외부 처리본. 삭제 시작 뒤 도착한 쓰기는 `ONJ-PS-S-031`로 거부한다. 백업 복원 시 삭제 표시를 재적용한다(삭제 표 자체는 보존). 백업 보존 기한과 "삭제 완료"의 뜻은 D-17(O09)에서 정하며, 그 전에는 즉시 완전 삭제를 약속하는 문구를 쓰지 않는다.

### 8.2 서비스 데이터로 들어가지 못하게 하는 차단 조건 (모두 기계 검사)

| 번호 | 차단 지점 | 검사 | 실패 시 |
|---|---|---|---|
| B1 | 저장소 분리 | 서비스 적재기는 `packages/fixtures/**`·`docs/blueprint/**` 경로를 입력으로 받지 않는다(경로 allowlist: R2 관측 목록에 있는 해시만) | `ONJ-KN-S-050` |
| B2 | 주장 삽입 | `origin=fixture`는 `review_status=accepted`가 될 수 없다(DB 제약 `chk_fixture_never_accepted`) | 삽입 거부 |
| B3 | accepted 조건 | `accepted ⇒ review_decision_id`. ReviewDecision은 ai-review만 쓰며, 서로 다른 모델 계열 2개 이상의 추출 일치 + 코드 검사 전부 통과 + 레드팀 반례 0 + 교차 문서 충돌 없음을 기록한다(ADR-0006, 제3부 §57.3). 가정 승인을 적는 필드가 없다 | 삽입 거부 |
| B4 | 근거 해시 | 주장 basis 근거 조항의 구획이 가리키는 RawAsset.sha256이 R2 관측 목록(archive listing, Git 고정)에 있어야 한다. 사례 문서 세 건의 해시는 세션 임시 영역에만 있고 R2에 없다 | 릴리스 차단 |
| B9 | 판 동일성 | `realizes`는 지문 있는 구획의 관측 근거가 있어야 accepted(K14). 사례의 realizes 여섯 건은 `origin=fixture`·가정 승인이며 B2에서 막힌다 | 삽입 거부 |
| B5 | 규칙 | 릴리스 빌더는 `publication_state=fixture_only` 규칙을 거부한다. `candidate`는 release_id·evidence_refs 필수(엔진 로더가 이미 강제, rule.rs 285~293행) | `ONJ-KN-S-050` |
| B6 | K9 | 규칙 근거 ⊆ accepted C0 basis. 픽스처 주장은 accepted가 아니므로(B2) 규칙이 컴파일되지 않는다 | 컴파일 거부 |
| B7 | CI | `packages/fixtures/**`를 참조하는 마이그레이션·시드·서비스 코드 import를 정적 검사로 금지. 릴리스 빌더 시험에 "픽스처 섞인 입력 → 거부" 사례 고정 | PR 차단 |
| B8 | 코드 우주 | 서비스 CodeSystem은 공식 출처 원본(RawAsset) + 해시 고정이 있어야 한다. 근사 우주로 계산한 scope_relation은 `not_comparable` 취급(K12) | accepted 불가 |

**지름길이 없음을 명시한다.** 사례 주장의 `review_status`를 손으로 `accepted`로 바꾸거나 `_review_note`를 지우거나 `origin`을 `pipeline`으로 고쳐 넣어도 B3(ReviewDecision 없음)·B4(R2 해시 없음)·B7(경로)에서 막힌다. ReviewDecision은 ai-review 실행 기록(모델 계열 2개, 코드 검사 로그, 프롬프트 판)을 참조하므로 손으로 만들 수 없다(참조 무결성 + 감사 로그 해시 연결).

### 8.3 정식 승격 경로

| 단계 | 구역 | 입력 | 출력 | 차단 조건 |
|---|---|---|---|---|
| P1 원본 보존 | data | 공개 URL(robots·요청 제한 준수) | RawAsset(R2, 조건부 쓰기) + SourceObservation | 200이어도 MIME·길이·파싱 실패면 격리. **R2 토큰 미폐기면 이 단계만 막힘(D-04)**. robots 확인 불가 호스트는 보류(롯데 사례) |
| P2 복원·구획 | data(docproc 공시용) | RawAsset | DocumentSegment(쪽 범위·문서 역할·구획 규칙 판·본문 지문), ClauseOccurrence(쪽·좌표·정확 인용·표 셀·추출기 판) | 쪽 수 불일치·별표 누락·끊긴 표·참조 미해결·구획 경계 미확정 → 자동 승인 차단 |
| P2b 본문 판 판단 | knowledge | DocumentSegment 지문·제목·개정 표기 | `realizes`(구획 → TermsEdition) 주장(pending) + 필요 시 새 TermsEdition·TermsLineage | 원본 해시 일치만으로 세우지 않음(K14). 지문 없는 구획은 보류 |
| P3 추출 | knowledge(ai-review, ai-gateway 경유) | ClauseOccurrence | 주장 후보(`pending`, `origin=pipeline`), 근거 없는 후보는 거절 | 문서 속 지시문 미실행(I13). 요약서만 근거인 C0는 basis 불가(K1) |
| P4 이종 계열 검수 | knowledge(ai-review) | 후보 | ReviewDecision → accepted / hold / rejected | **D-02 결정 전에는 이 단계가 비어 있다.** claude 계열만으로는 ReviewDecision을 만들 수 없다(families_count ≥ 2 제약). 불일치·반례는 hold(I14), 다수결 금지 |
| P5 일관성 제약 | knowledge(`packages/ontology`) | 현재 주장 집합(후보 뷰) | 제약 보고(K1~K14 위반 0) | 위반 1건이라도 후보 릴리스 중단(`ONJ-KN-S-051`) |
| P6 컴파일 | twin(컴파일러) | accepted C0 주장 | Rule(`candidate`, release_id 예약, 내용 해시) + 설명 템플릿 | K9, 엔진 로더 거부(허용 목록 밖 연산·반올림 누락), 두 표현 대조 불일치 |
| P7 그림자 비교 | twin | 새·옛 릴리스 + 같은 입력 묶음 | 차이 보고(원인 연결) | 원인 없는 금액 차이 1건이라도 배포 차단 |
| P8 릴리스 | knowledge | P5~P7 보고 | ReleaseManifest(구성원 목록·규칙 파일 해시·내용 해시, K15) + capability 표(K11) | 보고 ID 누락 시 생성 거부. 고정 뒤 구성원 변경·누락은 K15 위반 |

사례 세 상품(하나·현대·롯데)이 서비스에 들어가는 길은 이 경로뿐이다. 사례 파일은 P3의 **참고 입력**(AI 추출 프롬프트의 예시)으로도 쓰지 않는다. 평가셋 누출 방지(SYSTEM_CONTRACT §13)와 같은 이유다.
