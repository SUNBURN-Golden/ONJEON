# 실제 사례로 본 식별 표현 (토의용)

상태: **토의 자료. 미확정.** 2026-10-10 | [수집·지식 기반 설계 제안](수집_지식기반_설계_제안.md) §3(P2.1~P2.9)을 실제 공시 행으로 시험한다.

> **검토 중 표시(2026-10-10):** §B 수락 시험("약관 해시가 같다고 확인되어 same_as를 승인")은 조사 결론(같은 약관을 쓰는 다른 판매 구성)과 충돌해 철회 대상이다. §A 되돌림 절차의 ID 처리와 §B의 "보조 출처는 판매 구성을 만들지 않는다" 규칙도 재검토 중이다. 사례 3에는 협회 공시행 두 개(건강고지Ⅰ·일반심사)라는 새 관측이 있다. 모두 [데이터 모델 토의 보완안](데이터모델_토의_보완안.md)에 보류 상태로 있다.

- 아래 값(상품명, 코드, 날짜, 파일명, 해시)은 2026-10-10 조사에서 받은 원본에서 그대로 옮겼다. 원본은 세션 임시 영역에만 있다([조사 README](../../research/2026-10-10_source_survey/README.md) §보존 상태).
- `SO-…`, `TE-…`, `DL-…` 같은 내부 ID는 **설명용 예시**다. ID 형식은 정하지 않았다.
- 객체 이름은 제안서의 제안 이름이다. 확정되지 않았다.

## 0. 표현의 다섯 층 (제안서 P2.1 요약)

```text
출처 행 ListingObservation   한 회차에 출처가 보여 준 한 행. 원 행 해시로 고정. 고치지 않는다
   │  "이 행은 이 판매 구성을 보여 준다"  (IdentityLink, 근거·상태 있음)
   ▼
판매 구성 SaleOffering        한 기관이 한 판매기간에 판 하나의 단위. 내부 발급 ID
   │  "이 판매 구성의 약관은 이 문서다"   (OfferingDocumentBinding, 관측 구간 있음)
   ▼
문서 위치 DocumentLocator     URL·요청 방식. 시점마다 다른 내용을 줄 수 있다
   │  "이 위치에서 이 바이트를 받았다"    (SourceObservation, 수집 시각)
   ▼
원본 RawAsset                  받은 바이트. SHA-256
   = 문서 판 TermsEdition      약관 문서의 한 판(바이트 해시 기준)

계열 ProductLineage            판매 구성끼리 "같은 상품의 개정"이라는 주장. 탐색·설명용
```

연결은 모두 근거와 상태(`proposed` / `approved` / `rejected` / `hold` / `superseded`)를 가진 주장이다. 판매 구성끼리의 관계는 세 가지다: `same_as`(같은 판매 구성, 병합), `distinct_from`(다른 판매 구성임을 확인, 다시 제안하지 않음), `lineage`(같은 계열의 다른 판).

## A. 서로 다른 상품을 잘못 합치는 경우

### 생기는 경로
1. 코드 재사용(사례 2, 교보 dgtPdtCd 222개)
2. 같은 문서 해시(사례 1·5: 채널판, 종, 판매기간이 같은 파일을 씀)
3. 이름 정규화(우체국 "우체국급여실손의료비보험" 2행 중 하나는 계약전환용, E 기록. 삼성생명에서 무배당 표기·공백을 지우면 같아지는 이름 묶음 43개, C 기록 — 같은 상품인지는 확인하지 않았다)
4. 파일명 속 코드(사례 1의 [D] 행)
5. 출처 간 매칭(협회 공시행·다모아 행을 회사 행에 잘못 붙임)

### 미리 막는 규칙(제안)
- 판매 구성은 **출처 행 하나**에서 만든다. 코드·이름·문서 해시는 판매 구성을 만드는 키가 아니라 연결 제안의 근거다.
- 출처가 자기 상품 ID를 주면(교보 `dgtPdtPdSeqtId`, 메트라이프 `insProdSeq`) 그 ID가 다른 행끼리는 자동으로 `same_as`를 제안하지 않는다.
- 한 번 `distinct_from`으로 확인한 쌍은 같은 근거로 다시 제안하지 않는다.

### 발견 신호(정기 자동 검사)

| 신호 | 잡히는 사례 |
|---|---|
| 한 판매 구성·계열 안에 같은 이름공간의 출처 상품 ID가 둘 이상 | 사례 2를 코드로 묶었을 때 |
| 한 계열 안의 판매기간이 크게 끊기고(예: 수십 년) 그 사이 이름 변경 근거가 없음 | 사례 2(1983 → 2003) |
| 연결된 행들의 분류·채널 코드가 다름 | 사례 2(PAMS02/PAMS03), 사례 1을 합쳤을 때(PAMS04/PAMS06) |
| 연결된 약관 판끼리 본문 차이가 매우 큼 | 사례 2 |
| `identifier_collision` 건수 증가 | 코드 재사용 전반 |
| 개인 계약 매칭에서 후보가 둘 이상인 건수 증가(비공개 영역의 건수만, 개인 식별자 없음) | 잘못 합친 판매 구성에 계약이 붙은 경우 |
| 검수 AI·사람의 반례 | 모든 경우 |

### 되돌리는 절차(제안)
1. 잘못된 `same_as`(또는 `lineage`)를 `rejected`로 바꾸고 새 판으로 기록한다. 이전 판은 지우지 않는다.
2. **분리:** 원래 판매 구성 ID는 그 판매 구성을 처음 만든 출처 행(기준 행) 쪽에 남는다. 떨어져 나간 행은 새 ID를 받는다. 결과가 같은 입력에 늘 같게 나오도록 규칙으로 정한다.
3. 쌍에 `distinct_from`을 기록해 다시 합쳐지지 않게 한다.
4. **영향 범위:** 그 연결을 포함한 릴리스, 그 판매 구성 ID를 쓴 평가·화면, 영향받은 판매 구성에 붙은 개인 계약 매칭(비공개 영역)을 찾는다.
5. 새 릴리스에서 다시 평가한다. 개인 계약 매칭은 `ambiguous`로 내려 다시 확인받는다.
6. 과거 릴리스는 고치지 않는다. "정정됨"으로 표시하고, 그 릴리스로 다시 실행하면 당시 결과가 그대로 나온다(제안서 P3.5).

**수락 시험:** 사례 2의 두 행을 일부러 `same_as`로 승인한 뒤 되돌리면 (1) 기준 행 쪽 ID가 유지되고, (2) 떨어진 쪽이 새 ID를 받고, (3) 영향 릴리스 목록이 나오고, (4) 같은 쌍이 다시 제안되지 않는다.

## B. 같은 상품을 둘로 만드는 경우

### 생기는 경로
1. 같은 행의 재등록(사례 3, 하나손보 이름·기간 같은 6쌍)
2. 코드 이전·동시 코드(사례 4 가)
3. 이름 변경으로 계열이 갈라짐(사례 4 나, AIA "(구, …)", 하나손보 The·K → 하나)
4. 출처 간 따로 생성(같은 판매 구성을 회사 행·협회 행·다모아 행에서 각각 만듦)
5. 같은 출처의 탭 중복(삼성생명 전체 탭 6,680행 대 판매중+판매중지 6,681행)

### 미리 막는 규칙(제안)
- 판매 구성은 **기본 출처**(회사 공시실, 우체국은 고시·공공 API) 행에서만 만든다. 협회·다모아·finlife 행은 기존 판매 구성에 연결되거나 `external_only`(대응 판매 구성 못 찾음)로 남는다. 보조 출처가 판매 구성을 새로 만들지 않는다.
- 같은 회차·같은 출처에서 원 행 해시까지 같은 행은 관측 하나로 접는다(완전 중복 행).
- 계열은 이름이 아니라 출처 코드의 연속성으로 먼저 잇는다(사례 4 나).

### 발견 신호(정기 자동 검사)

| 신호 | 잡히는 사례 | 오탐 |
|---|---|---|
| 같은 기관·같은 정규화 이름·같은 개시일·같은 채널의 판매 구성 쌍 | 사례 3, 사례 4 가, 하나 6쌍 | 종·형만 다른 정당한 쌍(이름에 종 토큰이 남아 있으면 걸러짐) |
| 같은 문서 위치·해시를 공유하고, 코드·채널·종 같은 구분 요소가 없는 쌍 | 사례 4 가 | 사례 1(구분 요소가 있어 제외), 사례 5(종·기간이 달라 제외) |
| 한 계열의 판매가 끝난 날 다음 날 같은 기관에서 비슷한 이름의 새 계열이 시작 | 사례 4 나 | 실제 신상품 출시 |
| 보조 출처 행 하나가 판매 구성 둘에 매칭 | 출처 간 중복 | 채널 병기 |

### 되돌리는 절차(제안)
1. `same_as`를 승인하면 **생존 ID 하나**를 정하고 나머지는 `alias_of`(별칭)로 둔다. 별칭을 지우지 않는다. 생존 ID는 먼저 관측된 쪽이다(규칙으로 고정).
2. 과거 릴리스와 평가는 옛 ID 그대로 재현된다. 새 릴리스에서는 별칭이 생존 ID로 해석된다.
3. 병합이 잘못이었으면 별칭을 풀고 A의 분리 절차를 따른다.
4. 판단 보류 중(사례 3·4)에는 두 판매 구성을 모두 두고 `duplicate_candidate`·`unresolved_pair`로 표시한다. 분모 지표에서는 후보 쌍을 따로 센다. 화면에서 어떻게 보일지는 토의 5번(화면 흐름)에서 정한다.

**수락 시험:** 사례 3에서 두 약관 해시가 같다고 확인되어 `same_as`를 승인하면 SO-D2가 SO-D1의 별칭이 되고, 병합 전 릴리스는 SO-D2를 그대로 해석하며, 병합 후 릴리스의 판매 구성 수가 하나 줄어든다.
