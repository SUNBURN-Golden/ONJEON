# 가격 수집 명세 v0.2 (상세 부록)

2026-10-09 | 제3부 §47.1·§59의 하위 문서 | 화면 연결: `docs/design/화면_조작_설계서.md` §5, §8

**상위 문서는 [`docs/data/PREMIUM_DATA_CONTRACT.md`](../data/PREMIUM_DATA_CONTRACT.md)와 ADR-0010이다.** 이 명세는 그 계약에 데이터 모델 세부(조건·특약 라인·가격 분모·변동 이벤트), 검증 항목, 지표, 테스트 시나리오를 더하는 부록이다. 충돌하면 상위 문서를 따른다.

이 문서는 설계 요구사항이다. 실제 가격 수집, 크롤러, 데이터베이스는 아직 없다. 소스 후보는 AI 분모 조사(제3부 §57.6)로 확정한다. 수치 기준은 제안값이며 P2 파일럿으로 조정한다.

## 1. 결정과 원칙

사용자 결정(2026-10-08): 가격 데이터도 첫 출시의 수집·비교 대상이다.

1. **가격은 묶음으로만 저장한다.** 보험료는 가입 조건, 특약 구성, 기준일과 함께 한 레코드로 저장한다. 조건 없는 가격은 저장하지 않는다.
2. **가격 근거를 구분한다.** 공시 예시, 요율표 재현, 내 계약 납입액, 개인 견적, 미확인은 서로 다른 근거이며 섞지 않는다.
3. **공개 가격은 견적이 아니다.** 공시된 명시 조건의 가격이며 개인의 정확한 보험료가 아니다(v0.3 §21의 협회 비교공시 해석).
4. **가격 미확인 상품도 숨기지 않는다.** 미확인은 0원이 아니다(불변 원칙 3). 목록에 남기고 사유를 붙인다.
5. **광고비·수수료는 가격 정렬과 비교에 영향을 주지 않는다**(불변 원칙 1).
6. 가격 계산·표시의 결과는 근거(소스, 문서, 표 셀, 기준일)까지 추적할 수 있어야 한다(불변 원칙 5).
7. 보험료를 요율·위험률로 역산해 만들지 않는다. 사업방법서의 산출 근거는 원문으로 보관하되 첫 출시에서 재계산에 쓰지 않는다.

## 2. 가격 근거 종류

근거 코드는 PREMIUM_DATA_CONTRACT와 제3부 §47.1을 따른다. 신뢰 순위가 아니라 서로 다른 근거이며 한 종류를 다른 종류로 승격하지 않는다.

| 코드 | 이름 | 의미 | 출처 | 첫 출시 |
|---|---|---|---|---|
| `illustrative` | 공시 예시 | 공시된 명시 조건의 예시 보험료. 개인 정보 없이 누구나 같은 값을 본다 | 협회 비교공시, 보험사 공시실의 예시, 비로그인 공개 조회의 허용된 응답 | 수집·표시 |
| `table_derived` | 요율표 재현 | 확보한 공개 요율과 산식(요율·반올림·할인·구성 규칙)이 모두 있을 때 재현한 금액 | 공개 보험료표, 산식 | 검증된 범위만 |
| `contract_observed` | 내 계약 납입액 | 사용자 PDF에서 확인한 실제 납입액. 납입 시점을 함께 표시 | 사용자 가입내역 PDF | 수집·표시 |
| `quoted` | 개인 견적 | 개인 조건에 대한 유효 견적. 만료 시각이 있다 | 제출 견적서, 견적 연계 | 스켈레톤 |
| (상태) 미확인 | 가격 미확인 | 가격을 확인하지 못함. 사유 필수 | - | 표시 |

- 비로그인 공개 계산기가 개인정보·로그인·심사 연동을 요구하면 그 결과는 개인 견적이므로 수집하지 않는다. 인증을 우회하지 않는다(v0.3 §24.1).
- 자동차보험처럼 개인별 편차가 큰 상품군은 공개 가격에 `indicative_only` 표시를 붙인다.
- 보험료를 요율·위험률로 역산하지 않는다. `table_derived`는 산식과 입력이 모두 공개·확보된 경우에만 별도 검증을 거쳐 허용한다.
- 종류별 사용처:

| 종류 | 예산 필터·가격 정렬 | 비교 화면 | 현재 유지 기준선 |
|---|---|---|---|
| `illustrative` | 같은 비교 기준끼리 | 포함 | 사용 안 함 |
| `table_derived` | 검증된 범위만, 같은 비교 기준끼리 | 포함 | 사용 안 함 |
| `contract_observed` | 사용 안 함 | 현재 유지 열 | 사용 |
| `quoted` | 켜진 뒤 우선 적용 | 포함 | 사용 안 함 |
| 미확인 | 제외가 아니라 별도 노출, 건수 표시 | 점선 표시 | 해당 시 "일부 미확인" |

## 3. 소스 계층 (후보)

| ID | 소스 | 가져올 것 | 비고 |
|---|---|---|---|
| P-A | 협회 비교공시 | 보험 종류별 연령·성별 조건의 보험료 | 협회 목록과 보험사 목록의 교차 대조 소스 |
| P-B | 보험사 공시실의 상품요약서·공시 자료 | 표준 조건 예시 보험료 | 문서 안 표를 복원(제3부 §59, v0.3 §26) |
| P-C | 보험사 공개 보험료표 | 연령·성별·플랜별 요율표 | 있는 경우만 |
| P-D | 보험사 비로그인 공개 계산기 | 조건 격자 질의 결과 | 이용 조건과 요청 제한이 허용하는 범위에서만 |
| P-E | 사업방법서의 보험료 산출 근거 | 원문 보관 | 재계산에 쓰지 않음 |
| P-F | 사용자 가입내역 PDF | 내 계약 보험료 | 개인 영역에서 처리. 공시 정답셋에 섞지 않음 |
| P-G | 개인 견적(스켈레톤) | 제출 견적서, 견적 연계 | 켜는 조건은 별도 결정 |

- 소스마다 접근 방식, 요청 제한, 이용 조건 검토 결과를 `SourceRegistry`에 기록한다(v0.3 §6).
- 같은 가격이 P-A와 P-B 양쪽에 있으면 둘 다 저장하고 일치를 교차 검증한다.

## 4. 데이터 모델

### 4.1 PriceObservation

한 조건에서 한 번 관측한 가격 하나다.

| 필드 | 설명 |
|---|---|
| `price_id` | 내부 불변 ID |
| `product_version_id` | 상품 버전(v0.3 §27). 이름만으로 연결하지 않는다 |
| `price_kind` | §2의 근거 코드 |
| `source_id`, `evidence` | 소스, 자산 해시, 블록·표·셀, 정확 인용(제2부 §29의 FieldAssertion 규칙) |
| `amount` | `{currency:"KRW", minor:int}` 정수. 부동소수점 금지 |
| `amount_raw` | 원문 표기와 단위("12,300원", "1.2만원") |
| `frequency` | `monthly | annual | lump_sum | other` |
| `amount_scope` | `total_premium | main_only | rider_line`. 합계인지 일부인지 |
| `observed_at` | 우리가 관측한 시각 |
| `source_as_of` | 소스가 밝힌 기준일(없으면 null) |
| `effective_from`, `effective_to` | 가격이 적용되는 기간(valid time) |
| `recorded_at`, `superseded_at` | 시스템이 알게 된 시각, 대체된 시각 |
| `query_signature` | 조회 조합(조건 격자의 한 점) |
| `value_state` | 제2부 §28.3의 상태. `observed`일 때만 금액 허용 |
| `comparison_basis_id` | 이 가격이 속한 비교 기준(동일 조건 집합). 가격 비교·정렬의 단위 |
| `package_binding` | 묶음 가입·주계약·특약 종속·최저 가입금액 검증 결과 |
| `missing_dimensions` | 조건 중 확인하지 못한 항목 목록 |
| `review` | AI 승인 결과(제3부 §57). 금액이므로 C0 |
| `supersedes_id` | 이전 관측 |

### 4.2 PriceCondition

가격과 1:1이다. 값은 정규화하되 원문 표기를 함께 보관한다.

| 필드 | 설명 |
|---|---|
| `insured_age` | `{kind: exact | band, value, raw}`. 만 나이와 보험 나이를 구분 |
| `sex` | 남·여·무관 |
| `health_class` | 표준체·건강체·간편·유병자 등 원문 분류 |
| `smoker`, `occupation_class` | 있으면 |
| `insured_amount` | 주계약 가입금액(Money) |
| `insurance_period` | 만기형(세 만기·연 만기)과 기간 |
| `payment_period` | 납입 기간, 납입 방법 |
| `renewal` | 갱신형 여부, 갱신 주기 |
| `refund_type` | 해지환급형·무해지환급형 등 |
| `plan_variant` | 실손 세대, 표준형·선택형 등 |
| `channel` | 온라인·오프라인 등 소스가 구분하는 경우 |
| `discounts` | 적용된 할인 목록(원문) |
| `assumptions` | 소스가 밝힌 가정(예: 갱신 시 인상률 가정) |

조건 항목을 소스가 주지 않으면 비워 두지 않고 상태(`not_disclosed` 등)를 적는다. 조건 하나라도 모르면 사용자 조건과 정확 일치로 판정하지 않는다.

### 4.3 PriceRiderLine

특약 구성을 보존한다. 같은 상품이라도 구성이 다르면 서로 다른 가격 레코드다. 병합하지 않는다.

| 필드 | 설명 |
|---|---|
| `price_id` | 상위 가격 |
| `rider_occurrence_id` | 특약 발생본(v0.3 §27, 동명 특약 병합 금지) |
| `included` | 구성에 포함되는지 |
| `insured_amount` | 특약 가입금액 |
| `line_amount` | 특약별 보험료(소스가 주는 경우, 아니면 null) |

- 합계 레코드와 라인의 합이 맞는지 검사한다(§6).
- "주계약만"과 "주계약 + 특약 N개"는 각각 별도 가격이다.

### 4.4 ExpectedPrice (가격 분모)

문서 분모(제2부 §23.3)와 같은 방식으로 상품 버전마다 기대 가격 지점을 만든다.

| 필드 | 설명 |
|---|---|
| `product_version_id` | |
| `expected_condition` | 소스가 제공하는 조건 격자의 한 점 |
| `discovery_state` | 확인됨, 아직 못 찾음, 공개되지 않음 등 |
| `price_id_if_resolved` | |
| `missing_reason`, `first_missing_at`, `last_checked_at` | |

### 4.5 PriceChangeEvent

가격이 바뀌면 이벤트를 남긴다: 이전·이후 값, 변동률, 감지 시각, 원인(요율 개정, 조건 변경, 재공시, 파싱 차이).

## 5. 가격 상태와 미확인 사유

| 상태 | 뜻 | 화면 문구 |
|---|---|---|
| `observed` | 가격 확인됨 | 가격과 라벨 |
| `not_found` | 아직 못 찾음 | 가격 미확인 · 찾지 못함 |
| `not_disclosed` | 조사 범위에서 비공개로 확인됨(근거 필요) | 가격 미확인 · 공개되지 않음 |
| `unreadable` | 원문 판독 실패 | 가격 미확인 · 읽지 못함 |
| `conflicting` | 근거 충돌 | 가격 미확인 · 근거 충돌 |
| `pending_review` | 검토 중 | 가격 미확인 · 검토 중 |
| `condition_mismatch` | 공개된 조건이 사용자 조건과 달라 직접 적용 불가 | 가격 미확인 · 조건이 달라요 |
| `stale` | 정책상 기한이 지남 | 가격 확인일이 오래됐어요 |

- 어느 상태에서도 금액을 0, 무료, 제한 없음으로 바꾸지 않는다.
- 미확인 상품은 비교 목록, 담보 상세, 비교 화면에서 모두 보인다.

## 6. 수집 방법

### 6.1 순서

1. 상품 버전을 먼저 식별한다(제2부 §27). 가격만 따로 떠도는 레코드를 만들지 않는다.
2. 소스가 제공하는 조건 격자를 파악해 `ExpectedPrice`를 만든다.
3. 원문(표·계산기 응답)을 불변 보관하고 격자 각 점의 가격을 추출한다.
4. 정규화하고 검증한다(§7).
5. AI 승인(제3부 §57)을 거쳐 상태를 확정한다.

### 6.2 문서에서 추출할 때

- 표의 열 제목 단위(원, 천원, 만원)와 월납·연납 구분을 셀과 함께 묶어 근거로 삼는다(v0.3 §26.2).
- 연령 구간 표기("30~34세")는 구간으로 보관하고 한 나이로 바꾸지 않는다.
- 특약 구성표와 합계 행을 같은 레코드로 연결한다.
- 각주의 가정(할인, 갱신 가정)은 `assumptions`로 보존한다.

### 6.3 공개 계산기로 질의할 때

- 질의 가능한 조건 격자를 조사해 `query_matrix`로 기록한다(v0.3 §23.2).
- 격자는 모든 조합이 아니다. 소스가 허용하는 요청량 안에서 대표 연령, 성별, 대표 가입금액, 대표 기간·납입 조합을 우선한다. 조회하지 못한 조합은 `not_found`로 둔다.
- 개인정보·로그인·심사 연동이 필요해지면 중단하고 그 상품은 개인 견적 영역(스켈레톤)이라고 기록한다.
- 요청 제한, 백오프, 서킷 브레이커를 지킨다(v0.3 §25).

### 6.4 어댑터 계약 추가

기존 어댑터 기능(제2부 §24.1)에 다음을 더한다: `enumerate_price_points`, `fetch_price_table`, `query_price_grid`(허용될 때만), `reconcile_price_inventory`.

## 7. 정규화와 검증

LLM이 아닌 코드 검사를 앞세운다.

| 검사 | 내용 | 실패 시 |
|---|---|---|
| 단위 | 원·천원·만원, 천 단위 구분, 소수점 | `unreadable` 또는 재추출 |
| 빈도 | 월납·연납·일시납을 원문대로 저장. 연납÷12는 파생값 "월평균"으로 따로 저장하고 실제 월납과 구분한다 | 필요한 빈도의 값이 없으면 그 빈도는 미확인 |
| 합계 | 합계 = 주계약 + 특약 라인의 합(라인이 있을 때) | `conflicting` |
| 근거 일치 | 정확 인용이 해당 셀에 있는지 | 승인 보류 |
| 연령 순서 | 같은 조건에서 연령이 오를 때 보험료가 줄면 경고 | 레드팀 검토 후 보류 가능 |
| 성별·플랜 이상치 | 극단적 차이 경고 | 레드팀 검토 |
| 교차 소스 | 같은 조건의 P-A와 P-B 값 일치 | 불일치는 `conflicting` |
| 시계열 | 전일 대비 큰 변동은 재추출로 확인 후 확정 | 확인 전 기존 값 유지 |

- 연납÷12는 월평균 비용으로만 표시하고 실제 월납 보험료처럼 보이지 않는다. 연납에는 할인이 붙기도 하므로 월납 값으로 저장하지 않는다. 소스가 월납을 주지 않으면 월납 필드는 비어 있고 `not_disclosed`다. 납입기간과 보장기간이 다른 총납입액은 같은 지표처럼 비교하지 않는다.
- 갱신형의 갱신 후 보험료는 확정 총액이 아니다. 소스가 제공하는 가정별 시나리오로만 저장한다(v0.3 §11).
- AI 승인은 C0 정책(제3부 §57.3)을 따른다. 서로 다른 모델 계열 추출 일치, 검증, 레드팀, 코드 검사가 모두 통과해야 `observed`가 된다.

## 8. 기준일과 최신성

- 세 가지 시각을 분리한다: `source_as_of`(소스 기준일), `observed_at`(우리가 관측한 시각), `effective_from/to`(적용 기간).
- 화면의 "기준일"은 `source_as_of`이고 없으면 `effective_from`이다. 둘 다 없으면 "확인일"(`observed_at`)을 쓰며 라벨이 다르다.
- `stale` 판정 임계는 소스별 갱신 주기에서 정한다. P2에서 소스별 실측 후 확정한다(제안값은 없음).
- 매일 크롤링(제3부 §59.3)은 가격도 같은 일정으로 확인한다. 실패한 날은 마지막 검증 값을 유지하고 `stale` 경고를 붙인다.
- 가격 변동이 감지되면 `PriceChangeEvent`를 만들고 영향을 받는 비교·시뮬레이션만 다시 계산한다.
- 개인 견적(스켈레톤)은 만료 시각이 필수이며 만료되면 사용하지 않는다.

## 9. 비교 기준과 사용자 조건

화면의 예산 필터와 가격 정렬은 하나의 **비교 기준**(`comparison_basis_id`) 안에서만 한다. 비교 기준은 가격이 확보된 공시 조건 집합(연령·성별·가입금액·기간·구성 등)이며 사용자의 개인 견적이 아니다.

| 상황 | 처리 |
|---|---|
| 후보의 가격 조건이 비교 기준과 같음 | 비교 기준의 가격으로 표시, 근거 `illustrative` 또는 `table_derived` |
| 후보에 비교 기준과 같은 조건의 가격이 없음 | 가격 미확인(조건이 달라요). 가까운 다른 조건의 가격을 비교 기준 가격처럼 보여주지 않는다. 조건 시트에 "공시 조건: 45세 남"처럼 라벨과 함께 참고로만 보일 수 있다 |
| 사용자 조건과 비교 기준이 다름 | 조건 시트에 "내 조건 아님"을 표시 |
| 가격을 찾지 못함 | `not_found` 등 §5의 상태 |

- 예시 보험료를 사용자 나이에 선형 보간하거나 가입금액에 단순 비례시키지 않는다. 구간 추정 값을 만들지 않는다.
- 사용자가 고를 수 있는 비교 기준은 실제 확보된 조건 집합뿐이다. 가까운 나이의 공시 조건을 고르는 것은 사용자의 선택이며 결과는 그 조건의 가격이다.
- 만 나이와 보험 나이가 다를 때는 소스가 쓰는 나이 기준에 맞춘다.
- 개인 계약 납입액과 공개 표준 조건 예시 사이의 차이를 개인의 확정 절감액으로 표시하지 않는다. 가격 기준이 다르면 절감액을 계산하지 않는다.
- 갱신 첫해 가격을 평생 고정 비용으로 표시하지 않는다. 갱신 보험료가 공개되지 않으면 미래 총액을 만들지 않는다.

## 10. 화면 연결

| 화면 요소 | 가격 데이터 |
|---|---|
| 슬라이더의 현재 납입액 눈금(C2) | `contract_observed` 합계. 일부 미확인이면 "일부 미확인". 예산 값을 바꾸지 않음 |
| 보완안의 가격 보조줄(C3) | 담보 그룹의 후보 상품 가격(같은 비교 기준). 후보가 여럿이면 후보 사이의 최소~최대 |
| 예산 후보 분류 | 확인된 가격과 예산의 비교: 예산 안 / 예산 초과 / 가격 미확인(별도) |
| 담보 비교의 상품 행 | 가격 근거, 라벨, 기준일, 미확인 사유 |
| 하단 캡션(C1) | "공시 조건으로 비교 중", 탭하면 조건·가격 근거·기준일 |

합계 규칙:

- 합계는 같은 비교 기준·같은 구성의 확인된 가격만 더한다. 가입 가능한 묶음·주계약·특약 종속·공유 할인·최저 가입금액을 검증하지 못하면 조합 총액은 미확인이다.
- 특약 단가만 수집했다고 주계약과 임의 합산하지 않는다.
- 미확인은 0원으로 더하지 않고 건수(`unpriced_count`)로 따로 표시한다.
- 가격 범위는 서로 다른 후보 상품의 확인된 가격의 최소~최대일 때만 쓰며 한 상품의 보간 값이 아니다.

## 11. 품질 지표 (공개 `/coverage`와 관제)

| 지표 | 분자 / 분모 |
|---|---|
| 가격 확보율 | 확인된 가격 지점 / 기대 가격 지점 |
| 조건 완전성 | 조건 필드가 모두 채워진 가격 / 확인된 가격 |
| 특약 구성 보존율 | 라인이 있는 가격 / 라인이 있어야 하는 가격 |
| 일일 확인 달성률 | 24시간 안에 확인한 가격 소스 / 등록된 가격 소스 |
| 최신성 충족률 | `stale`이 아닌 가격 / 확인된 가격 |
| 충돌률 | `conflicting` 가격 / 확인된 가격 |
| 단위 오류 검출 | 합성 변이 주입 테스트에서 잡은 비율 |
| 가격 변동 이벤트 수 | 일별 |

하나의 숫자로 합치지 않는다. 보험사별·상품군별·소스별 분포와 최저 수준을 함께 공개한다. 분모에 없는 가격 지점이 발견되면 분모 누락 신호로 기록한다(제3부 §57.6).

## 12. 정답 없이 검증하는 방법

사람 정답이 없으므로(제3부 §57.4) 다음을 쓴다.

- 합성 가격표: 정답이 설계상 알려진 표. 단위(원/만원), 월·연 구분, 행·열 뒤바뀜, 합계 불일치를 변이로 주입해 파이프라인이 잡는지 확인한다.
- 교차 소스 일치: 같은 조건의 협회 공시와 보험사 공시의 일치율.
- 시계열: 같은 지점의 일별 변화에서 비정상 변동 탐지.
- 표본 재추출 감사: 확인된 가격 표본을 감사 에이전트가 처음부터 다시 추출해 대조한다.
- 환류: 사용자가 올린 가입내역의 실제 보험료와 공개 가격을 비교해 괴리가 큰 상품군을 표시한다. 이는 개인 영역 데이터이므로 개별 값을 공시 데이터에 섞지 않고 집계 신호로만 쓴다.

한계: 모든 에이전트가 같은 방향으로 틀리면 감지되지 않는다(제3부 R14). 가격 화면에도 "AI 검증"으로 표기하고 근거 보기를 항상 제공한다.

## 13. 저장과 재현

- 가격 레코드는 추가만 한다. 갱신은 새 레코드와 `supersedes_id`다. 물리 삭제는 사용자 삭제 요청 처리 외에 없다.
- 시뮬레이션과 비교 결과는 사용한 `price_id` 목록과 입력 스냅샷 해시를 저장한다. 같은 입력·릴리스·계산기 버전이면 같은 결과를 낸다(제3부 §49.6).
- 잘못된 가격이 발견되면 해당 가격과 파생 결과를 추적해 중단·정정·안내한다. 이전 화면 기록은 지우지 않는다.
- 사용자 가입내역에서 나온 납입액(`contract_observed`)는 사용자 영역에만 저장한다. 공개 가격 테이블과 같은 스키마에 두지 않는다.

## 14. 개인 견적 슬롯 (스켈레톤)

- 스키마에 `quoted` 근거, 만료 시각, 견적 조건 필드가 있다.
- 입력 경로(견적서 PDF 업로드, 견적 연계 API)는 없다. 화면에서는 보이지 않는다.
- 켜는 조건: 별도 결정. 켜더라도 공개 가격과 다른 칩 모양을 쓰고 공개 가격을 덮어쓰지 않는다. 개인 견적이 있어도 가입·인수·계약 확정을 뜻하지 않는다.
- `quotes_enabled` 플래그가 꺼져 있는 동안 관련 경로는 비활성이다(제3부 §58).

## 15. 테스트 시나리오 (수락 기준)

1. 단위 변이: "12,300원"을 "12,300만원"으로 바꾼 합성 표를 잡는다.
2. 조건 누락: 가입금액 조건이 없는 가격은 `observed`가 되지 않는다.
3. 구성 분리: 주계약만 가격과 주계약+특약 가격이 한 레코드로 합쳐지지 않는다.
4. 합계 불일치: 라인의 합과 합계가 다르면 `conflicting`이다.
5. 충돌: 같은 조건에서 두 소스의 값이 다르면 둘 다 보존하고 확정하지 않는다.
6. 보간 금지: 43세 사용자에게 40세·45세 공시만 있으면 43세 가격을 만들지 않는다. 비교 기준 조건의 가격 또는 가격 미확인(조건이 달라요)만 나온다.
7. 가입금액 불일치: 비례 환산하지 않고 가격 미확인(조건이 달라요)이 나온다.
8. 미확인 노출: 가격 없는 상품이 담보 비교 목록에 나타난다.
9. 합계: 미확인 1건이 있는 보완안의 합계가 0원으로 가산되지 않고 "미포함 1건"이 나온다. 묶음 검증이 안 된 조합의 총액은 미확인이다.
10. 가격 근거: 공시 예시와 내 계약 납입액이 다른 칩 모양과 아이콘이다.
11. 기준일: 모든 가격에 기준일 또는 확인일 라벨이 붙는다.
12. 재현: 같은 입력·릴리스로 다시 계산하면 같은 가격 범위와 trace가 나온다.
13. 갱신 가정: 갱신형의 갱신 후 보험료를 확정 총액처럼 표시하지 않는다.
14. 비로그인 계산기가 개인정보를 요구하는 상품은 수집하지 않고 사유가 기록된다.
15. 광고비·수수료 필드가 가격 정렬 코드에 입력되지 않는다(정적 검사).
16. 월평균 표시: 연납÷12가 "월평균"으로만 표시되고 월납처럼 보이지 않는다.
17. 가격 기준 차이: 현재 계약 납입액과 후보 공시 예시의 기준이 다르면 절감액이 계산되지 않는다.

## 16. 열린 항목

- P2 파일럿에서 소스별 가격 공개 범위와 조건 격자를 조사한다(AI 분모 조사와 같은 방식).
- `stale` 임계값.
- `table_derived`(공개된 요율·산식·반올림·할인·구성 규칙을 모두 확보한 검증된 재현)를 허용할 상품군과 재현 검증 기준. 연령 사이 추정과 가입금액 비례 환산은 어떤 상품군에서도 허용하지 않는다(§9, PREMIUM_DATA_CONTRACT 비교·계산 규칙 2).
- 가격이 공개되지 않는 상품군의 비율을 측정한 뒤 `/coverage`에 어떻게 보여줄지 정한다.
- 개인 견적의 켜는 조건(스켈레톤).
