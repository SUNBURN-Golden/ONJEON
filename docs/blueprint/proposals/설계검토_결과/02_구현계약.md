### 1.2 주장(Assertion) 저장 형식 (C-20, C-05 통합) — [설계 담당 결정(감리 대상)]

**FieldAssertion과 관계 주장을 한 테이블 `assertion`으로 통합한다.** 속성 값 주장은 `predicate`가 속성 이름이고 `value`를 갖는다. 관계 주장은 `predicate`가 T-box 관계 ID이고 `object`를 갖는다. 근거·범위·시점·상태·정정 필드는 공통이다. 이유: K1~K13 검사가 한 집합을 본다. 릴리스가 주장 ID 집합 하나로 정의된다. 정본 FieldAssertion의 필드(raw·정규화 값, 단위, value_state, 근거, 적용 범위, 추출·검증 이력)는 모두 열로 남는다.

```text
assertion(
  id, subject, predicate, object | value{raw, normalized, unit, value_kind, amount_form},
  scope{document, sales_config, contract_kind[], component_conditions[], insured_conditions[]},
  time{valid_from, valid_to, recorded_at, observed_at, judged_as_of},
  evidence[{ref, role ∈ evidence_role}],       -- 1개 이상. basis는 약관 ClauseOccurrence만 허용
  criticality ∈ {c0,c1,c2}, value_state, review_status, hold_reason?,
  review_decision_id?,                          -- accepted이면 필수(§8)
  supersedes?, correction_reason?,
  extractor{tool, version, prompt_version?}, origin ∈ assertion_origin{pipeline, fixture},
  onto_version, created_by_run
)
```

DB 제약(스키마로 강제, I7·I12·K1·K8·§8):

| 제약 | 내용 |
|---|---|
| `chk_accepted_needs_decision` | `review_status='accepted' ⇒ review_decision_id IS NOT NULL` |
| `chk_fixture_never_accepted` | `origin='fixture' ⇒ review_status <> 'accepted'` (픽스처는 pending·hold·rejected만) |
| `chk_c0_basis` | `criticality='c0' AND review_status='accepted' ⇒ evidence에 role=basis AND 조항의 doc_role ∈ {terms, rider_terms, annex, standard_terms}`가 1개 이상(판매본-문서 대응 `uses_document`는 예외: observation 허용, K1 구현과 같음) |
| `chk_no_private_ids` | 공개 스키마의 모든 텍스트 열에 `contract:|person:|upload:|del:|consent:` 접두어 금지(트리거) |
| `chk_premium_complete` | PremiumObservation은 `conditions`, `package_binding`, `as_of`, `evidence` NOT NULL |
| `chk_supersedes_linear` | 같은 주장을 둘이 대체하면 Conflict 행이 있어야 함(지연 제약, 릴리스 빌더가 재검사) |
| `fk_evidence_clause` | `evidence.ref`가 `clause:` 또는 `premium:`이면 해당 행이 존재하고, 그 행의 DocumentVersion.sha256이 **R2 관측 목록**(archive listing)에 있어야 함 — 릴리스 빌더 검사(DB FK가 아님) |

```text
release_manifest(
  release_id, release_hash, created_at,

  extractor_versions[], model_versions[]{provider_family_label, model_ref_hash, prompt_version},  -- 모델 식별자 원문은 해시로
  engine_version, rule_schema_versions[],
  assertion_ids_hash, rule_hashes[], premium_observation_ids_hash,

  explain_template_hash,
  shadow_compare_report_id,       -- 이전 릴리스와 같은 입력 비교 결과(원인 없는 차이 0건)
```

불변(I16). 캐시 키·개인 초안·평가 결과는 모두 `release_id`를 포함한다. 철회는 `withdrawn_at` 기록 + 이전 manifest 재지정이며, 철회된 릴리스로 계산된 저장 결과는 `result_state.knowledge_freshness=withdrawn`으로 표시된다(결과 상태 네 축, §2.5).

### 1.4 개인 영역 객체 (C-11, C-12) — [설계 담당 결정(감리 대상)]

개인 계약 상태 축 다섯(토의 13~16차: 정보 출처 / 확인 여부 / 실제·가정 / 확인 주체 / 기준 시점)을 어휘 정본에 넣는 방식(D-10):

| 축 | 어휘 처리 | 값 |
|---|---|---|
| 정보 출처 | 새 축 `fact_source` | `pdf_extracted`, `user_stated`, `user_confirmed_extract`, `assumed`, `release_derived` |
| 확인 여부 | 기존 `policy_holdings_status`(계약 단위) + 필드 단위는 `value_state`·`display_status` 재사용 | 기존 값 |
| 실제·가정 | 새 축 `fact_kind` | `actual`, `hypothetical` |
| 확인 주체 | 새 축 `confirm_party` | `user`, `insurer`, `document`, `none` |
| 기준 시점 | 필드 `as_of`(날짜) + 기존 `freshness` | — |

결과 상태 네 축(토의 9차: 입력 최신성·지식 최신성·오류에 따른 사용 제한·재현 가능)은 `result_state{input_freshness ∈ freshness, knowledge_freshness ∈ {fresh, stale, withdrawn}, usage_restriction ∈ {none, hold, circuit_breaker}, reproducible: bool}`로 뷰모델 공통 필드가 된다. `knowledge_freshness.withdrawn`과 `usage_restriction` 값은 새 어휘 축이다.

```text
contract_snapshot(id, person_id, upload_id?, sales_config_ref{release_id, sc_id, match ∈ contract_version_match},
  applied_documents[{doc_id, basis_evidence, from, to}],   -- 근거로 확인한 이력만. 최신 약관 자동 적용 금지
  components[{cov_ref, insured_amount_krw, fact_source, confirm_party, as_of}],
  special_conditions[], usage_counters[], sensitivity ∈ {private_policy, private_health},
  user_confirmed_at)
consent(id, person_id, purpose ∈ {service_required, document_processing, external_ai, family_history, family_link(skeleton)}, granted_at, withdrawn_at, version)
deletion_job(id, person_id, requested_at, steps[{target ∈ {raw, extracted, index, cache, derived, external}, state, done_at}], late_writes_rejected_count)
```

### 2.3 관제 API (C-16) — 운영자·정책 소유자·읽기 역할, 2FA

`/console/v1/`: `sources`, `denominator`, `changes`, `review-queue`(검수 감사: 에이전트별 판정·근거·코드 검사·레드팀·bbox, 읽기 전용), `impact`, `releases`(후보·공개·철회·그림자 비교 보고), `quality`, `audit-log`, `policy`(임계값·서킷 브레이커 상태. 변경은 정책 소유자 역할만), `gaps`, `acquisition-tasks`(문의 초안 보기. **발송 기능 없음**), `deletion-jobs`(건수·상태만), `cost`(AI 호출·R2 원장 요약). 사용자 원본·건강정보는 어떤 관제 응답에도 없다.

### 2.4 뷰모델 (C-13) — [설계 담당 결정(감리 대상)] D-15 반영

화면 설계서 §11의 `my_design` 뷰모델과 `amounts[].source` 계약을 깨지 않는다. 다음을 더한다.

| 뷰모델 | 추가 필드 | 뜻 |
|---|---|---|
| 공통 | `result_state{input_freshness, knowledge_freshness, usage_restriction, reproducible}` | 결과 상태 네 축 |
| 공통 `amounts[]` | `source` 기존 4종(`scenario:`, `premium:`, `candidate:`, `clause:`) 유지 + `evidence_kind ∈ {terms, summary, disclosure, user_input}` + `applicability ∈ {applies, not_applies, unverified}` | 근거 종류와 "이 상황에 적용되는지"를 분리(토의 21~24차) |

| ScenarioResult | `evaluation{payout, amount, missing_inputs, rule{id, version, content_hash, release_id}, engine_version, input_snapshot_hash}`, `judgements[{input_name, value ∈ tri, judged_by, evidence_assertion_ids[]}]`, `blocked_by[]`, `remaining_gaps[]`, `explain{template_id, text, amounts[]}` | 입력 단계 근거와 규칙 근거를 분리 |
| CompareView | `columns[{sc_id, cov_id, capability_state, display_status}]`, `axes[{concept_axis, per_column{value, evidence_kind, applicability}}]`, `scope_relations[{a, b, value, derived_from}]`, `price{basis_id, comparable_columns[], unpriced_columns[]}` | 큰 금액 자리는 `scenario:` 출처만 |
| PlanView | 기존 + `diff{groups ∈ diff_group, items[{diff_type, amounts[]}]}` | I9 |
| EvidenceView | `chain[{level ∈ {viewmodel, evaluation, rule, assertion, clause, raw, source}, ref, display}]`, `quote_shown: bool(D-12 플래그)` | 사슬 끝까지 |

### 2.5 상태·화면 매핑

`display_status`(파생, 저장 안 함)는 서버가 계산해 뷰모델에 넣는다. 매핑 규칙은 계약 시험으로 고정한다(SYSTEM_CONTRACT §10).

| 서버 상태 | display_status | 화면 상태(제3부 §44.2) |
|---|---|---|
| 모든 사실에 근거 사슬 완결, capability enabled | `confirmed` | 기준 |
| `missing_inputs` 비어 있지 않음 | `input_missing` | 판단 불가(질문 1개) |
| 주장 `not_found`/`unreadable` 또는 원문 미확보 | `data_missing` | 부분("확인 필요 n건") |
| `review_status=pending` | `under_review` | 부분 |
| `hold` 또는 미해소 Conflict 또는 서킷 브레이커 | `hold` | 부분 + 계산 없음 |
| 확인된 조건상 미적용 | `not_applicable` | 기준 |
| 릴리스 철회 | (별도) `result_state.knowledge_freshness=withdrawn` | 변경됨 |

## 4. 오류 계약 (C-22, 신설)

### 4.1 미확인과 오류의 구분

| 구분 | 전달 방식 | 예 |
|---|---|---|
| **미확인·보류·판단 불가**(정상 결과) | HTTP 200 + `display_status`/`result_state`/`missing_inputs` | 코드 모름 → undetermined, 약관 미확보 → data_missing, 검수 보류 → hold |
| **오류**(요청·시스템 실패) | HTTP 4xx/5xx + `{error_class, code, message_key, retryable, trace_id}` | 잘못된 enum, 인증 실패, 릴리스 없음, 타임아웃 |

"오래 걸리는 처리의 타임아웃을 지급 불가로 바꾸지 않는다"(SYSTEM_CONTRACT §10): 타임아웃은 오류이고, 화면은 마지막 성공 결과 + 실패 사실을 보인다.

## 6. 근거 계약 (C-02 보강)

### 6.1 evidence_ref 문법

```text
evidence_ref := clause_ref | premium_ref | assertion_ref | rule_ref | obs_ref | raw_ref | eval_ref
clause_ref    := "clause:" doc_sha12 "/" path_slug "#p" page [ "@" x "," y "," w "," h ]
premium_ref   := "premium:" ulid
assertion_ref := "assertion:" ulid
rule_ref      := "rule:" rule_id "@" rule_version "#" content_hash12
obs_ref       := "obs:" source_id "/" rfc3339 "/" sha16
raw_ref       := "raw:sha256:" sha64
eval_ref      := "eval:" ulid
```

`doc_sha12`는 DocumentVersion의 원본 SHA-256 앞 12자(충돌 시 전체 길이로 확장, 릴리스 빌더가 검사). 현재 픽스처의 `hana_2601_3d#c_2_1_art1_1` 같은 ID는 **픽스처 지역 ID**이며 정식 문법이 아니다. 픽스처 적재기가 정식 형식으로 변환하되 `origin=fixture`는 유지한다.

### 6.2 사슬 끝까지

| 단계 | 포함해야 하는 참조 | 끊기면 |
|---|---|---|
| 화면 숫자·문장 | `amounts[].source`, `release_id`, `input_hash` | 사실로 표시 금지(I6). `display_status=data_missing` |
| 뷰모델 → EvaluationResult | `eval_ref` 또는 인라인 결과 + `rule_ref` | 금액 자리 비움 |
| EvaluationResult → Rule | `rule_ref`(id·판·해시) + `evidence_refs[]` + **노드별** `trace[].evidence_ref?`(R17, T-TW-05) | 노드별 근거 없으면 규칙 수준 근거로 표시하되 "조항별 설명 없음" 표시 |
| 입력 단계 판정 → 주장 | `judgements[].evidence_assertion_ids[]` | 판정값 unknown 처리 |
| Rule → 주장 | K9: 규칙 `evidence_refs ⊆` 담보 C0 accepted 주장의 basis | 릴리스 차단 |

| P6 컴파일 | twin(컴파일러) | accepted C0 주장 | Rule(`candidate`, release_id 예약, 내용 해시) + 설명 템플릿 | K9, 엔진 로더 거부(허용 목록 밖 연산·반올림 누락), 두 표현 대조 불일치 |
| P7 그림자 비교 | twin | 새·옛 릴리스 + 같은 입력 묶음 | 차이 보고(원인 연결) | 원인 없는 금액 차이 1건이라도 배포 차단 |
| P8 릴리스 | knowledge | P5~P7 보고 | ReleaseManifest(불변) + capability 표(K11) | 보고 ID 누락 시 생성 거부 |

사례 세 상품(하나·현대·롯데)이 서비스에 들어가는 길은 이 경로뿐이다. 사례 파일은 P3의 **참고 입력**(AI 추출 프롬프트의 예시)으로도 쓰지 않는다. 평가셋 누출 방지(SYSTEM_CONTRACT §13)와 같은 이유다.
