# ADR-0001 기술 스택

상태: 부분 확정 | 날짜: 2026-10-08 | 근거: 제3부 §48

## 맥락

문서 복원·AI 추출이 데이터 트랙의 중심이고, 소비자 앱·공개 웹·관제 콘솔을 한 팀이 만든다. 클라우드 공급자는 미정이다.

## 결정

| 계층 | 선택 | 상태 |
|---|---|---|
| 백엔드 API | Rust(Axum) | 확정(사용자 결정) |
| 규칙 엔진 | Rust 크레이트, 정수·유리수 연산 | 확정(백엔드 결정의 결과) |
| 수집·검증·재계산 워커 | Rust | 확정 |
| 문서 복원·OCR 워커 | Python(Docling 등), 격리 컨테이너 | 제안 |
| 모바일 | React Native(Expo) + TypeScript | 제안(최신 선택 위임, 이의 없으면 확정) |
| 웹(공개·체험판·관제) | Next.js + TypeScript | 제안 |
| DB | PostgreSQL (+pgvector) | 제안 |
| 객체 저장소 | S3 호환(로컬 MinIO) | 제안 |
| 작업 큐 | PostgreSQL 기반. 복잡해지면 Temporal | 제안 |
| 인프라 | Docker, Terraform. 클라우드 미확정 | 제안 |

## 이유

- Rust는 규칙 엔진에 맞는다. 정수 연산, 소유권에 의한 불변성, 컴파일 시점의 열거형 검사(상태 enum, 3값 논리)로 불변 원칙 3·7을 타입으로 강제하기 쉽다.
- 한국어 보험 문서의 복원·OCR 도구는 Python 쪽이 성숙하다. 그 부분만 분리하고 큐와 파일로만 통신하면 Rust 선택의 이점을 해치지 않는다.
- React Native와 Next.js는 TypeScript를 공유하여 상태 enum·API 클라이언트·체험판 코드를 재사용한다. 네이티브 컴포넌트를 쓰므로 스크린리더·큰 글씨 대응이 유리하다.

## 결과와 위험

- Rust, Python, TypeScript 세 언어를 운영한다. 공통 계약은 `packages/schemas`(JSON Schema, OpenAPI)에서 각 언어로 생성한다.
- Rust 개발자 채용과 개발 속도가 위험이다. 첫 2주 안에 API·엔진 골격을 만들어 팀 속도를 측정한다.
- 모바일 프레임워크가 Flutter로 바뀌어도 서버·엔진·웹은 영향이 없다. 화면 코드만 교체 대상이다.
