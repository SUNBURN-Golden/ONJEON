# ADR-0018 온전 보험 데이터·지식 기반의 정체성과 범위

상태: 확정(사용자 결정, 2026-10-10) | 근거: 결정 원장 D19, 토의 1번(정체성과 범위) | 구체화하는 결정: ADR-0004(대상 범위), ADR-0013(전체 대상 목록 우선), D15(개발 구역)

## 맥락

작업 순서는 잡혔지만 데이터의 정체성, 포괄 범위, 완료의 정의가 구현자 판단에 맡겨질 여지가 있었다. 정리된 데이터베이스만 만들면 시간이 지날수록 실제 상품과 달라진다. 계산하기 어렵다는 이유로 상품이 수집 대상에서 빠질 위험도 있었다.

## 결정 (사용자)

### 1. 정체성

> 온전은 전 보험상품의 정보를 지속적으로 발견·수집·보존·구조화·검증·갱신하고, 이를 설명·비교·계산에 사용할 수 있게 제공하는 독립 기반을 만든다. 소비자 앱은 그 기반을 사용하는 첫 응용 서비스다.

- 만드는 것은 보험 지식을 계속 수집하고, 검증하고, 갱신해서 쓸 수 있게 제공하는 **시스템 전체**다. 한 번 정리한 데이터베이스가 아니다.
- **온전 보험 데이터·지식 기반** = 수집·데이터 기반 + 보험 지식·온톨로지 + 디지털 트윈·계산. 소비자 응용(온전 앱)이 이를 사용한다.

| 구역 | 맡는 일 | 결과물 |
|---|---|---|
| 수집·데이터 기반 | 전 기관·상품·특약 탐색, 약관·가격 수집, 원본 보존, 문서 복원, 변경·누락 감지 | 근거와 이력이 붙은 원본·추출 데이터 |
| 보험 지식·온톨로지 | 상품·담보·질병·조건의 의미와 관계 정리, 라벨링, 검수, 버전 관리 | 검증된 보험 지식 릴리스 |
| 디지털 트윈·계산 | 상품 조건의 실행 가능한 표현, 개인 계약 조건 적용, 시나리오 계산 | 재현 가능한 조건 판정과 계산 결과 |
| 소비자 응용 | 쉬운 설명, 조건·가격 비교, 내 보험 확인, 설계·시뮬레이션 | 온전 앱 |

- **독립의 뜻은 내부 구조의 분리다.** 앱 화면을 바꾸거나 다른 내부 기능을 붙여도 수집·지식·계산 시스템을 그대로 쓸 수 있게 만든다. 내부 서비스 사이의 API는 둔다.
- **지식 기반은 온전 내부 전용이다.** 외부 개발자용 API, 데이터 판매, 공개 배포는 현재 계획에 넣지 않고 설계하지 않는다.
- 개인 계약 데이터는 별도 비공개 영역에 두고 같은 트윈 엔진을 쓴다. **공개 지식 영역에는 개인 계약 식별자를 넣지 않는다.**
- "KIX 같은 기반"은 앱과 독립적으로 작동하는 기반을 만든다는 비유다. 다른 프로젝트의 코드를 가져오거나 의존하지 않는다.

### 2. 세 가지 트윈·계산 구분

| 대상 | 표현하는 것 | 존재 조건 |
|---|---|---|
| 상품 트윈 | 특정 판매본의 약관·담보·가격 조건·관계 | 사용자가 없어도 존재한다(공개 지식 영역) |
| 개인 계약 트윈 | 그 사람이 실제 가입한 판매본, 가입금액, 특약, 가입·갱신·부활·변경 이력, 개인별 인수 조건 | 비공개 영역. 상품 트윈을 판매본·지식 릴리스로 참조만 한다 |
| 시나리오 계산 | 특정 사건과 조건을 넣었을 때 확인된 규칙이 내는 결과 | 실제 보험금 지급을 보증하는 것으로 표현하지 않는다 |

**적용 약관:** 과거 원본은 보존하고, 개인 계약에는 근거로 확인한 갱신·변경 이력을 적용한다. 최신 약관을 자동으로 적용하지 않는다. 근거가 없으면 적용 약관을 미확인으로 둔다.

### 3. 수집 기반의 범위

크롤링은 PDF를 받는 기능보다 넓다.

| 기능 | 하는 일 |
|---|---|
| 발견 | 어떤 기관에 어떤 상품·특약·판매본이 있는지 계속 찾아낸다 |
| 수집 | 약관뿐 아니라 상품요약서·사업방법서·보험료표 등 필요한 자료를 연결해서 확보한다 |
| 보존 | 당시 원본과 조회 시각을 남겨 나중에 같은 결과를 재현한다 |
| 변경 추적 | 새 상품, 개정, 판매 종료, 문서 삭제, 가격 변경을 구분한다 |
| 영향 반영 | 바뀐 자료에 연결된 라벨·규칙·트윈·화면을 찾아 재검수한다 |
| 공백 관리 | 못 받은 자료와 이유를 남기고 재수집 대상으로 관리한다 |

약관이 바뀌면 새 원본 보존 → 변경 조항 확인 → 관련 라벨·규칙 검수 → 새 릴리스 → 영향받는 화면 갱신까지 이어진다. 과거 계약에는 해당 계약의 판매본을 유지하고 새 약관을 덮어씌우지 않는다. 이를 위해 원본·조항·필드·규칙·결과의 연결을 처음부터 기록한다.

### 4. 포괄 범위

| 항목 | 이번 범위 |
|---|---|
| 보험사의 개인보험 | **포함.** 대상 상품군의 판매 중·판매 종료 상품과 특약·개정 이력까지 |
| 우체국보험 | **포함.** 보험사와 기관 유형은 구분해서 관리 |
| 공제 | **제외.** 제외 이유를 기록하고 확보율 분모에서도 제외 |
| 단체보험·퇴직연금·자동차보험 | 현재 구축 범위에서 제외, 후속 통합 |
| 지식 기반 외부 API·데이터 판매·공개 배포 | 현재 계획에 넣지 않음 |

**"전 상품"의 뜻:** 이번에 포함한 기관·상품군 안의 전 상품·전 특약·과거 판매본. 구현자가 임의로 몇 회사나 최신 상품만 수집하는 것은 허용하지 않는다. 계산이 어렵다는 이유로 상품을 수집 대상에서 빼지 않는다. "전 상품 포괄"과 "전 상품 계산 가능"은 별개 목표다. 모든 상품을 목록과 근거로 추적하고, 설명·조건 비교·가격 비교·계산은 각각 검증된 범위부터 제공한다.

### 5. 완료의 평가

아래 넷을 **따로** 평가하고 따로 보고한다. 하나가 다른 것을 대신하지 않는다.

| 축 | 묻는 것 | 주의 |
|---|---|---|
| 추적 체계 완성 | 분모(포함 범위의 전 판매본)에 대해 능력별 상태와 미확보 사유를 보고할 수 있는가 | 이것만으로 데이터 구축 완료가 아니다 |
| 실제 데이터 확보 수준 | 분모 중 원본·구조화 데이터를 실제로 확보한 비율 | 미확보 사유를 기록한 항목은 확보로 세지 않는다 |
| 검증된 기능 범위 | 설명·조건 비교·가격 비교·계산 각각이 검수를 통과한 범위 | 능력마다 따로 센다 |
| 최신성 | 마지막 수집 시도, 마지막 성공, 내용 확인, 검수·배포 시각 | 넷을 구분해 기록한다 |

미확보 사유만 쌓인 상태를 "전수 구축 완료"로 표시하지 않는다.

### 6. 개인 계약에서 발견한 누락 상품

초기에는 수집 영역으로 자동 전달하지 않는다. 회사명·상품명도 개인 계약에서 추출한 정보이고, 이름을 지웠다고 자동으로 공개 정보가 되지 않는다. 별도 동의와 최소화 기준은 후속으로 설계한다(결정 원장 O18).

## 구현자의 범위 해석 (사용자 확인 대상)

사용자 결정을 기존 대상 목록(`data/registry/`)에 적용하면서 구현자가 해석한 부분이다. 사용자가 달리 정하면 따른다.

| 대상 | 해석 | 이유 |
|---|---|---|
| 한국무역보험공사(공영보험) | 범위 밖. 제외 사유 기록 | 무역·수출 신용 등 기업 대상 정책보험이다. 개인보험 상품군이 아니다 |
| 개인연금보험(생보·손보) | 포함 | 보험사의 개인보험이다. 제외한 것은 퇴직연금이다 |
| 재보험 전업사, 보증보험 등 | 기관은 추적한다. 개인보험 대상 상품이 없으면 대상 상품 0과 그 근거를 기록한다 | 기관 목록 누락과 대상 상품 없음을 구분하려고 |
| 농협(구 공제) | 공제는 제외. NH농협생명·NH농협손해보험은 보험사로 포함 | 공제사업이 보험사로 이관된 뒤의 상품은 보험사의 개인보험이다 |

## 결과

- ADR-0004의 "국내 모든 보험사의 모든 보험"은 이 결정의 포괄 범위로 구체화된다. ADR-0004의 구축 순서 W5 중 자동차는 후속 통합으로 옮긴다.
- BLUEPRINT §12의 열린 결정 "공제·우체국보험 포함 여부"를 닫는다.
- 확보율 분모는 포함 범위(보험사의 개인보험 + 우체국보험)의 판매본이다. 공제는 분모에 넣지 않는다.
- 다음 토의(수집 기반 설계)에서 무엇을 수집할지, 빠진 것을 어떻게 찾을지, 변경을 어떻게 알아챌지를 정한다.
