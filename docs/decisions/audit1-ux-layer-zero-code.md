# Decision: P15-P19 (app, web, state catalog, user comprehension test) have no code, no Flutter or Next.js scaff

Decided by Claude Sonnet 5.5 xhigh (ONJEON autoloop, 2026-10-26 11:09 KST); revised in fix round 1 (2026-10-26) after design review; reversible.

**Decision:** Part of the finding is out of date and part still holds. Close it by recording the actual state of each part and adding one contracts task, T-CT-08, as a prerequisite of T-AP-02. Do not start new screen work.

(1) **P15 app: a scaffold exists, the data path does not.** T-MB-01 is merged (commits 7536980, a09af15). `apps/mobile/pubspec.yaml` exists, and `apps/mobile/lib/` has go_router routing for four tabs, three entry points and the `/evidence/:ref` route, the seven common state frames (`lib/states/`), design tokens, an example-mode banner and a lint that bans arithmetic on krw amounts. `apps/mobile/evidence/test.log` records a run of `flutter test` with 97 passing tests. What is still missing: there is no API integration (the generated Dart packages have types but no transport, so the app makes no calls), no feature screens (T-MB-02 to T-MB-04), and no CI step for `flutter analyze`/`flutter test` (see `apps/mobile/README.md`, "Known limits").

(2) **P16 web: no code.** `apps/web/` does not exist. T-WB-01 is an S4 task whose prerequisites (T-AP-04, T-KN-07) are not done.

(3) **P17 state catalog: frames exist, the catalog does not.** The seven frames and their rules are covered by widget tests (`apps/mobile/test/states_test.dart`). The capture catalog (every screen in each of the seven states) needs real screens and comes with T-MB-02 onward.

(4) **P19 user comprehension test: no evidence yet.** There is no `docs/ux-tests/` directory. D-16 is already decided in docs/decisions/DEC-D-16.md (2026-10-15). The ONJEON autoloop agent wrote it on the owner's behalf, and the owner can override it before the test starts. That answers "who writes the D-16 proposal". It sets six tasks U1-U6, a round 1 of 8-12 participants for finding problems, a confirmation round of 12 or more fresh participants that alone supports '이해됨', thresholds of 80% for U1/U2/U3/U5 and 90% for U4/U6, and a rule that 3 or more participants repeating the same misunderstanding fails the task. T-UX-01 (S5, after T-MB-03) must commit PREREG.md under docs/ux-tests/ before the first session, and audit1-start-gates-enforcement enforces the D-16 start gate in code.

(5) **L8 view-model contract: mostly in place, not complete.** packages/schemas/json/{plan_view,coverage_detail,evidence_view,compare_view}.schema.json exist with generated Rust, Dart and TS types, and `Amount.source` is required in common.schema.json. But `Amount.evidence_kind` and `Amount.applicability` are still optional `x-onjeon-pending-axis` strings with only a snake_case pattern. A document that leaves both out validates, and so does one with an invented value such as `invented`. So the contract does not yet force the I6 fields that T-AP-02's done criteria require (amounts[].source, evidence_kind and applicability). T-AP-02 cannot fix this itself: its allowed paths are `services/api/src/{public/coverages,public/evidence,viewmodel}/**` and it forbids `packages/schemas/vocabulary.json`.

(6) **Follow-up assigned: T-CT-08** (added to tasks.json and 03_작업명세.md; S0; prerequisites T-CT-01, T-CT-02, T-CT-03). It adds the two vocabulary axes (evidence_kind: terms, summary, disclosure, user_input; applicability: applies, not_applies, unverified, from 02 §2.4), replaces the pending strings in Amount and CompareCell with `$ref`s, makes both fields required in Amount, bumps the contract version as a breaking change, and must ship the rejection test `amount-evidence-axes-required`: an Amount with either field missing, or with a value outside the vocabulary, fails. Changing the vocabulary is a canonical change, so T-CT-08 has the same `canon_change` approval rule as T-CT-02 (BLUEPRINT §10.2, merge only after an owner instruction). T-CT-08 is now in T-AP-02's `prereq_tasks`, so the daemon cannot start T-AP-02 before the contract forces the fields. T-MB-02 depends on T-AP-02, so it also waits.

(7) **I6 evidence stays with T-AP-02's server-side contract test** ('I6 계약 시험'; a broken evidence chain gives data_missing with no amount). Once T-CT-08 is merged, that test runs against a contract that rejects amounts with no evidence kind or applicability. The mobile app only reads the generated client. Do not move I6 into the app.

`tools/tests/test_ux_layer_zero_code.py` checks this record against the repo: the scaffold claim against `apps/mobile/`, T-CT-08's ownership, its approval rule and rejection test, the T-AP-02 dependency, the matching rows in 03_작업명세.md, and the current state of the Amount schema. Until T-CT-08 lands, it asserts that missing and invented values are still accepted, so this record stays honest. After T-CT-08 lands, it asserts that both are rejected.

**Why:** The first version of this record said no P15-P19 code was expected yet and that the L8 contract was already fixed. Both statements were wrong for this head. The app scaffold is merged and tested, and the contract still accepts amounts with no evidence kind or applicability. The finding's two questions do have answers: DEC-D-16 records who decided D-16 and the numbers it set, and the view-model schemas exist ahead of the screens. But "testable I6 evidence" needs the contract to require the two fields, and no task owned that work. T-CT-08 now owns it, together with its rejection-test evidence, and T-AP-02 depends on it. Not critical: this is a reversible change to task sequencing and documentation. It involves no money, credentials, legal or production impact, and the vocabulary change itself still goes through the canonical approval gate.
