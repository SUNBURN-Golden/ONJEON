# V1-c 소비자 화면 연결 검증

2026-10-09 | 설계 검증용. 아래 화면 값은 실제 공시 문서에서 왔지만 AI 1차 해석이며 검수하지 않았다. 서비스 화면이 아니다.

## 0. 무엇을 확인했나

V1-b에서 인코딩한 같은 자료로 선택한 화면(`docs/design/assets/selected-my-plan.png`의 내 설계 탭과 담보 상세 시트)이 소비자의 세 질문에 답하는지 본다.

- 무엇을 보장하나
- 언제 못 받나
- 왜 이 가격인가

예시 인물: 40세 남자, 가입한 보험 없음(`policy_holdings_status=none_declared`), 월 예산 15만 원, 진단 보장에 "추가 검토"를 고름.

| 파일 | 내용 |
|---|---|
| `screen/my_design.real_sample.json` | 내 설계 탭 뷰모델(화면 설계서 §11 형식) |
| `screen/coverage_detail.cancer.json` | 진단 보장 상세 시트 뷰모델: 세 질문, 차이 항목, 기능 자격, 시나리오 |

모든 줄은 `refs`로 인코딩된 필드·조항·가격 관측치를 가리키고, 금액이 든 줄은 `amounts`로 금액마다 출처를 선언한다. `tools/validation_check.py`는 문구에 적힌 금액과 선언한 금액이 같은지, 가격·후보 가입금액·조항 문구 출처와 값이 같은지, 가격 칩의 나이·성별·기준일이 가격 관측치와 같은지 검사한다. `cargo test --test real_clauses`는 시나리오를 엔진으로 다시 계산해, 지급액 문구가 엔진 결과에서 생성한 금액 문구로 시작하는지와 `scenario:` 출처 금액이 엔진 값과 같은지 검사한다(`screen_payout_text_and_amounts_come_from_the_engine`, 변조 시험 `screen_check_catches_tampered_numbers`). 이 검사들은 내부 일관성 검사이며 원본 재검증이 아니다.

## 3. 세 질문에 대한 판정

| 질문 | 답이 화면에 나오는가 | 근거 | 막힌 부분 |
|---|---|---|---|
| 무엇을 보장하나 | 예. 금액·횟수·대상이 한 줄씩 | 제7조, 별표1·2, 특약 제10조 | 소액암 금액은 예시 환산(G06)이라 보류 |
| 언제 못 받나 | 예. 면책·감액·정의 제외·고의·갱신 제외가 모두 첫 층에 | 제3·9·26조, 별표1 (주), 특약 제11조 | 특약 면책은 원문 미발췌(G12), 코드 차수 충돌(G21) |
| 왜 이 가격인가 | 부분. 조건·구성·기준일·환급 구조는 나옴 | 요약서 해약환급금 예시 | 40세 남자 한 점뿐. 다른 사용자에게는 "조건이 달라 적용 불가"(G19) |

판정: 같은 자료로 세 질문이 선택한 화면 구조 안에서 답해진다. 화면 구조를 바꿀 필요는 없다. 다만 아래 §5의 문제가 드러났다.

## 4. 표시 상태 파생과 검수 뒤 바뀌는 것

| 값 상태 → 검수 상태 | display_status | 칩 문구 |
|---|---|---|
| observed·derived + pending | `under_review` | 확인 중 |
| observed·derived + accepted | `confirmed` | 조건 확인됨 |
| 아무 값 + hold(`conflicting_sources`) | `hold` | 근거가 서로 달라요 |
| 아무 값 + hold(그 밖의 사유) | `hold` | 판단 보류 |
| not_found·not_disclosed | `data_missing` | 자료 필요 |
| 사용자 입력 없음 | `input_missing` | 입력 필요 |

지금은 모든 값이 AI 1차 해석이라 C0 필드가 accepted가 아니다. 그래서 `explain`·`compare_conditions`·`compare_price`·`simulate` 모두 `blocked`다(뷰모델 `capabilities`). 서비스에서는 이 상태로 사실 문장을 내보내지 않는다. 다른 계열 AI 검수(ADR-0006)를 통과하면 "확인 중" 줄이 "조건 확인됨"으로 바뀌고 기능 자격이 열린다. "판단 보류"와 "자료 필요" 줄은 근거가 해소될 때까지 남는다.

## 5. 연결하면서 드러난 화면 설계 문제

| ID | 문제 | 처리 |
|---|---|---|
| S1 | 미해결 항목이 하나라도 있으면 `row_label=needs_condition`이 우선한다. 실제 자료에는 거의 모든 담보에 보류·자료 필요가 있어서, 시안의 세 라벨(유지·추가 검토·조건 확인)이 "조건 확인" 하나로 몰린다 | 열린 항목으로 올림(화면 설계서 §13). 후보: 지급에 영향을 주는 C0 미해결만 `needs_condition`을 띄우고 나머지는 상세 시트 칩으로 |
| S2 | 행 부제 "보장 요약 · 가장 중요한 제한"은 필드에서 만들 수 있다: "암 진단비 · 90일 면책, 1년 50%"(20자 안팎) | 규칙으로 확정: 부제의 제한은 `when_not_paid`의 첫 C0 항목 1~2개 |
| S3 | 가격 보조줄 "월 5.1만"은 51,290원을 줄인 표시다 | 비교·예산 판정은 원 단위 정확값으로, 목록 표시만 만원 소수 첫째 자리. 상세 시트는 원 단위 |
| S4 | 상세 시트 순서(화면 설계서 §4.5)에 "왜 이 가격인가" 블록이 따로 없다 | §4.5에 추가: 가격·조건·구성·환급 구조·갱신·다른 조건 상품·가격 미확인 |
| S5 | 원문이 공시한 묶음 금액(주계약+특약)과 구성원 금액을 함께 보여야 한다 | `package_binding=source_bundle`일 때만 합계 한 줄 + 구성원 줄. 임의 합산 금지는 그대로 |
| S6 | 공개 가격이 40세 남자 한 점뿐이라 다른 나이·성별 사용자에게는 대부분 "가격 미확인 · 조건이 달라 적용 불가"가 된다. 예산 슬라이더가 걸러낼 상품이 거의 없다 | 화면은 정직하게 그대로 둔다(보간 금지). 가격 격자 출처 조사(G19)를 M3의 우선 과제로 |
| S7 | 시나리오(만약에) 줄은 상세 시트에도 필요하다. 숫자는 엔진 결과만 쓴다 | 상세 시트에 "만약에" 블록. 화면 숫자 = 엔진 결과를 테스트로 강제 |
| S8 | 보험 없음 응답에서 "그대로인 것"이 비어 보인다 | "가입 보험 없음(본인 답변)"을 그 칸에 표시 |
| S9 | 첫 버전은 화면 문구의 금액을 검사하지 않았다. 지급액 문구를 9,999만원으로, 가격을 1원으로 바꿔도 통과했다(2026-10-09 리뷰) | 금액마다 출처 선언, 지급액 문구는 엔진 결과에서 생성, 가격은 가격 관측치와 대조. 변조 시험을 CI에 둠 |
| S10 | 첫 버전은 나이·성별만 같다는 이유로 "공시 예시 조건과 같다"고 적었다. 보험나이 기준·위험등급·채널은 원문에 없다 | `condition_match`로 일치·불일치·미확인을 나눠 적고 "나이·성별 일치 · 나머지 조건 미확인"으로 표시 |
