# 소비자 기능과 전체 구조 토의 자료

상태: **토의 자료. 미확정.** 2026-10-10

- 논의 순서(사용자 지정): **소비자 기능 → 전체 구조와 레이어 → 레이어 간 연결 → 세부 데이터 모델**. 이 문서는 앞의 두 단계 자료다. 레이어와 데이터 모델은 정하지 않는다.
- §1·§2는 사용자가 제시한 방향을 옮긴 것이다. §3 이후는 구현자의 분석이고 합의 전이다.
- 근거 조사: [2026-10-10 공시 출처 조사](../../research/2026-10-10_source_survey/README.md). 데이터 모델 쟁점은 [데이터 모델 토의 보완안](데이터모델_토의_보완안.md)에 보류 상태로 있다.

## 1. 온전이 돕는 판단 (사용자 제시)

> 온전은 소비자가 "왜 이 보험이 필요한지, 다른 상품과 무엇이 다른지, 어떤 상황에서 얼마나 받을 수 있는지"를 스스로 판단하게 만드는 서비스여야 한다. 약관을 쉽게 요약하는 것만으로는 부족하고, 그 내용을 자기 상황에 적용할 수 있어야 한다.

핵심 기능(사용자 제시):
1. 자기 상황에 필요한 보험과 보장을 이해한다.
2. 원하는 보장을 보험사별로 비교한다.
3. 특정 사건에서 자기 계약으로 받을 수 있는 금액과 조건을 확인한다.
4. 이 과정을 복잡한 약관을 직접 읽지 않아도 직관적으로 수행한다.

## 2. 중심 흐름과 여섯 경험 (사용자 제시)

**중심 흐름:** 내게 필요한 보장 찾기 → 같은 조건으로 상품 비교 → 사건을 넣어 작동 확인. 기존 계약이 있는 사람은 "내 보험 확인"에서 바로 들어온다.

| 경험 | 소비자에게 보이는 것 | 지켜야 할 것 |
|---|---|---|
| E1. 상품을 고르기 전에 감당하기 어려운 상황 찾기 | 짧은 질문("치료 때문에 일을 쉬면, 생활비를 얼마나 버틸 수 있나요?")에서 시작. 부양가족, 소득 중단 대비, 이미 가진 보장, 걱정하는 상황을 이어서 보험으로 보완할 부분과 스스로 감당할 수 있는 부분을 보여 준다 | 답하지 않은 정보는 미확인으로 남긴다. "지금은 추가 가입이 필요하지 않을 수 있어요"도 말할 수 있어야 한다 |
| E2. 상품보다 같은 상황에서의 차이 비교 | "이 진단을 받으면 A·B·C 상품은 각각 어떻게 처리하나요?" 첫 화면에 차이 나는 항목부터: 보장하는 범위, 지급 제한, 지급 횟수·한도, 유지 조건(갱신·종료·보험료 변화), 가격(어떤 가입 조건의 금액인가) | 공통 내용은 접는다. 종합점수로 줄 세우지 않고, 본인이 중요하게 보는 조건으로 비교한다 |
| E3. 사건을 넣으면 계산 과정까지 보여 주기(대표 기능 후보) | 필요한 정보만 차례로 묻는다. 결과를 셋으로 나눈다: 현재 입력과 확인된 약관으로 계산한 금액 / 추가 확인에 따라 달라질 수 있는 금액 / 계산에서 제외된 담보와 이유. 큰 숫자 아래 "왜 이 금액인지". 가입일·사건일을 바꾸면 면책·감액 때문에 결과가 어떻게 달라지는지 확인 | 실제 지급 확정과 약관 기반 계산을 화면에서 분명히 구별한다 |
| E4. 내 보험이 작동하는 지도 | 담보명 수십 개 대신 진단·치료·입원·회복·일을 쉬는 기간·간병 같은 생활의 흐름으로 펼친다. 상황을 누르면 관련 보장이 모이고 조건과 금액을 확인한다 | 빈칸을 곧바로 "부족"이라고 하지 않는다. 보장 없음, 자료 없음, 적용 여부 미확인을 다르게 보여 준다 |
| E5. 갈아타기 전에 얻는 것과 잃는 것 | 현재 계약과 바꿀 계약을 나란히 놓는다. "이 보장은 넓어지지만, 이 조건은 달라져요." 보험료 외에 없어지는 보장, 새 가입 조건, 면책·감액, 유지·해지 조건 | 자료가 부족하면 비교를 완성한 척하지 않고 무엇을 더 확인해야 하는지 알린다 |
| E6. 설명 검증(후속) | 설계안·설명 문구를 넣으면 약관과 대조한다. 결과는 근거로 확인됨 / 조건이 빠져 있음 / 자료로 확인할 수 없음. 상담 자리에서 물을 질문을 만들어 준다 | 사람을 평가하지 않는다 |
| 공통 | 한 번 눌러 근거 보기: 짧은 결론 → 조건 펼치기 → 정확한 원문 위치 | — |

**전체 구조에 대한 사용자 제안:** 보험 지식 기반 위에 **필요성 판단·상품 비교·사건 계산** 세 기능을 구분하고, 앱이 이를 하나의 자연스러운 흐름으로 잇는 안부터 논의한다. 필요성 판단은 약관 데이터와 계산 엔진만으로 저절로 나오지 않으므로 별도의 판단 기능이 필요하다. 지급액 계산은 확인된 계약 조건과 규칙을 정확하게 적용해야 한다. 상품 ID와 병합 규칙은 이 기능들이 요구하는 정확성과 이력 추적을 뒷받침하는 하위 설계로 다룬다.

## 3. 세 기능이 공유하는 것과 갈리는 것 (구현자 분석, 합의 전)

### 3.1 기능마다 다른 것

| | 필요성 판단 | 상품 비교 | 사건 계산 |
|---|---|---|---|
| 돕는 판단 | 내 상황에서 무엇을 대비할지, 보험으로 대비할지, 기존 보장으로 충분한지 | 같은 보장처럼 보여도 무엇이 다른지 | 내 계약의 어떤 조건이 작동하는지 |
| 대상 | 사람(상황·기존 보장·선호) | 판매 중인 상품(상품 트윈) | 내 계약(개인 계약 트윈) |
| 입력 | 가족·소득·생활비·저축·걱정하는 상황(모두 선택), 기존 계약 | 비교 기준(담보 개념 또는 사건 시나리오), 가입 조건(나이·성별 등) | 사건 사실(종류·날짜·진단·입원 등), 계약 사실 |
| 판단 근거의 성격 | **규범적 판단 기준**: 어떤 위험을 우선할지, 무엇을 스스로 감당 가능하다고 볼지. 약관에서 나오지 않는다 | 약관에서 나온 조건 필드와 가격 관측 | 약관에서 나온 실행 규칙 |
| 요구하는 정확성 | 가정과 기준이 투명하고, 바꾸면 결과가 어떻게 달라지는지 보이는 것 | **같은 조건**에서만 비교하고, 비교할 수 없으면 그렇다고 말하는 것 | 확인된 조건을 **정확히** 적용하고, 모호하면 보류하는 것 |
| 틀렸을 때의 피해 | 불필요한 가입 또는 필요한 대비를 놓침 | 다른 상품을 같다고 오해 | 받을 수 있는 돈을 놓치거나, 받을 수 없는 돈을 기대 |
| 결론의 예 | "이 상황은 기존 보장으로 대부분 덮여요", "지금은 추가 가입이 필요하지 않을 수 있어요" | "B는 유사암을 별도 담보로 나눠 20%만 줘요" | "이 조건에서 1,000만 원, 면책기간 확인에 따라 0원일 수 있어요" |

### 3.3 갈리는 지점에 대한 관찰

1. **E2("같은 상황에서의 차이")는 상품 비교 안에서 사건 계산을 쓴다.** 상품 비교와 사건 계산은 같은 엔진을 쓰고 입력이 다르다. 상품 비교는 상품 트윈에 대표 가정을, 사건 계산은 개인 계약 트윈에 개인 사실을 넣는다. 엔진을 하나로 둘지, 기능마다 둘지는 다음 단계의 질문이다(§6).
2. **필요성 판단만 약관 밖의 근거가 필요하다.** "스스로 감당할 수 있는 부분"을 말하려면 건강보험 본인부담 구조, 치료비·소득 중단 기간의 일반적 수준 같은 정보가 필요할 수 있다. **이번 조사는 이 영역을 다루지 않았다.** 출처·정확성·갱신을 따로 조사해야 한다(§5 신규 조사 후보).
3. **필요성 판단의 기준은 버전이 있는 지식이어야 한다.** 기준이 바뀌면 같은 사람에게 다른 결론이 나온다. 그래서 결론마다 어느 기준의 판으로 나왔는지 남아야 한다. 이는 약관 규칙의 릴리스와 같은 원리다.
4. **필요성 판단은 개인 정보의 폭이 넓다.** 소득·생활비·저축·부양가족은 지금 설계(가족력 선택, 예산)보다 넓다. 모두 선택 입력이고, 개인 영역에만 두며, 답하지 않은 것은 미확인으로 남긴다(사용자 제시 원칙). 동의·보존 범위는 다음 단계에서 다룬다.
5. **E4 지도의 "보장 없음"은 가장 강한 주장이다.** 계약의 판매 구성과 적용 약관이 확인되고, 그 약관 전체를 해석했을 때만 말할 수 있다. 그 밖에는 "자료 없음"이나 "적용 여부 미확인"이다.
6. **E5 갈아타기는 세 기능을 모두 쓴다.** 현재 계약(개인 계약 트윈)과 후보 상품(상품 트윈)을 같은 사건으로 계산하고, 조건 차이를 비교하고, 내 상황에 비춘다. 잃는 것 가운데는 약관 밖의 사실도 있다. 예를 들어 오래된 실손 계약은 재가입 조항이 없어 개정 약관이 적용되지 않고, 새 계약에서는 면책기간이 새로 시작된다.

### E3·사건 계산

| 필요한 정보·연결 | 조사로 본 현실 | 근거 |
|---|---|---|
| 내 계약의 판매 구성 | E1과 같은 문제. 특정되지 않으면 계산을 보류한다 | 사례 검토 |
| 가입일 기준 적용 약관 | 판매기간 안에서 약관 파일이 바뀌었거나 판매 종료 뒤 다시 쓰인 흔적이 있다(라이프플래닛 치아 2026-04~06, 삼성화재 2026-01~03 판매분). 그 기간 가입자는 판매 당시 약관을 알 수 없을 수 있다 | 사례 4·5 |
| 가입 뒤 덧씌워지는 변경 | 표준약관 소급(2009.10 이후 실손에 2019.1.1부터), 실손 재가입, 금융위 변경명령. 우체국은 개정 불적용(2차) | [F](../../research/2026-10-10_source_survey/F_history.md) §3.2, [근거 구분](../../research/2026-10-10_source_survey/근거_구분.md) §3 |
| 가입일·사건일 바꿔 보기 | 개인 계약에서는 가입일을 바꿔도 판매 구성은 바뀌지 않는다(가정 계산). 상품 비교에서 가입일을 바꾸면 다른 판매 구성·약관 판이 될 수 있다(삼성생명은 같은 이름의 판매본이 한 달 단위로 15개) | C §3.1 |
| 청구할 회사 | MG손보 → 예별손보처럼 바뀐다 | F §3.3 |
| 계산 엔진 | 규칙 엔진 v0.1, V1 표본 검증(표본 14개, 조항 142개, 필드 74개). 전 상품 계산 가능을 뜻하지 않는다 | `docs/blueprint/validation/` |

결과의 세 구분(사용자 제시)은 엔진의 3값 판정(참·거짓·미확인)과 빠진 입력 목록에 대응한다. "추가 확인에 따라 달라질 수 있는 금액"은 미확인 조건이 참일 때와 거짓일 때의 결과를 함께 보여 주는 것이다.

### E4·내 보험 지도

| 필요한 정보·연결 | 조사로 본 현실 |
|---|---|
| 담보 → 생활 흐름 단계 | 공시 자료에 없다. 지식 체계에서 만들어야 한다 |
| 보장 없음 / 자료 없음 / 적용 미확인 구분 | 자료 없음과 미확인의 원인이 조사에서 많이 나왔다: 판매 중지 상품의 요약서 없음, 약관 미확보, 판매 구성 모호, 그 기간 약관 미확인 |

### E5·갈아타기

| 필요한 정보·연결 | 조사로 본 현실 |
|---|---|
| 현재 계약과 후보 상품을 같은 사건으로 계산 | E3과 E2의 엔진을 함께 쓴다 |
| 잃는 것: 유지 시 유리한 조건 | F 조사가 직접 관련된다. 1·2세대 실손은 재가입 조항이 없어 개정 약관이 적용되지 않는다(약 47.5%, 요약 출처). 계약 전환은 6개월 안에 철회할 수 있다. 새 계약은 면책기간이 다시 시작된다 |
| 해지 관련 | 해약환급금 공시는 상품군마다 다르다(우체국 별표3, 협회 저축성). 보장성은 해약환급금 미지급형이 많다(상품명). 회사 공시는 미조사 |

### E6·설명 검증(후속)

| 필요한 정보·연결 | 조사로 본 현실 |
|---|---|
| 설명 문장 → 검증된 필드·조항 대조 | 지식 기반의 검증된 필드가 전제다 |
| 설계안의 특약 구성·보험료 → 판매 구성·가격 조건 | 판매 구성 특정과 가격 조건 문제가 그대로 온다 |
| 설계안의 개인정보 | 개인 영역에서만 다룬다 |

### 공통·한 번 눌러 근거 보기

통합약관이 수백~1,468쪽이라 문서 링크만으로는 근거를 찾을 수 없다. 쪽·조항 단위 연결이 필요하다. 판매기간·판매 상태 같은 사실은 목록 원본의 행까지 이어져야 한다. 원문 사본을 보여 줄지는 정해지지 않았다(제안서 C4).

| 후보 | 분류 | 막는 것 |

## 6. 다음 단계(전체 구조와 레이어)에서 볼 질문

1. 사용자 제안대로 "보험 지식 기반 + 필요성 판단·상품 비교·사건 계산 + 앱"으로 나눌 때, 계산 엔진은 상품 비교와 사건 계산이 함께 쓰는 하나인가, 기능마다 따로인가
2. 필요성 판단 기준은 보험 지식 기반의 일부인가, 별도의 판단 지식인가
3. 개인 계약 트윈과 개인 상황은 어디에 두고, 세 기능이 어떻게 읽는가(공개 지식 영역에 개인 식별자를 두지 않는다는 기존 결정 안에서)
4. 확인 상태(확인됨·미확인·확인 중·충돌)를 기능에서 앱까지 어떻게 전달하나
5. 세 기능이 하위 설계(상품 ID·병합·이력)에 요구하는 것:
   - 사건 계산: 정확한 판매 구성과 가입일 기준 약관 판. 정정되면 지난 계산 결과에 알린다
   - 상품 비교: 현재 판매 여부와 같은 조건. 서로 다른 상품을 합치지 않는다
   - 필요성 판단: 기존 보장이 일부 미확인이어도 진행하되 그 사실을 보인다
   - 공통: 과거 결과를 재현하고, 판단이 바뀐 이력을 남긴다
