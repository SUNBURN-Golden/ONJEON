## 인계 기준: 온전의 제품 목적 (진행 지시, 2026-10-13)

이 인계의 최상위 기준은 온전의 원래 제품 목적이다.

- **만드는 것:** 철저한 데이터 수집·관리·레이블링, 그것을 기반으로 한 수준 높은 디지털 트윈, 소비자가 쉽게 이해하는 직관적 UX/UI. 이 셋이 끝까지 연결된 **완성품**이다.
- **목적:** 보험 소비자와 공급자 사이의 정보비대칭을 줄인다. 소비자가 설계사의 설명을 검증하고, 불필요하거나 불리한 선택을 스스로 구별하게 한다.
- 이 목적은 [09_제품목적_대응표.md](../09_제품목적_대응표.md)에서 목적 → 소비자 기능 → 데이터·레이블 → 트윈 기능 → 화면 → 구현 작업 → 완료 증거 순서로 과제와 완료 기준에 연결된다. 그록봇이 다루는 과제의 완료 판정은 이 표의 완료 증거를 따른다.
- 일부 상품 시연이나 자동 개발 데몬 완성은 첫 출시 완성품이 아니다. 데몬 과제(T-OP-00·T-OP-09)는 개발 도구다.
- 미확보 사유를 기록한 것을 데이터 확보 완료로 세지 않는다. 결과를 바꾸는 조건은 숨기지 않는다. 종합점수로 정답을 대신 정하지 않는다.

## 0. 비용 정책 (사용자 결정 U-05, 2026-10-13)

- 작업당·일일·월간 비용 상한을 두지 않는다. 상한이 없다는 것은 실행 차단 사유가 아니다.
- 비용 절감을 이유로 첫 출시 범위, 데이터 확보, 정확성 검증, 독립 리뷰를 줄이지 않는다.
- 사용량·비용은 기록한다. 누적만으로 작업을 멈추지 않는다.
- 무한 재시도, 중복 실행, 응답 없는 작업은 비용과 별개로 규칙에 따라 멈춘다.
- R2 수집 정책과 외부 서비스의 권한·사용량 제한은 그대로다. 제품 완성에 확장이 필요하면 범위와 변경안을 구체적으로 제시해 사용자 결정을 받는다.

## 1. 그록봇의 역할 (사용자 결정 2026-10-12)

- 그록봇은 **전령**이다. 자기 VM의 데몬으로 다음 일을 한다.
  - 지시 봉투와 결과 봉투를 전달한다.
  - 상태를 기록한다.
  - 정해진 규칙(`daemon_rules.json`)에 따라 빌더를 부르고 인계한다.
- 제품·설계·리뷰 판단은 하지 않는다. 규칙에 없는 일은 반송 코드(R-xx)를 붙여 담당자에게 돌려보낸다.
- 역할 순서는 [daemon_rules.json](../daemon_rules.json)의 `roles`를 따른다.
  - 설계·감리: Fable(백업 GPT Astra)
  - 빌더: Sonnet → Cursor CLI(Grok 4.7) → grokbuild CLI(Grok 4.7) → Devin CLI(SWE2) → Claude Code(GLM 5.3) → 모두 쓸 수 없으면 작업을 보존하고 대기
  - 리뷰: 작성한 계열을 제외한다
  - 감리: 병합 10개마다 한 번, 그리고 즉시 감리 대상

**[상태 기록 2026-10-26] 직렬 제한 해제** ([audit1-serial-daemon-prerequisite](../../../../decisions/audit1-serial-daemon-prerequisite.md), 되돌릴 수 있음). 위 문단의 "제품 과제는 임대하지 않는다"는 단계 2·3 기간에만 적용했다. 그 기간은 끝났고, 이 기록이 그 제한을 대체한다.
- 실제 진행 순서: 단계 2 T-OP-00 병합(#21, 2026-10-15; 후속 T-OP-00b #97, 2026-10-16) → 단계 3 T-OP-09 병합(#98, 2026-10-16) → T-TW-02(#105, 2026-10-16), T-OP-01(#101, 2026-10-16), T-CT-01(#102, 2026-10-17).
- T-OP-09는 R1~R22 중 PASS 17, PARTIAL 5, FAIL 0으로 닫혔다([RESULTS.md](../../../../vm_check/2026-10-16/RESULTS.md)). PARTIAL인 R6·R7(claude 외 CLI 미확인), R9·R11·R21(빌더가 벤더 CLI가 아닌 대역 스크립트)과 명세 공백 G51~G57, 일부만 해소된 G47은 **남은 데몬 후속 과제**다. 해소된 것으로 적지 않는다.
- 05 §7 가동 전 점검표의 서명 기록은 없다. 미확인으로 기록하며, 단계 4 칸의 규칙대로 차단 사유로 쓰지 않는다.
- 남은 데몬 후속 과제는 제품 과제를 막지 않는다. 데몬 작업과 제품 과제는 병행한다. 예외는 출시 전 최종 감리 T-OP-08(final_gate) 하나다. 이 과제는 데몬 운영 기록(모의·실제 실행기 검증 보고서)을 축 5에 공개해야 하므로 T-OP-00·T-OP-09를 선행으로 둔다. 다른 제품 과제는 tasks.json에서 T-OP-00·T-OP-09를 선행으로 두지 않는다(`tools/tests/test_pr_policy.py`의 `SerialDaemonPrerequisite`가 검사).
- 다시 직렬로 돌리는 조건: PARTIAL 시나리오(R9·R11·R21)가 실제 자동 개발 운영에서 늦은 쓰기·중복 실행·작업 유실로 나타나면 고칠 때까지 제품 과제 임대를 멈춘다.

## 5. 사용자가 정하거나 준비할 것

**가동 전에 필요한 것(단계 4의 조건):**
- 운영 수치(05 §3) 기본값 확인: 임대 TTL 3600초, 하트비트 300초, 동시 임대 2, 정지 확인 window_s 5초, 인계 실패 재시도 한도(사건별 3/3/0/2/3/1). **비용 상한은 두지 않는다**(사용자 결정 U-05, 2026-10-13). 이 수치들은 비용 통제가 아니라 고장·무한 반복 통제다
- 모델 계열 해석: Fable과 Sonnet을 같은 claude 계열로 볼지. 리뷰에서 제외할 계열이 이 해석으로 정해진다.
- VM 준비(사람): 보호 브랜치, 데몬 보존 전용 자격(preserve_credential), 빌더별 단기 쓰기 자격, 작업 트리 쓰기 금지 격리 방법, 자동 병합 끄기.
- GPT Astra(설계·감리 백업) 경로: 확인하거나 "미확인"으로 기록.

**가동을 막지 않는 것:**
- A-01(정본 문구) 정본 반영
- D-08 범위
- K17 후보
- R2 토큰 폐기(T-OP-04 등 R2 단계만 막음)

## 6. 독립 리뷰 경로

이 세션의 설계 담당(Fable), 빌더(Sonnet), 구현자는 모두 claude 계열이다. 그래서 지금까지는 작성 계열 밖의 리뷰가 없었다. VM에서 Grok 4.7(Cursor CLI·grokbuild)이나 SWE2가 "확인됨"이 되면 claude 계열이 작성한 PR을 그 계열이 리뷰할 수 있다. 이것이 처음으로 생기는 독립 리뷰 경로다. 단계 0에서 이 경로를 먼저 확인한다.

## 7. 멈추는 조건 (그록봇이 판단하지 않고 멈추는 경우)

- 규칙에 없는 조건이 생기면 → 반송(return_codes).
- 비밀값 패턴이 검출되면 → 즉시 중단(R-10).
- 같은 실패가 재시도 한도를 넘거나, 중복 실행이 감지되거나, 작업이 응답하지 않으면 → 정해진 규칙에 따라 멈추고 원인을 해결한다. **비용 누적만으로는 멈추지 않는다**(U-05). 사용량·비용은 기록한다.
- 상태가 손상되면 → 반송(R-08). 사람이 해소 기록을 남기기 전에는 재개하지 않는다.
- 인계 실패가 재시도 한도를 넘으면 → handoff_blocked. 사람의 복구 결정을 기다린다.

## 8. 아직 확인되지 않은 것

[상태 기록 2026-10-26] 아래 목록은 2026-10-13 인계 시점의 상태다. 그 뒤 T-OP-00(#21)과 T-OP-09(#98)가 병합됐다. 남은 항목은 §3 상태 기록에 적는다.

- 모의 코어는 필수 시험 ID 33개 중 16개만 구현됐다. 명세 공백 G29~G50은 명세에서 해소됐지만(07 §1f) 모의 코어가 아직 읽지 않는 필드가 있다(`spec_gaps.py`의 `core_reads`가 no·partly인 항목). 범위는 §9에 적는다.

- 코어는 표준 라이브러리만 쓴다.
- I/O는 어댑터 인터페이스(`tools/daemon/core/ports.py`)로 분리했고, 모의 어댑터만 있다.
- 코어는 `core_contract.reads`에 적힌 구조화 필드만 읽는다. 목록에 없는 경로를 읽으려 하면 시작할 때 멈춘다. 자연어 `when`·`note`는 읽지 않으며, AST 검사와 설명 키 변경 검사가 이를 확인한다.

**규칙 변형 검사**
- 빌더 시험(약 30종)과 구현자의 별도 반증 검사 둘 다 했다.
- 구현자가 바꾼 규칙과 결과:

| 바꾼 규칙 | 결과 |

| handoff_sequence에서 preserve와 revoke_token 순서 바꿈 | M29·M33 실패 |

| 동시 임대 2 → 1 | M30 실패 |

- 시나리오는 max_wall_s 값을 규칙에서 읽어 시험한다. 그래서 기본값을 크게 바꿔도 통과한다. 상대 시험이며 실패가 정상이 아니다.
- 규칙 파일에 비용 상한 필드를 넣는 것은 모의 코어가 아니라 spec_check G46이 막는다.

**명세 공백 현황(`tools/daemon/spec_gaps.py`, 07 §1e 대비)**
- 설계 담당의 7차 수정으로 G01~G28 중 22건이 필드로 해소됐다. 6건(G11, G12, G16, G18, G20, G21)은 일부만 해소됐다.
- 코어를 맞추는 과정에서 새 공백 G29~G50이 기록됐다. 코어는 이를 추측으로 채우지 않았고, 좁게 해석한 내용을 `core_took`에 적었다. 주요 항목은 다음과 같다.
  - 임대 수 세기의 범위(G29)
  - recovery_decision과 restart_resume의 일부 단계가 문장이다(G30·G31)
  - switch_policy가 읽기 목록에 없다(G32)
  - `unmapped_condition` 반송이 임대를 끝내지 않는다(G37)
  - 인계 중 비밀값 검출을 받는 전이가 없다(G38)
  - 결과 봉투의 중복 전달이 "늦은 봉투"로 분류된다(G40)
  - cancelled void를 만드는 규칙이 없다(G41)
  - usage_record의 append-only와 슬롯 갱신이 모순된다(G46)
  - limits 기본값이 읽기 목록 밖이다(G47)
  - M32 검증 규칙(G49)
  - hard_stop 트리거와 사건 이름의 대응이 없다(G50)
- 설계 담당이 G29~G50 22건을 모두 구조화 필드로 해소했다(07 §1f). `spec_gaps.py`는 이 22건을 "해소(필드)"로 표시하고, 모의 코어가 그 필드를 지금 읽는지(`core_reads`)와 빌더가 바꿀 것(`core_change`)을 같이 적는다. 이 상태는 명세에 대한 것이고 코어 동작의 증명이 아니다. G11·G12·G16·G18·G20·G21은 여전히 "일부 해소"다(남은 부분은 코어가 새 필드를 읽어야 닫힌다).
- §3 단계 2의 첫 일은 빌더가 코어를 새 필드에 맞추는 것이다. 그 뒤 나머지 시나리오를 구현한다. 그록봇은 공백을 해석하지 않고 담당자에게 돌려보낸다.

**이 모의 검증이 증명하지 않는 것**
- 실제 프로세스, 파일 시스템(잠금·rename·fsync), Git·원격 푸시, 네트워크, CLI, 모델 호출. 모의 Git의 tree 해시는 모델일 뿐이다.
- 다중 프로세스 경쟁(스레드와 잠금으로만 시험)
- 실제 제공자 청구와 사용량 기록의 대조. 프록시를 거치지 않는 호출은 기록할 수 없다(`not_meterable`)
- 리뷰·감리 흐름과 구현하지 않은 시나리오

모두 단계 2·3(T-OP-00 완성, T-OP-09)에서 확인한다.
