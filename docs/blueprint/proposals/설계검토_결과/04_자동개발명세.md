## 2. 상태 기계

### 2.1 상태

| 상태 | 뜻 |
|---|---|
| `blocked` | 선행 과제가 `post_merge_states`에 없거나 `decision_gates.start` 미결 |
| `queued` | 실행 가능 |
| `leased` | 임대(lease_id, **fencing_token**, TTL). 쓰기 전 |
| `building` | 격리 작업 트리에서 쓰는 중. 하트비트 필요 |
| `handoff` | 전환 신호 감지. 쓰기 중단·보존 중(이전 토큰 폐기) |
| `paused_no_builder` | 모든 빌더 불가. 작업 보존 후 대기 |
| `pr_open` → `ci_failed` / `review_pending` | PR 열림 → CI 결과 |
| `review_in_progress` → `changes_requested` / `review_approved` | 리뷰(대상 SHA 고정) |
| `audit_pending` | 즉시 감리 대상, 병합 전 감리 대기 |
| `merge_wait` | 사람 병합 대기. `reason ∈ {ready, reviewer_unavailable, auditor_unavailable, decision_pending}` |
| `merged` → `audit_queued` → `done` | 사람이 병합 → 정기 감리 묶음 → 종료 |
| `returned` | 반송(return_code). **담당자가 해소를 기록하면(`owner_resolved`) queued로 재개** |
| `cancelled` | 담당자 취소 |

**병합 뒤 상태(병합 뒤 상태와 선행 조건 대응):** `post_merge_states = [merged, audit_queued, done]`. 선행 과제 충족은 `state in post_merge_states`로 판정한다. 이미 완료된(done) 선행도 충족이다.

### 2.2 사건과 전이

모든 전이는 `event`를 갖는다(`events` 목록 36개). 핵심 전이:

| from → to | event | 조건(기계) |
|---|---|---|
| blocked → queued | `prereqs_satisfied` | 모든 선행이 `post_merge_states`에 있고 `decision_gates.start ⊆ decisions_recorded` |
| queued → leased | `lease_granted` | 빌더 가용, 충돌 경로 임대 없음, 잠금, `fencing_token = last+1` |
| leased → building / queued | `first_heartbeat` / `lease_expired` | 첫 하트비트 / 없으면 토큰 폐기·프로세스 종료·자격 회수 후 큐로 |
| building → handoff | `switch_signal` | 허용 출처의 신호만(§3) |
| building → returned | `result_out_of_scope`(R-01) / `result_verdict_requested`(R-02) / `heartbeat_missed_twice` / `fence_violation`(R-11) / `secret_detected`(R-10) / `budget_exhausted`(R-07) / `result_failed_tests` 3회(R-06) | — |
| building → building | `result_failed_tests` | 같은 작성자 재임대(새 토큰). 전환 아님 |
| handoff → leased / paused_no_builder | `preserved` / `no_builder` | WIP 커밋 푸시(현재 토큰) + 인계 기록 + 토큰 폐기 뒤 |
| pr_open → ci_failed → building | `ci_failed` → `lease_granted` | 같은 작성자 |
| review_pending → review_in_progress / merge_wait | `reviewer_assigned` / `reviewer_unavailable` | 작성 계열 밖 리뷰어 유무 |
| **merge_wait → review_pending** | `reviewer_available` | 리뷰어 복귀 → 리뷰 재개 |
| review_in_progress / review_approved / audit_pending / **merge_wait** → review_pending | `head_sha_changed` | 코드가 바뀌면 진행 중·완료된 리뷰·감리 결과 무효(R-04 기록), 변경분 재리뷰 |
| review_approved → audit_pending / merge_wait(ready) / merge_wait(decision_pending) | `audit_required` / `audit_not_required` / `decision_pending` | 즉시 감리 판정 → `decision_gates.merge ⊆ decisions_recorded` 여부 |
| audit_pending → merge_wait(ready / decision_pending) / changes_requested / merge_wait(auditor_unavailable) | `audit_pass` / `decision_pending` / `audit_changes_requested` / `auditor_unavailable` | 감리 결과(SHA 일치) |
| **merge_wait → audit_pending** | `auditor_available` | 감리 담당 복귀 → 감리 재개 |
| **merge_wait → merge_wait** | `decision_recorded` | `decision_pending` → `ready` 사유 갱신 |
| merge_wait → merged | `pr_merged_observed` | 사람 병합 관측. 데몬은 병합하지 않는다. `reason != ready`였으면 R-12 기록 |
| merged → audit_queued / done | `impl_counter_incremented` | 구현 PR은 카운터 +1 / docs-only는 done |
| audit_queued → done | `batch_audit_pass` | 정기 감리 기록(지적은 새 수정 과제) |
| **returned → queued / cancelled** | `owner_resolved` / `owner_cancelled` | 담당자 해소 기록 → attempt+1, 새 토큰 |
| * → returned | `unmapped_condition` | 표에 없는 모든 조건 |

### 2.3 결정 관문(결정 차단: 설명과 기계 규칙 대응)

과제마다 `decision_gates{start[], merge[]}`가 있다. **시작 전이(blocked → queued)는 `start`만 본다. 병합 대기 전이(→ merge_wait)는 `merge`만 본다.** `merge` 미결이면 `merge_wait(decision_pending)`에서 기다리고, 결정 기록이 오면(`decision_recorded`) `ready`로 바뀐다. README 차단 범위표는 tasks.json의 `decision_gates`에서 생성한다. 검증 상태: 명세됨 → T-OP-00 시험 `decision-gate-merge-only` → T-OP-09.

## 3. 빌더 순서와 전환 조건 (모델 전환 신호 대응)

전환은 **사용량 제한·서비스 가용성** 문제일 때만 한다(운영 규칙 1). 신호는 **빌더 CLI 자신의 모델 호출 상태 채널**만 본다. 자식 프로세스 출력, 시험 로그, 수집 대상 사이트 응답, 저장소 API 응답은 보지 않는다. 각 신호의 `detect`는 `{source, match, scope}` 구조다.

| 신호 | source | match | scope |
|---|---|---|---|
| `usage_limit` | `provider_http_response` | 429, 또는 제공자가 문서화한 할당량 오류 유형 | `model_provider` |
| | `runner_exit_code` | CLI별 확인표(05 §1b)에 기록된 한도 종료 코드만 | `runner_self` |
| `auth_failure` | `provider_http_response` | 401/403 | `model_provider` |
| | `runner_auth_probe` | 인증 상태 명령이 미인증·만료 보고 | `runner_self` |
| `service_unavailable` | `provider_http_response` | ≥500 또는 연결 오류 3회 연속 | `model_provider` |
| | `runner_exit_code` | CLI별 확인표의 불가 종료 코드만 | `runner_self` |
| `runner_missing` | `runner_version_probe` | 명령 없음 또는 버전 프로브 비정상 종료 | `runner_self` |

허용 출처는 네 가지뿐이다: `provider_http_response`(scope는 반드시 `model_provider`), `runner_exit_code`, `runner_auth_probe`, `runner_version_probe`. CLI별 종료 코드·구조화 오류의 확인 방법은 05 §1b에 두고, **미확인이면 그 CLI의 `runner_profile`은 비어 있어** HTTP 응답·인증 프로브·버전 프로브로만 전환한다. 금지 사유: 시험 실패, CI 실패, 리뷰·감리 지적, 품질 불만, 느린 진행, 자식 프로세스 stderr 문자열, 수집 대상 사이트 HTTP 오류, 저장소 API 오류. 검증 상태: 명세됨 → T-OP-00 `provider-scoped-switch` → T-OP-09(실제 CLI의 상태 채널 확인).

전환 절차: 쓰기 중단 확인·현재 토큰 폐기 예약 → WIP 커밋을 현재 토큰으로 푸시 → 토큰 폐기·프로세스 그룹 종료·임대별 쓰기 자격 회수 → 인계 기록 → 다음 빌더가 같은 브랜치·같은 SHA에서 **새 토큰**으로 시작 → `authors_families` 갱신. 마지막 빌더까지 실패하면 `paused_no_builder`. 몰래 대체 없음.

## 4. 독립 리뷰 배정

```text
candidates = builders 순서
for c in candidates:
    if c.family in pr.authors_families: continue   # 작성 참여 계열 제외(운영 규칙 2)
    if c.available: assign(c); break
else: state = merge_wait(reviewer_unavailable)      # 복귀 시 reviewer_available 사건으로 review_pending
```

리뷰 결과는 `sha`를 가진다. `pr.head_sha`와 다르면 무효(R-04 기록, `head_sha_changed`). 계열표는 daemon_rules.json `roles.families`. Fable·Sonnet 같은 계열 해석은 사용자 확인 전까지 더 엄격한 쪽을 쓴다. 그 결과 이 환경에서 확인된 경로(claude 계열)만으로는 Sonnet 작성 PR의 리뷰어가 없고 모든 PR이 `merge_wait(reviewer_unavailable)`에 머문다. 병합만 막고 작성·시험·설계는 막지 않는다.

## 6. 봉투 형식

- 지시 봉투 필수: `envelope_id, task_id, attempt, lease_id, fencing_token, builder, runner, branch, base_sha, worktree, allowed_paths, forbidden_paths, inputs, tests, done_criteria, deadline_heartbeat_s, budget, reply_to`. 빌더 규칙 6줄(허용 경로 밖 금지, 정본 금지, 비밀값 금지, 판단은 반송, 병합 금지, **푸시는 데몬을 통해 토큰과 함께**).
- 결과 봉투 필수: `envelope_id, task_id, attempt, lease_id, fencing_token, builder, runner, status, branch, head_sha, touched_paths, tests_run, test_log_ref, signals_seen, cost_units, calls, wall_s`. 수락 조건: `fencing_token == current_token(task_id)`. 아니면 R-11.
- 리뷰·감리 결과: `sha` 필수. 결정 기록: `decision_id, recorded_at, recorded_by, source_ref`(데몬은 ID 존재만 본다).

| 검사 시점 | 푸시, PR 갱신, 결과 봉투 수락, 인계 보존. 토큰이 현재 값과 다르면 거부(R-11) | 같음 |

| 푸시 경로 | 빌더는 원격에 직접 푸시하지 못한다. 데몬이 토큰 검사 뒤 푸시(임대별 단기 자격, 종료 시 회수). 보호 브랜치가 빌더 계정의 직접 푸시를 막는다 | 명세됨 → T-OP-09(저장소 설정은 사람이 함) |
| 임대 종료 | 만료·전환·반송 시 프로세스 그룹 종료, 쓰기 자격 회수, 토큰 폐기, 인계 기록 | 명세됨 → T-OP-00(모의 종료 신호) → T-OP-09(실제 프로세스) |

**주의:** 위 표의 어떤 행도 "차단된다"를 증명하지 않는다. T-OP-00은 데몬 규칙(토큰 비교·거부 경로)만, T-OP-09는 실제 CLI 프로세스와 저장소에서 교체 전후 동시 쓰기가 0건인지를 검증한다. 보호 브랜치·단기 자격은 저장소·호스트 설정이며 사람이 적용하고 T-OP-09가 확인한다.

## 11. PR #2 AIOPS 인계안과 다른 점

중앙 AIOPS를 재가동하지 않는다. 데몬은 판단 주체가 아니라 전령이다. 자동 병합 권한이 없다. 역할·전환 정책은 U-04가 정했고 이 문서는 그것을 기계 규칙으로 옮겼을 뿐이다.
