# 데이터 모델 토의 보완안 (보류 중)

상태: **토의 자료. 미확정. 보류.** 2026-10-10

- 사용자 검토(PR #4, c79a9a5)에서 나온 지적 네 가지와 그에 대한 보완 방향, 그리고 사례 하나를 끝까지 따라간 기록이다.
- **원칙, 상품 후보의 형태, 판매 구성 구분 기준은 확정하지 않았다.** 사용자가 논의 순서를 "소비자 기능 → 전체 구조와 레이어 → 레이어 간 연결 → 세부 데이터 모델"로 바꿨다. 이 문서는 세부 데이터 모델 단계에서 다시 연다.
- 이 문서는 [수집·지식 기반 설계 제안](수집_지식기반_설계_제안.md) P2.1·P2.3·P2.4·P2.7과 [사례 검토](사례_표현_검토.md) §A·§B의 일부와 충돌한다. 충돌하는 부분은 두 문서에 표시만 했고, 내용은 아직 고치지 않았다.

## 1. 사용자 지적(요약)

| 번호 | 지적 | 충돌한 곳 |
|---|---|---|
| 1 | 원본 파일과 약관 판을 다시 같은 것으로 취급한다. 통합약관 파일 하나에 주계약·특약 수백 개가 들고, 재압축하면 해시가 바뀐다 | 제안서 P2.4(약관 판 ID = 원본 SHA-256) |
| 2 | 미확인 상품을 만드는 규칙이 문서마다 다르다. 어느 출처에서 발견했든 상품 후보로 추적해야 한다 | 제안서 P2.1(`unlinked`), 사례 검토 §B(보조 출처는 판매 구성을 만들지 못함), 사례 3·4(행마다 생성) |
| 3 | 문서가 같다는 이유로 상품을 합치는 시험이 남아 있다 | 사례 검토 §B 수락 시험("약관 해시가 같으면 same_as 승인") |
| 4 | 잘못 합친 것을 되돌릴 때 기존 ID를 복원해야 한다. 처음부터 오인한 경우와 이미 있던 둘을 잘못 병합한 경우는 절차가 달라야 한다. `distinct_from`도 정정 가능한 판단이어야 한다 | 사례 검토 §A 되돌림 절차 2·3 |

## 2. 원칙 (사용자 제안 문구, 합의 전)

> 출처가 보여 준 사실은 그대로 보존하고, 우리가 내린 동일성·적용 관계 판단은 별도로 기록한다. 판단이 바뀌어도 원래 개체와 과거 결과를 잃지 않는다.

이 원칙을 지키기 위한 따름 규칙(구현자 보완 제안, 합의 전):

1. 개체는 지우거나 다시 번호를 매기지 않는다. 병합은 개체를 바꾸는 일이 아니라 "같다"는 판단 하나를 더하는 일이다.
2. 관측과 참조는 처음 연결된 개체 ID에 건다. 병합된 대표 ID에 걸지 않는다. 대표 ID는 판단들로부터 계산한다.
3. 판단은 고치지 않고 덧쌓는다. 정정하면 기존 판단은 "대체됨"이 되고 새 판단이 추가된다. `distinct_from`도 같다.
4. 릴리스는 그 시점의 판단 집합을 고정한다. 과거 릴리스로 다시 실행하면 당시 결과가 나온다.

## 3. 지적별 보완 방향 (합의 전)

### 3.1 원본 파일과 약관 판의 구분

| 대상 | 무엇을 식별하나 | 정하는 방법 | 성격 |
|---|---|---|---|
| 원본 파일 | 받은 바이트 | SHA-256 | 관측 |
| 문서 구획 | 파일의 어느 부분(쪽, 조항 경로)이 어떤 약관·특약인가 | 원본 해시 + 범위 + 구획 규칙의 판 | 판단 |
| 약관 판 | 어떤 내용과 적용 범위를 가진 판인가 | 내부 발급 ID. 근거는 정규화한 본문 지문(정규화 규칙의 판 포함), 제목, 개정 표기 | 판단 |
| 약관 계열 | 같은 약관·특약의 여러 판 | 내부 발급 ID | 판단 |
| 적용 관계 | 그 판이 어느 판매 구성·종·형·심사 유형·기간에 적용되나 | 근거·상태가 붙은 주장 | 판단 |

- 바이트가 같으면 같은 판이다. 반대는 성립하지 않는다(재압축본은 원본이 달라도 같은 판일 수 있다). 본문 비교도 정규화가 차이를 숨길 수 있으므로 판이 같다는 결론은 판단이다.
- 메트라이프처럼 통합약관 안의 특약과 특약 탭의 별도 파일은 원본 둘의 구획 둘이 같은 판을 담은 경우다.

### 3.2 상품 후보

- 출처 행은 하나도 빠짐없이 어떤 대상에 연결된다: 기존 판매 구성, 기존 상품 후보, 새 상품 후보. `unlinked` 상태는 두지 않는다.
- 어느 출처든 상품 후보를 만들 수 있다. 출처마다 다른 것은 생성 권한이 아니라 근거의 무게다.
- 출처 행과 판매 구성의 단위가 다를 수 있다(채널 병기 행, 심사 유형별 행, 담보 단위로 펼친 행). 그래서 `same_as` 외에 `covers`(행 하나가 여러 판매 구성을 덮음), `part_of`(행이 판매 구성의 일부)가 필요할 수 있다.
- 열린 쟁점: (가) 후보를 판매 구성과 같은 유형에 "후보" 상태로 둔다(ID 유지). (나) 별도 유형으로 두고 정규 개체에 연결한다(단위가 다른 출처를 담기 쉬움).

### 3.3 판매 구성 동일성의 조건

사례 검토 §B의 수락 시험("약관 해시가 같으면 same_as 승인")은 철회 대상이다. 문서 동일성은 근거 하나일 뿐, 필요조건도 충분조건도 아니다. 동일성 승인 조건 후보:

1. 판매 기관이 같다.
2. 판매기간이 같거나 차이가 설명된다.
3. 구별 속성(코드, 채널, 종·형, 심사 유형, 범주)에 차이가 없거나, 출처가 같은 대상이라고 밝힌 근거가 있다.
4. 약관·사업방법서·요약서를 모두 비교했고, 차이가 있으면 "같은 대상 안의 교체"라는 근거가 있다.
5. 반대 근거(예: 협회의 별도 공시행)가 없다.

이 조건은 "판매 구성이란 무엇인가"(제안서 C8)에 달려 있다. 심사 유형이 다르면 다른 판매 구성인지, 같은 판매 구성 안의 변형인지가 먼저 정해져야 한다.

### 3.4 되돌림

| 상황 | 되돌리는 방법 | ID |
|---|---|---|
| 이미 있던 A와 B를 잘못 병합 | 병합 판단을 "대체됨"으로 | B를 원래 ID로 복원 |
| 처음부터 여러 대상을 하나(A)로 오인해 생성(예: 교보 코드 1000649로 1983년·2026년 상품을 한 계열로) | A를 나눈다. A의 생성 근거(어느 출처 행에서 만들었나)에 맞는 쪽이 A를 유지 | 나머지는 새 ID(ID가 없던 대상) |
| 개체는 맞는데 출처 행을 엉뚱한 개체에 연결 | 연결만 고친다. 올바른 개체가 없으면 새 후보 | 개체 ID는 그대로 |

`distinct_from`은 같은 근거로 다시 제안하는 것만 막는다. 새 근거가 생기면 다시 검토한다.

**아래 표의 회차 날짜와 "잘못된 승인"은 가정이다.** 행 값과 등록 시각은 원본 값이다.

| 단계 | 관측(보존) | 판단(기록) | 그 시점의 해석 |
|---|---|---|---|
| ① 첫 발견(가정 회차 08-10) | 회사 행 LO-5(08-07 등록, 사업방법서 `e8d156f9…`, 요약서 있음). 협회 행 `N09PB144455`, `N09PB144456` | LO-5 → 판매 구성 SO-α. 협회 두 행 → 상품 후보 PC-1, PC-2. PC-1·PC-2와 SO-α의 관계는 제안 상태 | 판매 구성 1, 후보 2. 모두 지식 기반 안에 있다 |
| ② 중복 의심(가정 회차 09-10) | 회사 행 LO-6(09-07 등록, 같은 이름·개시일, 사업방법서 `8766985f…`, 요약서 없음) | 출처 키(UUID)가 달라 기존 개체에 붙지 않음 → SO-β. `same_as(SO-α, SO-β)` 제안, 중복 후보 | 판매 구성 2(중복 후보 쌍) |
| ③ 동일성 승인(가정, 잘못된 승인) | 두 약관 바이트가 같다고 가정 | 이름 + 약관 해시로 `same_as` 승인 → SO-β는 SO-α의 별칭. LO-6의 연결은 여전히 SO-β | 릴리스 R3에서 1개로 보임. 이 기간의 개인 계약 매칭은 "병합된 SO-α"로 기록 |
| ④ 잘못된 승인 발견 | 같은 시점에 약관은 같은데 사업방법서 바인딩이 둘 → 불변식 위반. 협회 별도 공시행 둘이 반대 근거 | 두 사업방법서 비교 → 건강고지Ⅰ과 일반심사로 확인됐다고 가정 | 오류 확인 |
| ⑤ 복원 | 관측은 그대로 | `same_as`를 "대체됨"으로. `distinct_from(SO-α, SO-β)` 기록(근거: 사업방법서 차이, 협회 두 행). PC-1·PC-2를 SO-α·SO-β에 각각 연결 제안 | 릴리스 R4에서 2개. SO-β는 원래 ID로 복원 |
| ⑥ 영향 정리 | — | R3는 "정정됨"으로 표시하되 내용은 그대로. R3 기간에 병합된 SO-α로 매칭된 개인 계약은 "SO-α/SO-β 재확인 필요"(비공개 영역) | 과거는 R3로 재현, 현재는 R4 |

드러난 것:
- ③은 §3.3 조건 4·5를 지키면 승인 전에 막힌다(사업방법서 차이와 협회 별도 행이 이미 보였다).
- ⑥이 깔끔하려면 개인 계약 매칭이 병합 대표가 아니라 사용자가 확인한 원래 개체(SO-α 또는 SO-β)를 기록해야 한다.

## 5. 데이터 모델 단계에서 정할 것(보류)

1. 원칙 문구와 따름 규칙 네 개
2. 상품 후보의 형태((가)/(나))와 `covers`·`part_of` 연결
3. 심사 유형·종·채널 차이가 판매 구성을 나누는 기준인지, 같은 판매 구성 안의 변형인지(제안서 C8)
