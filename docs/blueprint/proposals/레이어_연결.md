# 레이어 간 연결과 갈아타기 검증 (토의용)

상태: **토의 자료. 미확정.** 2026-10-10 | 바탕: [소비자 기능과 전체 구조 토의 자료](소비자_기능_필요정보.md) §3.8(책임 영역, 사용자 제시), [흐름 따라가기: 암 보장](흐름_따라가기_암보장.md) §5

- 순서(사용자 지정): 레이어 간 연결을 먼저 설계하고, 갈아타기 흐름으로 그 연결을 검증한다.
- 연결은 세 흐름(지식 생산 / 소비자 요청 / 변경·정정)으로 나누어 본다. 연결마다 다섯 질문에 답한다: **무엇을 전달하나 / 누가 쓸 수 있나 / 어떤 판을 쓰나 / 실패하거나 모르면 어떻게 답하나 / 바뀌면 누가 다시 확인하나.** API 이름과 필드 형식은 정하지 않는다.
- §1은 사용자가 이번에 제시한 원칙이다. §2 이후는 구현자 초안이고 합의 전이다.

## 1. 이번 토의의 원칙 (사용자 제시)

| 흐름 | 연결 | 지켜야 할 것 |
|---|---|---|
| 지식 생산 | 수집 → 문서 복원 → 의미 추출·검수 → 지식 릴리스 | 새로 수집했다고 곧바로 서비스에 반영하지 않는다 |
| 소비자 요청 | 화면·대화 → 서비스 조합 → 지식·개인 영역·판단·계산 → 결과 | 한 요청에서 사용한 입력과 판을 고정한다 |
| 변경·정정 | 새 지식 릴리스 → 개인 영역의 영향 확인 → 재검토·재계산 → 사용자 안내 | 과거 결과를 보존하고, 무엇 때문에 달라졌는지 설명한다 |

5차 의견을 더 정확히 한 네 가지:

1. **개인 영역은 하나의 판이 아니라 여러 기록을 묶은 상태다.** 증권 추가, 소득 수정, 상품 연결 정정은 서로 다른 변화다. 계약 사실·개인 상황·상품 연결 판단을 따로 판 관리하고, 계산할 때 쓴 조합을 고정한다. 소득을 고쳤다고 약관 연결까지 다시 할 필요는 없다.
2. **새 지식 릴리스를 받았다고 개인 계약을 최신 약관에 자동으로 연결하지 않는다.** 새 릴리스는 "우리가 아는 내용이 바뀌었다"는 뜻이지 "그 사람의 계약 조건이 바뀌었다"는 뜻이 아니다. 개인 영역은 변경 목록을 받아 자기 계약에 관련된 정정인지 확인하고, 확인된 범위에서만 연결과 결과를 고친다.
3. **개인별 특별조건의 뜻이 공통 지식에 이미 있다고 가정하지 않는다.** 공통 지식은 알려진 조건의 해석 방법을 준다. 개별 계약에만 있는 문구는 개인 영역 안에서 근거와 해석 상태를 보관한다. 공통 유형에 맞지 않는 조건을 억지로 끼워 넣지 않는다.
4. **계산 엔진의 비저장 원칙은 요청 로그·오류 기록·캐시까지 포함한다.** 엔진 코드를 공유하는 것과 개인 입력을 공개 상품 계산 환경으로 보내는 것은 별개다.

| 기록 | 예 | 바뀌면 다시 해야 하는 것 |
|---|---|---|
| 계약 사실 | 증권에서 읽고 사용자가 확인한 회사·상품명·가입일·담보·가입금액·납입 상태 | 상품 연결 판단, 그 계약을 쓴 계산 |

| 개인 상황 | 가족, 소득 공백 대비, 걱정하는 상황(모두 선택) | 필요성 분석만 |
| 선호 | 사용자가 중요하다고 확인한 조건 | 비교의 정렬과 "사용자가 중요하게 보는 조건"만 |
| 동의 | 기능별 사용 동의와 범위 | 그 범위 밖 사용 중단 |
| 저장된 결과 | 결과와 그 요청의 고정 묶음, 결과가 쓴 공통 지식의 대상 ID 목록 | — (보존) |

## 3. 흐름별 연결

### 3.1 지식 생산

| 연결 | 무엇을 전달하나 | 누가 쓸 수 있나 | 어떤 판 | 실패·모름 | 바뀌면 누가 확인하나 |
|---|---|---|---|---|---|
| L1 수집 → 원본 보관 | 원본 바이트, 관측 기록(요청·시각·상태·해시) | 수집기만 추가. 덮어쓰기·삭제 없음 | 원본 해시, 어댑터 판 | 실패·차단·형식 불일치도 관측으로 남긴다. 성공과 구분 | 변경 감지가 지식 생산 대기열에 올린다(서비스 반영 아님) |
| L2 원본 → 문서 복원 | 추출 텍스트·표·좌표·구획 | 복원 워커가 파생 저장소에만 추가 | 추출기 판 | 불확실하면 보류 표시 | 추출기 판이 바뀌면 재생성과 재현 검사 |
| L3 복원 → 의미 추출·검수 | 후보 필드·조항·관계, 동일성·대응 판단 후보와 근거 | 추출 AI는 후보만 쓴다. 승인은 검수(교차 AI·코드 검사·사람) | 라벨 사전·모델·프롬프트·규칙 판 | 미확인·충돌·보류는 후보 상태로 남는다 | 원문이 바뀌면 영향 범위를 재검수 |
| L4 검수 → 지식 릴리스 | 불변 릴리스(사실·판단·근거·확인 상태·실행 규칙)와 **이전 릴리스 대비 변경 목록** | 릴리스 승인 주체만. 릴리스는 고치지 않음 | 지식 릴리스 | 출시 검사를 못 넘으면 릴리스 없음(이전 릴리스 유지) | 철회·정정도 새 릴리스와 변경 목록으로 |
| L5 판단 기준 작성 → 판단 기준 판 | 기준·참고 자료·기본 가정, 근거 | 판단 기준 관리 주체만 | 판단 기준 판 | 참고 자료가 없으면 그 기준을 "근거 없음"으로 두고 쓰지 않음 | 새 판과 변경 목록 |

**서비스는 릴리스된 지식과 판단 기준만 읽는다.** 수집·복원·검수 중인 것은 서비스에서 보이지 않는다(§1 원칙).

### 3.2 소비자 요청

| 연결 | 무엇을 전달하나 | 누가 쓸 수 있나 | 어떤 판 | 실패·모름 | 바뀌면 누가 확인하나 |
|---|---|---|---|---|---|
| Q1 화면·대화 → 서비스 조합 | 사용자 요청: 의도, 사용자가 확인한 사실·선호의 변경 | 화면은 개인 기록에 직접 쓰지 않는다. AI가 구조화한 사실·선호는 **사용자 확인 뒤에만** 개인 영역에 쓰인다 | — | 해석이 불확실하면 되묻는다 | — |
| Q2 서비스 조합: 요청 고정 | 이 요청에 쓸 판의 조합: 지식 릴리스, 판단 기준 판, 엔진 판, 개인 기록 유형별 판 | 서비스 조합 | 전부 | 판이 서로 맞지 않으면(예: 상품 연결 판단이 지금 쓰는 릴리스와 다른 릴리스에서 만들어짐) 결과를 내지 않고 "다시 확인 필요"로 답한다 | — |
| Q3 서비스 조합 ↔ 개인 영역 | 목적별 최소 정보. 비교에는 가격 조건에 필요한 나이·성별 등, 계산에는 계약 표현, 필요성 분석에는 상황 요약 | 읽기는 동의 범위 안에서 목적을 밝혀서. 쓰기는 사용자 확인 사실·선호와 결과 저장만 | 개인 기록 유형별 판 | 입력이 없거나 동의가 없으면 "미입력" "동의 없음"(오류가 아님) | — |
| Q4 서비스 조합 → 공통 지식 | 상품·조건·가격·대응·후보, 확인 상태 | 읽기 전용 | 고정한 지식 릴리스 | 대상 없음 / 미확인 / 충돌을 정상 결과와 구분 | — |
| Q5 서비스 조합 → 계산 엔진 | 계산 요청: 규칙(지식 릴리스 안), 계약 표현(개인 계약 또는 상품 + 명시한 가정), 사건 입력, 여러 계약의 관계 계산 여부. **입력마다 성격(확인된 실제 / 명시한 가정)을 함께** | 엔진은 상태를 갖지 않는다. 개인 입력은 개인 영역의 실행 환경에서만 처리하고, 요청 로그·오류 기록·캐시에도 남기지 않는다(§1-4) | 엔진 판, 규칙 판 | 금액·3값·계산 과정·빠진 입력. 계산할 수 없으면 "규칙 미지원" "관계 미지원". **0원과 미지원을 구분** | — |
| Q6 서비스 조합 → 필요성·비교 기능 | 지식 조회 결과, 계산 결과, 최소 개인 정보, 판단 기준(판), 선호 | 기능은 읽기만. 지식·개인 기록을 고치지 않는다 | 고정 묶음 | 결과 구조의 불확실성·범위에 담는다 | — |
| Q7 서비스 조합 → 화면·대화 | 결과 구조 + 조건의 성격(근거별) + 범위 + 고정 묶음 + 판 혼합 검사 결과 | 화면·AI는 결과에 없는 숫자·기간·예외·조건을 만들지 않는다 | 고정 묶음 | 미확인·미지원·충돌을 사용자 언어로 보이되 정상 결과처럼 보이지 않는다 | — |
| Q8 서비스 조합 → 개인 영역(결과 저장) | 결과, 고정 묶음, **결과가 쓴 공통 지식의 대상 ID 목록** | 서비스 조합 | — | — | 변경·정정 흐름이 이 목록으로 영향을 찾는다 |

### 3.3 변경·정정

| 연결 | 무엇을 전달하나 | 누가 쓸 수 있나 | 어떤 판 | 실패·모름 | 바뀌면 누가 확인하나 |
|---|---|---|---|---|---|
| C1 지식 릴리스 → 변경 목록 공개 | 바뀐 대상 ID와 바뀐 내용의 종류(사실 정정, 동일성 판단 변경, 약관 판 연결 변경, 철회)와 사유. **개인 정보 없음** | 지식 릴리스 주체 | 이전·새 릴리스 | — | — |
| C2 개인 영역: 영향 확인 | 변경 목록 × 개인 영역의 상품 연결 판단·저장된 결과의 대상 ID 목록 | 개인 영역이 스스로 한다(공통 지식은 누구의 계약이 영향을 받는지 모른다) | 개인 기록 판, 새 릴리스 | 관련 없음 → 아무것도 하지 않음. 관련 있음 → "재검토 필요" 표시. 사용자 사실이 필요하면 질문 대기(예: 연결 후보가 둘로 나뉨) | 개인 영역 |
| C3 재검토·재계산 | 확인된 범위에서만 상품 연결 판단의 새 판, 새 결과 | 개인 영역(연결), 서비스 조합(재계산 요청) | 새 고정 묶음 | 확인할 수 없으면 기존 연결을 유지하되 "새 정보로 재확인 필요" | — |
| C4 사용자 안내 | 결과가 달라졌거나 확인이 필요할 때만. 무엇 때문에 달라졌는지(어느 변경 항목) | 서비스 조합 → 화면 | 이전·새 고정 묶음 | — | — |
| C5 판단 기준 판 변경 | 필요성 분석 결과에만 영향 | 판단 기준 관리 → 개인 영역(저장된 필요성 결과가 쓴 판과 대조) | 판단 기준 판 | — | 개인 영역 |
| C6 개인 기록 변경 | §2 표의 "바뀌면 다시 해야 하는 것"만 다시 한다 | 개인 영역 | 해당 기록 유형의 새 판 | — | 개인 영역 |

**C2·C3의 원칙(§1-2):** 새 릴리스가 나왔다는 이유로 계약을 최신 약관에 다시 잇지 않는다. 바뀐 것이 "그 계약에 적용되는 사실에 대한 우리의 앎"일 때만, 확인된 범위에서 고친다. 과거 결과는 지우지 않고, 새 결과와 나란히 남는다.

## 4. 연결에서 드러난 확인 사항

1. **변경 목록은 개인 정보 없이도 충분히 구체적이어야 한다.** 개인 영역이 자기 기록과 대조할 수 있도록 바뀐 대상 ID 단위로 나와야 한다. 이는 [데이터 모델 토의 보완안](데이터모델_토의_보완안.md)의 "판단은 원래 개체 ID에 걸고 대표는 계산한다"와 맞물린다.
2. **저장된 결과마다 "쓴 대상 ID 목록"이 있어야 C2가 가능하다.** 없으면 새 릴리스마다 모든 결과를 다시 계산해야 한다.
3. **여러 단계의 대화에서 요청 고정을 얼마나 유지하나.** 대화 도중 새 릴리스가 나오면, 그 대화는 처음 고정을 유지하고 "더 새로운 정보가 있어요"를 알릴지가 화면 흐름의 질문이다.
4. **특별조건의 해석 상태가 미확인이면, 그 조건이 걸린 담보의 계산은 "특별조건 해석 미확인"으로 멈춘다.** 다른 담보는 계산한다.
5. **개인 정보 삭제 요청은 개인 영역의 기록·결과를 지운다.** 공개 쪽에는 지울 것이 없다(공개 쪽에 개인 정보가 없으므로). 재현 보존보다 삭제가 우선한다는 기존 원칙(SYSTEM_CONTRACT §5)과 같다.

## 5. 갈아타기로 검증하기

흐름(사용자 제시): 내 현재 계약을 확인한다 → 새 상품과 비교한다 → 얻고 잃는 보장을 본다 → 신규 가입 조건과 가격의 미확인을 확인한다 → 유지·추가·전환·보류를 판단한다.

검증 초점(사용자 제시): **기존 계약의 확인된 보장과 새 상품의 가정상 보장을 똑같이 확정된 것처럼 비교하지 않는가.**

### 5.1 단계별 연결

| 단계 | 쓰는 연결 | 이 단계에서 확인되는 것 / 가정인 것 |
|---|---|---|
| ① 현재 계약 확인 | Q3(계약 사실·특별조건·상품 연결 판단), Q4(약관 판·적용 시간 변화), Q5(실제 입력으로 계산) | **확인 수준이 항목마다 다르다.** 계약 사실은 사용자 확인됨, 상품 연결은 확인/후보/미확인, 특별조건은 해석됨/미확인 |
| ② 새 상품과 비교 | Q4(판매 중인 상품의 조건·가격·대응 항목), Q5(같은 사건을 새 상품에 명시한 가정으로 계산) | 새 상품의 조건은 **약관상 조건**이다. 가입 승인, 적용될 심사 유형, 적용될 가격, 붙을 특별조건은 모두 **가정**이다 |
| ③ 얻고 잃는 보장 | Q6(비교 기능), Q5(기존 계약 + 새 상품의 여러 계약 계산) | 비교 항목마다 양쪽의 확인 수준을 따로 붙인다. 잃는 것에는 약관 비교만으로는 보이지 않는 것이 있다(아래 5.2) |
| ④ 신규 가입 조건·가격의 미확인 | Q4(공시 가격의 조건), Q3(나이·성별) | 공시 가격은 대표 조건의 금액이다. 본인 적용 여부, 인수 심사 결과는 확인할 수 없다 |
| ⑤ 유지·추가·전환·보류 | Q6(필요성·비교 기능), Q7 | 기준선은 **현재 계약**이다. 선택지마다 무엇이 확정이고 무엇이 가정인지가 따라붙는다 |

### 5.2 잃는 것 가운데 약관 비교만으로는 안 보이는 것

조사에서 나온 것만 적는다.

| 잃을 수 있는 것 | 어디서 아나 | 근거 |
|---|---|---|
| 기존 계약에 이미 지난 면책·감액 기간 | 기존 계약의 가입일(개인 계약 사실) + 기존 약관 / 새 계약은 새 가입일(가정)부터 다시 시작 | 계산 엔진에 가입일을 입력으로 줌 |
| 재가입 조항이 없는 오래된 실손 계약의 조건 고정 | 기존 계약의 세대(지식) | F 조사: 1세대·초기 2세대 실손은 재가입 조항이 없어 개정 약관이 적용되지 않음(금융위 보도자료, 요약 등급) |
| 실손 전환 뒤 되돌리기 | 전환 철회 조건(지식) | F 조사: 4·5세대 전환은 6개월 안 철회 가능(요약 등급) |
| 해지 시 돌려받는 돈 | 기존 계약의 해약환급금(개인 사실, 증권·해약환급금 예시표) | 공시 해약환급금은 상품군마다 다르고 보장성은 미지급형이 많다(E·상품명). 개인 값은 공통 지식에 없다 |

### 5.3 검증 결과

| 확인 | 결과 | 필요한 보완 |
|---|---|---|
| 기존 확인 보장과 신규 가정 보장을 같은 확정으로 보이지 않는가 | Q5가 입력마다 "확인된 실제 / 명시한 가정"을 받고, 결과가 그 성격을 그대로 돌려주면 지켜진다 | 결과 구조의 비교 항목마다 **양쪽의 확인 수준과 가정 목록**이 붙어야 한다. 지금 공통 결과 구조(기준선·후보·…)에는 이 칸이 명시되어 있지 않다 |
| 기존 + 신규를 함께 계산하는가(추가 가입) | Q5의 여러 계약 관계 계산(G4)으로 처리. 미지원이면 "관계 미지원" | 엔진 v0.1은 실손 비례분담을 표현하지 못한다(GAP_REPORT) |
| 잃는 것을 놓치지 않는가 | 해약환급금처럼 개인 값이 필요한 것이 개인 기록 유형에 없다 | 개인 영역의 계약 사실에 **계약 가치(해약환급금·납입 상태)**를 넣을지, 별도 기록으로 둘지 |
| 기존 상품과 새 상품의 비교 항목 대응 | 기존 계약은 판매 중지 상품일 수 있다. 대응 판단이 판매 중 상품끼리만 있으면 비교가 안 된다 | 공통 지식의 비교 항목 대응이 **판매 중지 상품의 약관 판**까지 다뤄야 한다 |
| 전환의 순서 위험 | 새 계약 승인 전에 기존 계약을 해지하면 보장 공백이 생길 수 있다. 이것은 추천이 아니라 확인할 사실이다 | 조건의 성격 중 "적용을 막는 조건"(새 계약 승인 전)으로 다음 행동에 연결 |
| 나중에 새 상품 약관이 정정되면 | 저장된 갈아타기 결과의 대상 ID 목록(Q8)으로 C2가 찾아 안내 | §4-2 |
| 사용자가 소득만 고치면 | C6: 필요성 분석만 다시 | — |
| 사용자가 이미 갈아탔다면 | 기존 계약이 "해지됨"으로 계약 사실의 변경 이력에 남는다 | 변경 이력에 해지·전환을 넣는다 |

### 5.4 검증에서 나온 보완 후보 (합의 전)

1. 결과 구조의 비교 항목마다 **양쪽의 확인 수준과 가정 목록**
2. 개인 영역에 **계약 가치(해약환급금·납입 상태)** 기록
3. 공통 지식의 비교 항목 대응이 **판매 중지 상품**까지
4. 전환의 순서 위험을 조건(적용을 막는 조건)과 다음 행동으로 연결
5. 계약 사실의 변경 이력에 **해지·전환** 포함
