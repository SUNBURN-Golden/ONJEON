## 4. 이 검사들이 증명하는 것과 증명하지 않는 것

| 검사 | 종류 | 증명하는 것 | 증명하지 않는 것 |
|---|---|---|---|
| 온톨로지 I1~I7, D1~D7, K1~K16 변이 | 동작 검증(실행해서 결과 비교) | 사례 세 상품 범위에서 다음 성질이 성립한다: 릴리스 불변(새 주장·새 판·참조 노드 교체 뒤에도 결과·설명이 같다), 재현과 사용 제한의 분리, 판의 구성과 지문의 역할, 정정 이력 | 약관 해석의 정확도(미검수, 사례 가정 승인), 서비스 구현, 보통약관 정의 구획, 사업방법서에 따른 적용 범위 차이 |
| spec_check 기계 검사 | 명세 정합성 계산(그래프·경로·전이표) | 작업 그래프의 선후, 경로 권한, 최종 관문의 덮는 범위, 데몬 전이표의 형식 요건 | 실제 데몬·실행기의 동작, 명세의 제품 의미 |
| spec_check 존재 검사 | 필드·문구의 유무 | 요구한 필드·시험 ID·문서 칸이 있다 | 그 내용이 맞는지 |
| 엔진 시험(cargo test) | 동작 검증 | 기존 rule-0.1 엔진의 의미론 | 새 설계 묶음 |

특히 다음은 **검증되지 않았다**.
- 데몬 안전장치(펜싱, 격리, 쓰기 자격 회수, 전환 신호 검증, 예산 예약, 강제 종료)는 "명세됨" 또는 "모의 검증 대상" 상태다. 모의 도구(T-OP-00)와 실제 실행기 검증(T-OP-09)은 아직 없다. "이전 CLI의 쓰기가 차단된다"는 증명되지 않았다.
- CLI별 종료 코드와 제공자 오류 채널(05 §1b)은 전부 확인하지 못했다.
- 판단 기준 관리, 부분 보류, 사용 제한 공지의 제품 의미는 사람이 검토해야 한다.

## 5. 검토 요청 범위

1. 원본 F01~F12 각각에서 07의 대응(변경 위치, 검증 증거, 미검증)이 지적의 수락 기준을 충족하는가.
2. 07의 A-01~A-04와 검토서 본문 항목의 처리가 맞는가.
3. 08 요구추적표가 원구상의 완성품 범위를 빠짐없이 담는가. 완료 가능한 일부 경로를 전체로 바꾼 곳이 없는가.
4. 판단 기준 관리(F11)가 사용자 결정(2026-10-12)의 범위와 일치하는가. 설계 승인과 서비스 적용 승인이 분리되어 있는가.
5. spec_check.py 자체가 지적을 제대로 검사하는가. 검사기도 구현자(claude 계열)가 썼으므로 검토 대상이다.
