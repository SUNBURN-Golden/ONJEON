## 0. 이번 요청의 진행 지시(사용자)

- 첫 구현 목표는 일부 상품의 연결이나 부분 기능 시연이 아니라 **첫 출시 범위의 완성품**이다.
- 설계 통합안에 전체 소비자 기능과 데이터·운영 기반을 모두 포함하고, 완성품까지의 구현 계획과 완료 기준을 작성한다.
- **상품 하나를 끝까지 연결하는 작업은 내부 검증 단계로 배치**한다. 이 작업을 납품 목표나 출시 범위로 바꾸지 않는다.
- 개발은 내부적으로 나눠 진행한다. 다만 최종 전달물에는 화면·API·지식·엔진·개인 영역·운영이 실제로 연결돼 있어야 한다. 시안용 숫자, 미연결 버튼, 임시 데이터로 완성됐다고 보고하지 않는다.
- 기능 완성, 실제 데이터 확보, 계산 검증, 사용자 이해, 운영 준비를 **각각** 평가한다. 남은 공백과 그 영향은 공개한다.
- 원구상의 기능을 구현 편의 때문에 임의로 후속으로 미루지 않는다.

이 지시는 정본의 단일 출시 결정(ADR-0007, 제3부 §43.2)과 같은 방향이다. 정본도 "MVP·베타·기능별 단계 공개는 없다"고 정했다. 내부 단계는 "공개 MVP나 시장 범위 축소가 아니다"(SYSTEM_CONTRACT §2).

## 0.2 진행 지시(사용자): 온톨로지 (2026-10-12)

- 온톨로지를 보험 지식 기반의 **명시적인 설계 대상**으로 포함한다. 개념 목록뿐 아니라 관계의 의미, 적용 범위와 시점, 근거, 미확인·충돌, 정정 이력, 일관성 제약을 정의한다.

### 2.9 디지털 트윈의 활용 범위 (U-02 반영)

디지털 트윈은 정본 정의대로 "L5 상품 모델과 개인 계약 모델을 L6 규칙으로 실행해, 사용자가 고른 가정에서 무엇이 지급되고 무엇이 막히는지 재현하는 것"이다(BLUEPRINT §4). 보험사의 인수·지급 결정을 복제하지 않는다. U-02에 따라 트윈은 계산 화면 하나가 아니라 아래 기능 전체의 공통 실행 경로가 된다.

| 기능 | 트윈이 하는 일 | 트윈 결과가 없을 때 남는 것 |
|---|---|---|
| 만약에(가상 탐색) | 상품 트윈 + 명시한 가정 → 지급·불지급·판단 불가, 면책·감액 경계일 | 조건 설명 |
| 같은 담보·같은 상황 비교 | 같은 사건을 여러 상품 트윈에 넣어 결과와 근거를 나란히 보인다 | 조건 비교(compare_conditions) |
| 담보 상세의 "만약에 줄" | 사용자가 고른 날짜·조건으로 계산한 한 줄 | 보장·제외 설명 |
| 내 보험(홈·계약 상세) | 개인 계약 트윈(적용 약관 이력·특약·가입금액) 위에서 상황별로 계산 | 계약 요약과 원문 |
| 실제 사건 확인 | 개인 계약 트윈 + 사용자가 확인한 사실 → 조건부 계산, 결과를 바꾸는 미확인과 확인 주체 | 다음에 확인할 것 |
| 두 안 비교·갈아타기 | 현재 계약 트윈과 보완안 트윈에 같은 사건을 넣어 얻는 것과 잃는 것(면책 재시작·감액·제외·종료)을 계산 | 조건 차이 목록 |
| 여러 계약 | 정액 중복, 실손 비례분담, 계약 간 지급 관계 | 계약별 결과(합산하지 않음) |
| 변경 영향 | 새 릴리스와 이전 릴리스에 같은 입력을 넣어 차이를 찾는 그림자 비교, 영향받는 저장 결과 표시 | — |

**적극 활용의 경계:** 계산 자격(capability `simulate`)이 승인된 담보에서만 트윈 결과를 보인다. 승인되지 않은 담보는 "아직 계산하지 않아요"와 함께 확인된 설명·조건 비교를 보인다(ADR-0004 §3, 제3부 §43.2). 적극 활용은 트윈이 다룰 수 있는 범위(W1~W6 연산, 여러 계약, 입력 단계)를 넓히는 것이다. 승인 없이 결과를 켜는 것이 아니다.

## 3. 통합 구조

### 3.1 계층과 구역

정본의 L0~L9(BLUEPRINT §4)와 구역(D15: data / knowledge / twin / app / contracts)을 뼈대로 둔다. 토의 자료의 영역 A~H, X(전체 구조 1차 정리)를 그 위에 얹으면 아래와 같다.

| 정본 계층 | 구역 | 토의 영역 | 대응 관계 |
|---|---|---|---|
| L0 소스 원장·분모, L1 수집, L2 복원 | data | A 공개 자료 기반 | 같음 |
| L3 추출, L4 AI 검수, L5 정규 모델, L7 릴리스 | knowledge | B 공통 보험 지식(변경 목록·오류 격리 공지 포함) | 토의가 변경 목록·오류 격리 공지를 지식 쪽 출력으로 명시 |
| (없음) | (없음) | C 판단 기준 관리(필요성 기준·참고 자료·가정의 판) | **정본에 대응 계층 없음.** 정본은 "필요한 돈 기본값 출처"(O05)만 미정으로 둠(§4 X-04) |
| L6 규칙 컴파일·엔진 | twin | D 계산 엔진 | 같음. 토의는 여러 계약 관계와 계산 전 호환 검사를 명시 |
| 개인 영역 | app(비공개 처리 모듈) | E 비공개 개인 영역 | 같은 방향. 토의는 개인정보를 쓰는 **요청 전체**를 경계 안에 둠 |

| (각 계층의 AI 게이트웨이) | — | X 외부 AI 처리 | 같은 방향. 보낼 정보와 보존 조건은 미정(O08) |

[검토 의견(구현자)] C(판단 기준 관리)는 정본에 없는 새 영역이다. 이 영역 없이 E1(필요성 판단)을 만들면 근거 없는 기본값이 생긴다. 이것은 정본이 금지한 일이다(O05, BLUEPRINT §2 "근거 없는 충족률"). 영역을 두지 않기로 하면, 정본대로 "사용자 직접 가정만, 기본 필요액 없음"으로 구현해야 한다.

[검토 의견(구현자)] 온톨로지(§0.2)는 knowledge 구역의 L5 정규 모델에 해당한다. 정본 L5는 객체 목록만 두고 관계의 의미·범위·시점·제약은 정하지 않았다. 온톨로지는 그 빈 곳을 채운다. 엔진(twin)은 실행 중에 온톨로지를 조회하지 않는다. 입력 단계가 릴리스된 온톨로지로 코드 소속·시점을 판정해서 그 결과와 근거 주장을 엔진 입력으로 넘긴다(ADR-0014 §4, D15). 책임 경계 전체는 [온톨로지 설계안 §11](온톨로지/온톨로지_설계안.md#11-책임-경계)에 있다.

### 3.2 근거 사슬과 표시 원칙

정본의 근거 사슬(BLUEPRINT §5.2)을 유지한다. 화면 숫자 → 뷰모델(release_id·input_hash) → EvaluationResult → Rule → FieldAssertion → ClauseOccurrence → RawAsset → SourceRegistry 순서다. 사슬이 끊긴 정보는 사실로 나가지 않는다(I6).

토의 21~24차의 비교 시안에서 정리된 표시 원칙(토의상 제안·사용자)은 이 사슬 위의 표현 규칙이다.
- 큰 금액 자리에는 명시한 가정에서 약관으로 계산한 결과만 올린다. 공시 문구로 한 산술 예시는 근거 안에 둔다.
- 출처 종류(공시·요약서·약관)와 "이 상황에 적용되는지"를 따로 표시한다.
- 확인 필요 상품도 같은 목록·같은 자리에 둔다. 자료 부족을 상품의 단점처럼 보이게 하지 않는다.
- 감액 같은 규칙은 시점이 바뀌어도 남기고, 적용 여부만 바꾼다. 기준일을 확인한 경우에만 "해당 없음"이라고 쓴다.
- 보험료는 조건이 같을 때만 직접 비교하고, 견적이 아님을 표시한다.

[검토 의견(구현자)] 이 원칙은 정본 I6·I7·I8·불변 원칙 3·9와 충돌하지 않는다. 오히려 정본의 display_status·capability를 화면에서 어떻게 읽히게 할지를 구체화한다. 뷰모델 계약(화면 설계서 §11)에 "근거 종류"와 "적용 확인" 필드를 더하는 것으로 반영할 수 있다.

### 4.1 이번에 정정한 내 작업의 정본 충돌

[검토 의견(구현자)] 24차 비교 시안은 롯데손보의 상품요약서 조건(보장 개시 90일, 1회한, 1년 미만 50%)을 "확인된 조건"으로 표시했다. ADR-0014 §1은 "실행 규칙의 C0 근거는 약관이다. 상품요약서는 교차 검증과 쉬운 문장에만 쓴다"고 정한다. 이 표시는 그 규칙과 충돌했다. 그래서 이번 커밋에서 "요약서에 적힌 조건(약관과 대조 전)"으로 바꿨다. 이 부분은 이번 차수의 사실 정정에 해당한다.

## 9. 자동 개발 역할과 운영 규칙 (사용자 결정 U-04, 2026-10-12)

전문과 실행 절차는 [자동 개발 설정안](자동개발_설정안/README.md)에 있다. 요약하면 다음과 같다.
- **설계·구현 계약과 감리:** Fable(백업 GPT Astra)
- **빌더:** Sonnet → Cursor CLI–Grok 4.7 → grokbuild CLI–Grok 4.7 → Devin CLI–SWE2 → Claude Code–GLM 5.3 → 작업 보존 후 대기
- **독립 리뷰:** 빌더 순서에서 작성 계열을 뺀다
- **감리 시점:** 병합 구현 PR 10개마다. 개인정보 경계·계산 의미·공통 계약·릴리스 구조를 바꾸는 PR은 즉시 감리한다
- **백업 전환 사유:** 사용량 제한·서비스 장애일 때만 전환한다
- **자동 병합:** 없다
- **코드 리뷰와 약관 검수:** 별개다. 개발 역할표는 약관 검수 모델 구성의 승인이 아니다

**이 결정이 설계에 주는 영향(검토 의견·구현자).** §8.3의 구현자 선택 항목은 이제 설계 담당 Fable이 정하고 감리받는다. 지식 검수 모델 구성(D-02)은 이 역할표로 정해지지 않는다(운영 규칙 7).
