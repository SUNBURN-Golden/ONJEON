이 문서는 사용자가 결정한 역할 구성과 운영 규칙을 실행 설정의 형태로 옮긴 안이다. 실행기·스케줄러·CI·자동 병합 어디에도 연결하지 않았다.
- PR #2의 AIOPS 인계안을 채택하는 문서가 아니다. 중앙 AIOPS를 재가동하지도 않는다.

- 기계가 읽는 형태의 같은 내용은 [roles.draft.json](roles.draft.json)에 있다.

## 2. 운영 규칙 (사용자 결정, 2026-10-12)

1. 백업 전환은 사용량 제한·서비스 가용성 문제일 때만 한다. 테스트 실패·리뷰 지적은 수정 대상이다. 다른 모델로 바꿔 통과를 구하지 않는다.
2. Cursor의 Grok과 grokbuild의 Grok은 같은 모델로 취급한다. 실행 경로가 달라도 독립 리뷰로 세지 않는다. 여러 모델이 작성에 참여했다면 그 작성 계열들을 모두 리뷰에서 제외한다.
3. 인계할 때 기존 브랜치·커밋·미커밋 변경·시험 결과·남은 작업을 보존한다. 이전 실행의 쓰기를 중단한 뒤 다음 빌더가 이어받는다.
4. 리뷰는 대상 커밋에 고정한다. 이후 코드가 바뀌면 변경분을 다시 검토한다. 독립 리뷰어가 없으면 병합을 기다린다.
5. 개인정보 경계, 계산 의미, 공통 계약·릴리스 구조를 바꾸는 PR은 10개를 기다리지 않고 감리한다.
6. 감리 담당자가 직접 작성한 변경은 다른 모델 계열이 검토한다.
7. 코드 리뷰와 보험 지식 검수는 별도다. 개발 역할표를 약관 검수 모델 구성의 승인으로 해석하지 않는다.
8. 위 구성은 역할·전환 정책의 승인이다. 실제 모델 지원 여부와 인증·사용량은 환경에서 확인하고, 지정 모델을 다른 모델로 몰래 대체하지 않는다.

## 3. 규칙을 실행 절차로 옮긴 안 (구현자 초안)

### 3.1 한 작업의 흐름

1. **계약:** 설계 담당(Fable, 불가 시 GPT Astra)이 작업 묶음(WP)마다 범위·계약·완료 기준을 고정한다([구현 계획](../구현계획_검토본.md) §14).
2. **작성:** 메인 빌더(Sonnet)가 WP 브랜치에서 구현하고 PR을 연다. PR 본문에는 WP ID, 작성에 참여한 모델과 실행 경로, 대상 SHA, 실행한 시험과 결과를 적는다.
3. **독립 리뷰:** 빌더 우선순위 순서에서 작성 계열을 뺀 첫 번째 가능한 모델이 대상 SHA에 고정해 리뷰한다. 리뷰 기록에는 리뷰어 모델·실행 경로·SHA를 남긴다.
4. **수정:** 지적과 CI 실패는 **같은 작성자**가 고친다(규칙 1). 새 SHA에서는 변경분을 다시 리뷰한다(규칙 4).
5. **병합:** 사람(사용자)이 병합한다. 자동 병합은 없다. 독립 리뷰어가 없으면 기다린다.
6. **감리:** 병합된 구현 PR이 10개 쌓일 때마다 감리를 연다. 규칙 5의 PR은 병합 전에 즉시 감리한다.

### 3.2 백업 전환 절차

| 단계 | 하는 일 | 남길 기록 |
|---|---|---|
| ① 판정 | 전환 사유가 사용량 제한이나 서비스 장애인지 확인한다. 시험 실패·리뷰 지적이면 전환하지 않는다 | 오류 메시지 원문, 시각 |
| ② 쓰기 중단 | 현재 실행을 멈추고 더 쓰지 않음을 확인한다 | 마지막 쓰기 시각 |
| ③ 보존 | 미커밋 변경을 같은 브랜치의 WIP 커밋으로 남기고 푸시한다. 시험 결과와 남은 작업 목록을 인계 기록에 적는다 | 브랜치, SHA, 시험 로그 위치, 남은 작업 |
| ④ 인계 | 다음 순위 빌더가 같은 브랜치·같은 SHA에서 시작한다 | 새 담당 모델·실행 경로 |
| ⑤ 리뷰 제외 갱신 | 작성 참여 계열 목록에 새 담당 계열을 더한다 | PR 본문의 작성 계열 목록 |
| ⑥ 마지막 순위까지 실패 | 작업을 보존한 채 대기한다. 다른 모델로 몰래 대체하지 않는다 | 대기 사유 |
