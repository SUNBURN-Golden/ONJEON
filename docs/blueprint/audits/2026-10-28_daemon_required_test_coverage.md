# Audit 3: T-OP-00 필수 시험 33개와 실제 테스트 연결

범위: `audit3-daemon-required-test-coverage`. 단일 기준은 `docs/BLUEPRINT.md`, 출시 완료 판정은 [09 제품 목적 대응표](../proposals/설계검토_결과/09_제품목적_대응표.md)다. 이번 수정은 T-OP-00 개발 도구의 검사·회귀 증거이며 제품 출시 완료 판정이 아니다.

지적 당시 `Coverage`는 필수 ID 33개 중 16개만 검사했고 설계 묶음의 `실행로그_dry_run.txt`도 16개 실행·17개 미실행과 옛 STATIC 14개를 기록했다. 현재 기준 코드에는 이미 전체 시나리오와 정본·모의 목록·실제 레지스트리의 양방향 대조가 있다. 이를 유지하면서 남아 있던 설계 검사와 기록의 빈틈을 닫았다.

- `spec_check.py` G12b: 정본 T-OP-00의 필수 ID를 `CORE_SCENARIOS`·`FLOW_SCENARIOS`의 실제 등록과 대조한다. 소스를 실행하지 않고 AST로 등록 목록과 지역 함수 정의를 확인한다. 미등록·누락·중복·빈 목록·함수 삭제·형식/읽기 오류·모의 목록 불일치를 실패로 처리한다. 기존 G12의 과제 필드 존재 검사와 구분한다.
- `dry_run.run_scenario`: 검사가 0개인 빈 함수는 실패다. `--require-all` 없이도 적용한다. 빈 함수로 바꾼 33개 필수 ID와 무표기 시나리오의 34개 사례가 수정 전 통과했던 문제를 재현하고 차단했다.
- 회귀 시험: 필수 ID 각각의 등록 삭제 33개·함수 정의 삭제 33개·빈 실행 33개를 검사한다. 기존 `Coverage`는 정본 33개, CLI 선택, unittest 메서드, 실제 통과 결과를 연결한다. 기존 양방향 검사는 누락·미등록·중복을 거부한다.
- CI `design-specs`: 설계 검사 뒤 `--scenario all --require-all --quiet`을 실행한다. 정적 함수 존재 검사와 실제 실행 성공을 함께 확인한다.
- 설계 묶음의 dry-run 로그를 현재 전체 실행으로 재생성했다. STATIC은 정적 검사 13개와 설명 키 변조·삭제 비교 2개로 15개다. `Coverage`가 이 로그의 출력을 현재 실행과 대조하므로 다시 16개만 기록하거나 검사 수가 낡으면 시험이 실패한다. 공용 로그 두 개도 현재 소스 해시로 갱신했다.

검증 명령·원시 로그·ID별 실행 대응·소스 해시는 [실행 증거](../../../tools/evidence/audit3-daemon-required-test-coverage/README.md)를 참조한다. AST 대조는 등록 형식과 함수 존재를 검사하며 함수의 의미를 증명하지 않는다. 동작은 실제 모의 시나리오의 기대·실제 값 검사와 변이 회귀로 확인한다. 실제 제공자 실행·생산 데이터·소비자 화면·출시 관문을 이번 검증의 완료 범위로 세지 않는다.
