## 2. "위 다섯 검토 사항"의 해석과 점검

사용자 지시의 "위 다섯 검토 사항도 함께 점검하세요"는 바로 앞에 나열된 **작성 항목 1~5(전체 코드 설계, 구현 계약, 실행 작업 명세, 자동 개발 명세, VM 실행 준비)** 각각을 스스로 점검하라는 뜻으로 해석했다. 다른 해석(구현계획 §16의 1~5)도 가능하므로 §1에서 그 여덟 항목을 모두 다뤘다. 아래는 작성 항목 1~5의 자기 점검이다.

| 작성 항목 | 점검 질문 | 결과 |
|---|---|---|
| 1 전체 코드 설계 | 전 기능(통합안 §2)이 구역에 배정되었나. 온톨로지 검증 흐름과 맞나. 재사용 범위가 파일 근거를 갖나 | 배정 표(01 §3)에 기능 11개. 흐름 5단계가 결과.txt 질문 11개와 대조됨. 재사용 표 17행에 경로·줄 수·근거. **미확인:** Flutter·Next.js·Axum 골격은 없으므로 재사용 판단 대상이 아님 |
| 2 구현 계약 | C-01~C-20 전부 다뤘나. 빠진 계약을 더했나. 각 계약의 차단 결정이 좁은가. 시험 전용 유지·승격 경로가 지름길 없이 닫히나 | C-21~C-26 추가. 차단은 §9 표에서 "~만"으로 좁힘. 승격 경로 P1~P8과 차단 B1~B8. **미확인:** DB 제약의 실제 SQL은 T-CT-05에서 작성 |

## 3. 설계 담당 선택 항목 — [설계 담당 결정(감리 대상)]

정본과 토의 원칙 안에서 정했다. 정본과 충돌하는 선택이 필요한 곳은 없었다. 모두 즉시 감리 대상이다.

### 3.1 D-05 세 흐름을 4탭 안에 두는 방식

| 토의 흐름 | 배치 | 트윈 | 진입 제목(토의 21차 방향) |
|---|---|---|---|
| A 가상 탐색 | **만약에** 탭 → 상황 선택 → 상품 트윈(공개, `POST /v1/scenarios`) | 상품 트윈 | "이런 일이 생기면 어떻게 되나요" |
| B 내 계약 확인 | **홈**(담보 요약 목록) + 계약 상세 | 개인 계약 트윈(계정·확인된 스냅샷 있을 때) | "내 보험 이해하기" |
| C 실제 사건 확인 | **만약에** 탭의 두 번째 진입 제목 → 개인 계약 트윈 + 확인한 사실(`POST /v1/evaluations`) | 개인 계약 트윈 | "실제로 일어난 일 확인하기" |
| 세 진입점(예시로 둘러보기 / 처음부터 준비하기 / PDF 올리기) | 첫 실행 온보딩과 홈 상단. 탭이 아님 | — | 정본 그대로 |

근거: 정본의 4탭(홈·만약에·내 설계·내 정보)과 세 진입점·화면 목록을 바꾸지 않는다(BLUEPRINT §7.1, 제3부 §44.1). A와 C는 같은 계산 경로(입력 단계 → 엔진)를 쓰고 다른 점은 트윈(상품 vs 개인 계약)과 사실의 출처(가정 vs 확인)이므로 같은 탭에서 진입 제목으로 가른다. 다섯 번째 탭을 만들지 않는다. C의 사건 사실 입력 범위는 D-06·D-07에 따른다(사진·진단서 없음, ADR-0005 유지).

### 3.2 D-09 공개 지식 데이터 모델과 온톨로지 저장 방식

| 항목 | 선택 | 근거·경계 |
|---|---|---|
| 판매본 식별 | `SalesConfiguration`은 증거로 묶은 내부 ID(ulid). 회사·이름·코드·기간·파일 어느 조합도 자연 키가 아니다. 공시 행·회사 목록 행과의 대응은 `disclosure_of`·`uses_document` **주장**이다 | 조사 H1·H5·H7(상품명·코드 ≠ 식별자). 이름 유사도 병합 금지(SYSTEM_CONTRACT §5) |
| 연결·병합의 되돌림 | 두 판매본이 같다는 판단은 `same_configuration_as` 주장(새 관계, 대칭, 전이 없음)으로만 하고, 틀리면 supersedes로 정정한다. 노드를 물리적으로 합치지 않는다 | 통합안 §8.3 "연결·병합은 되돌릴 수 있다" |
| 약관 판 (수정판, onto-0.2 반영) | 이전 판의 "문서 판 = 원본 해시 + 문서 역할"은 회귀였다(토의 10~12차 보완안 §3.1이 이미 원본·구획·판·계열을 나눴다). 수정: `RawAsset`(관측) → `DocumentSegment`(원본+쪽 범위+역할+구획 규칙 판, 본문 지문) → `TermsEdition`(본문 판, 파일 해시 아님) → `TermsLineage`. 관계 `segment_of`·`in_segment`·`realizes`·`edition_of`·`in_edition`·`uses_edition`(적용 기간 **양끝 포함**). 지문은 근거 중 하나이고 판 동일성 승인은 ReviewDecision으로만(02 §1.3a) | 검증 D1·D2 통과(이 세션 재실행). `applicable_config()` 양끝 포함 |
| 구성 요소 | `Component`(종·형·심사 유형·특약 선택)에 `determined_by ∈ {user_choice, disclosure_underwriting, mandatory, dependent, in_contract_event}`(토의 10~12차 다섯 방식) | 어휘 새 축 후보. T-CT-02 |
| 주장과 FieldAssertion | **한 테이블 통합**(02 §1.2) | K 검사 단일 집합, 릴리스 = 주장 ID 집합 |
| 온톨로지 판 정책 | `onto-MAJOR.MINOR`. MINOR 추가만, MAJOR는 의미·제약 변경 → 전 A-box 재검사 + 즉시 감리. 릴리스 manifest가 onto 판을 고정 | 02 §5 |
| 범위 관계의 코드 우주 | **공식 코드 체계 목록**(`CodeSystem` 노드: 체계·개정차수·고시·시행일·전체 코드 목록 RawAsset 해시)이 있을 때만 계산값을 accepted로 둔다. 없으면 `not_comparable`. 픽스처 우주(3자리 + 별표 세부)는 `fixture_only` | 설계안 §10.3 "코드 범위는 근사". K12를 약하게 하지 않음. **조사 항목:** KCD 9차 전체 세부 코드의 공식 출처 |

### 3.3 D-10 개인 계약 상태 축·결과 상태 네 축의 어휘 반영

02 §1.4의 표대로 새 축 `fact_source`, `fact_kind`, `confirm_party`, `usage_restriction`과 `freshness`에 더하는 `knowledge_freshness` 값 `withdrawn`을 어휘 정본에 추가한다(T-CT-02, BLUEPRINT §6·§10.2 절차). 기존 축(`policy_holdings_status`, `contract_version_match`, `value_state`, `display_status`, `freshness`)은 재사용하고 중복 축을 만들지 않는다. 사용자 결정은 필요하지 않다(정본 절차 안). 즉시 감리.

### 3.4 D-15 뷰모델 근거 종류·적용 확인 필드

`amounts[].source` 4종 계약을 유지하고 `evidence_kind ∈ {terms, summary, disclosure, user_input}`과 `applicability ∈ {applies, not_applies, unverified}`를 **추가**한다(02 §2.4). 큰 금액 자리에는 `source=scenario:` **그리고** `evidence_kind=terms`만 올린다. 요약서 근거는 `summary`+`unverified`로 근거 영역에만 둔다. 24차 시안의 ADR-0014 충돌(요약서를 확인된 조건처럼 표시)은 이 두 필드로 구조적으로 막힌다.

## 4. 온톨로지(C-20) 검토 — 개념·관계·제약·책임 경계

### 4.1 재실행 결과

(재검토 9554c96 뒤, 구현자 수정분) 기준 릴리스가 `rel:case-r26`(in_edition 주장 2개 추가, 입력 단계 판 case-0.2; r24·r25는 case-0.1 고정값 그대로 이력 재현용)으로 바뀌었고 K16(근거 묶음), K13(원시 보존·비교 자격), resolve(연결 검증)가 고쳐졌다. 구현자 실행 결과 `검증/결과.txt`: "r24 K1 위반 재현 True · r25·r26 위반 0 True · 범위 관계 narrower True · 질문 11/11 · 제약 자체 시험 15/15 · 릴리스·문서 모델 시험 21/21 · 전체 통과"(D4·D5·D8·D9·E1~E4·P1 회귀 포함). 재검토 e02755a S01 뒤 구현자 재실행: "… 릴리스·문서 모델 시험 23/23 · 전체 통과"(S01·S01b 추가, 적용 판매 구성 복수일 때만 모호함). 재검토 10f470c T01 뒤: "… 릴리스·문서 모델 시험 24/24 · 전체 통과"(T01: 범위 미확인 연결 보류·무관한 특약 허용·경쟁 판 보류·순서 독립). 설계 담당은 이 판에서 재실행하지 않았고(러너 재빌드 필요) 구현자 기록을 인용한다. 02 §1.3(input_stage_edition)·§1.3a·§1.7이 이 결과를 따른다.

(onto-0.1, ffbcaf6 시점) 이 세션에서 `cargo build`(runner) 후 `python3 -I ontology_check.py`를 다시 실행했다. 출력이 `검증/결과.txt`와 바이트 단위로 동일했다(질문 11/11, 자체 시험 13/13).

(onto-0.2, 수정판) 구현자가 보강한 검증기를 다시 실행했다. 종료 코드 0, 출력이 갱신된 `검증/결과.txt`와 **바이트 단위로 동일**: "r24 K1 위반 재현 True · r25 위반 0 True · 범위 관계 narrower True · 질문 11/11 · 제약 자체 시험 15/15 · 릴리스·문서 모델 시험 12/12 · 전체 통과". 릴리스 고정(I1~I7: 새 주장·참조 노드·적용 관계 교체 뒤 재현 동일, 사용 제한 공지는 영향 담보만 차단)과 문서 모델(D1~D5: 구성 전부 같은 지문, 원본 해시·지문 일치는 승인 아님, 별표 다름·빠짐은 다른 판)이 동작 검증됐다. 약관 해석의 정확도는 이 결과가 보증하지 않는다(설계안 §10.3). 이것은 토의 자료 수준 검증이며 서비스 코드의 검증이 아니다.

### 4.2 충분한 것

- 주장의 범위·시점 넷·근거 역할·정정 사슬·공백/작업 분리는 정본 L5의 빈 곳(관계 의미·적용 시점·제약)을 채운다. ADR-0014 §1(C0 근거는 약관)을 K1로, 불변 원칙 6을 "최신 약관 자동 적용 금지"로, I7을 K13으로, 개인 식별자 금지를 K8로 기계 검사로 옮긴 점이 적합하다.
- 책임 경계(설계안 §11)는 D15와 맞는다. 엔진은 온톨로지를 조회하지 않고 입력 단계가 판정값과 근거를 넘긴다. 검증의 엔진 입력에 `dx_in_category`만 있는 것이 그 증거다.

### 4.3 수정 필요 — [설계 담당 결정(감리 대상)]

| 번호 | 문제 | 수정안 |
|---|---|---|
| O-1 | T-box `relations`가 `ParameterTable`을 치역으로 쓰지만 `classes`에 없다 | 클래스 `ParameterTable`(키 구간·열린 구간 관측 시각·원문 해시) 추가. 관계 `parameter_from`의 치역으로 명시 |
| O-2 | 범위 관계 계산의 코드 우주를 담는 개념이 없다 | 클래스 `CodeSystem`(체계·개정차수·고시·시행일·전체 코드 목록 RawAsset 해시) 추가. `CodeSet.code_system → CodeSystem`. K12는 두 범주의 CodeSet이 같은 CodeSystem을 가리키고 그 목록이 있을 때만 "계산 가능" |
| O-3 | (onto-0.2에서 해소) ReviewDecision은 02 §1.2 `review_decision_id`·`chk_accepted_needs_decision`과 K14의 `decision.by=review_decision`으로 개념 안에 들어왔다. 이전 판에서 'K15'로 제안했던 내용은 T-box K15(릴리스 고정)와 번호가 겹치므로 폐기한다 | 추가 조치 없음. T-box 번호가 단일 기준이다 |
| O-4 | `excludes_codes`의 치역이 DiseaseCategory를 포함해 범주 그래프가 생기지만 순환 검사는 K4(narrower)만 있다 | **K17 후보(제안, T-box에 없음):** `includes_codes`/`excludes_codes`로 이어지는 범주 그래프에 순환이 없다. 이전 판에서 함께 적었던 '같은 역할 문서의 적용 구간이 겹치면 Conflict'는 **철회**한다(F02: 통합약관과 개별 특약 파일, 재압축본이 정상적으로 겹친다. 충돌은 동일 적용 범위에서 양립 불가한 주장인지로만 판단) |
| O-5 | K8이 문자열 접두어 검사다. 공개 스키마에 타입 없는 텍스트가 있으면 우회될 수 있다 | DB 트리거(02 §1.2) + 참조 열을 타입 있는 FK로. 접두어 검사는 보조로 유지 |
| O-6 | (onto-0.2에서 해소) K1 문구가 구조 주장(`uses_edition`·`realizes`·`disclosure_of`)의 관측 근거 예외를 명시한다 | 추가 조치 없음 |
| O-7 | `valid_from/valid_to` 포함 여부가 문서에 없다 | 양끝 포함으로 명시(검증 구현과 일치). 가입일이 `valid_to`와 같으면 그 판 |
| O-8 | `judged_as_of`가 CodeSet 속성과 주장 time 필드에 둘 다 있다 | CodeSet의 판정 시점 규칙은 "어느 시점의 코드 체계로 판정하나"(예: 진단일), 주장의 `judged_as_of`는 "이 주장이 전제한 판정 시점". 이름을 `code_judgement_rule`과 `judged_as_of`로 나눈다 |
| O-9 | `same_configuration_as`(판매본 동일성) 관계가 없어 되돌릴 수 있는 병합 수단이 없다 | 관계 추가(대칭, 전이 없음, 양쪽 증거 필수) |
| O-10 | 설계안 §13의 "정본 반영 위치"가 BLUEPRINT §5.1 객체 추가를 포함한다 | 정본 변경이므로 **[사용자 결정 필요]**(D-21 경로). 이 묶음에서는 `packages/schemas/ontology/tbox.json`(onto-0.1)로만 옮기고 정본은 고치지 않는다 |

### 4.4 설계안 §12 선택 항목의 선택안

§3.2에 포함: 저장 통합(한 테이블), 판 정책(onto-MAJOR.MINOR), 코드 우주(공식 CodeSystem 필수), 입력 단계 계약(C-26). 조사 항목(KCD 9차 공식 목록 출처, 다른 회사 정의 표현 다양성)은 T-KN-01·T-KN-08의 입력 조사로 둔다.

## 6. 이 묶음이 하지 않은 것

- 규제 검토(D-12 원문 재배포, D-18 적용 요건, O10). **규제 검토 대상, 이 문서는 판단하지 않음.**

- 코드 작성·커밋·푸시·가동·병합·배포·문의 발송.
