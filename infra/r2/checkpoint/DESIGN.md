# 원장 체크포인트 설계

## 문제

원장은 `ledger/v1/<순번>.json` 기록의 해시 연결이다. 실행마다 모든 기록을 읽고 검증하므로 읽기(Class B)가 기록 수에 비례하고, 입장 한도(Class B 110)에 맞춰 `max_ledger_records`가 100으로 묶여 있다. 100건에 도달하면 새 실행을 거부하고 101번째 쓰기도 막는다(BUDGET.md §5). 기록은 지우지 않으므로 이대로면 사용량이 쌓이는 만큼 도구가 못 쓰게 된다.

## 해법

체크포인트는 순번 1..N 기록의 **요약**이다. 한 번만 쓰는 객체 `checkpoint/v1/<N 10자리>.json`(`If-None-Match: *`). 실행은 가장 새 체크포인트 하나와 그 뒤의 기록만 읽는다.

| 필드 | 뜻 |
|---|---|
| `seq`, `tail_sha256` | 요약이 덮는 마지막 기록의 순번과 그 파일의 SHA-256. 뒤따르는 첫 기록의 `prev_sha256`이 이 값과 이어져야 한다 |
| `genesis_sha256` | 기록 1의 해시. 정책이 고정한 값과 같아야 한다 |
| `policy_sha256` | 알려진 정책이어야 한다 |
| `prev_checkpoint` | 앞 체크포인트의 순번과 파일 해시(체인). 첫 체크포인트는 null |
| `month`, `at` | 쓴 시각. 이 달 이전의 달은 요약에서 접힌다 |
| `state.totals` | (달, 작업)별 사용량. 정산된 예약은 측정값(예약 이하), 접힌 예약은 전액, 원장 이전 사용량 포함. 체크포인트의 달 이전은 `past`(작업별 전체 합)로 접는다. 달 한도 항목은 그 달에만 전역에 들어가므로 정확하다 |
| `state.open` | 아직 정산되지 않은 예약(24시간 이내). 뒤에 오는 정산 기록이 찾을 수 있게 남긴다 |
| `state.settled_runs` | 정산이 끝난 실행의 입장 수(달·작업별). 입장 목록(LIST)에서 이들을 빼고 나머지를 입장 한도로 센다 |

24시간(`OPEN_GRACE_S`)보다 오래된 미정산 예약은 죽은 실행이다(실행 시간 제한이 SIGALRM으로 강제된다). 전액으로 접고, 나중에 도착한 정산은 무시한다(사용량이 줄지 않는 쪽).

## 읽기 비용

| 단계 | 요청 |
|---|---|
| 체크포인트 | LIST `checkpoint/v1/` 1, GET 1 |
| 그 뒤의 기록 | 1000개 단위 블록 접두어 LIST 1(블록이 끝까지 차면 다음 블록까지), 기록마다 GET 1 |
| 뒤따르는 기록이 없을 때 | 체크포인트가 덮는 마지막 기록을 GET 1회로 확인(삭제·교체 감지) |

체크포인트 이후 기록이 `max_ledger_records`(100)에 도달하면 일반 실행을 거부한다(`>=`). 쓰기 직전에도 `count - base_seq >= limit`를 검사하여 예약·정산 모두 101번째 기록을 보내지 않는다. 99건에서 예약이 마지막 자리를 쓰면 정산은 실패하고 예약 전액을 유지한다. 즉 한도 100은 "체크포인트 간격 상한"이 된다. 체크포인트가 없으면 전체 LIST에 같은 상한을 적용한다. 감사용 `read(full=True)`만 읽기 상한을 우회하며 쓰기 상한은 우회하지 않는다.

단, `checkpoint` 명령의 세션만 읽기 상한을 넘는다(`Ledger.over_limit_ok`, 세션 `purpose="checkpoint"`). 쓰기 상한은 모든 세션에 적용한다. 체크포인트를 **예약 전에** 입장 한도 안에서 저장한 뒤, 새 체크포인트를 읽어 확인하고 예약·정산을 쓴다. 100건에서는 체크포인트 100 → 예약 101 → 정산 102가 되어 다음 실행은 뒤따르는 기록 두 건만 읽는다. 체크포인트 PUT·크기 검사·확인 읽기가 실패하면 예약이 없으므로 정산도 쓰지 않는다. 실패한 실행의 입장은 전액 계상되지만 원장 뒤받침은 늘지 않아 저장소가 복구되면 다시 체크포인트를 시도할 수 있다. 월별 입장·비용 한도는 그대로 적용된다.

복구 세션도 전체·작업 caps와 남은 입장 몫을 먼저 검사한다. 검증한 기록과 입장 목록을 재사용하여 체크포인트 쓰기 전 불필요한 재읽기를 없앴다. 100건에서 예약 완료까지 Class A 7·Class B 103(기존 체크포인트가 있으면 Class B 104)으로 입장 한도 A 8·B 110 안이다. `audit` 세션은 읽기·쓰기 상한을 모두 지킨다. 100건에서 감사가 거부되면 먼저 체크포인트를 쓴 뒤 감사를 실행한다. 감사의 전체 이력 읽기(`read(full=True)`)는 예약 후에만 수행한다. 비용을 아끼려면 한도 전에 여유를 두고 체크포인트를 쓴다.

## 쓰기

`python3 -I tools/r2_budget.py checkpoint --job infra/r2/jobs/initial-119.json`. `status` 프로필 실행이며, 순서는 입장 → 기록 검증·예산 검사 → 체크포인트 저장·확인 → 예약 → 정산이다. 체크포인트 저장까지 계량기는 입장 한도를 유지하며 자료 접근은 허용하지 않는다. 8192바이트 크기 한도와 `If-None-Match`를 유지한다. 같은 순번이 이미 있으면 내용(시각 제외)이 같을 때만 `already_present`, 다르면 중단한다. CLI는 입장 단계에서 저장한 결과를 출력하며 체크포인트를 다시 쓰지 않는다. 자신의 예약·정산은 체크포인트 뒤 기록이 된다. 빈 원장이나 이미 전부 요약된 원장은 `nothing_new` 뒤 예약·정산을 진행한다. 예약 경쟁에서 지면 새 체크포인트 기준으로 다시 읽고 한도를 재검사한다.

## 검증

`python3 -I tools/r2_budget.py audit --job …`(`verify` 프로필 실행)이 모든 체크포인트를 원래 기록에서 다시 계산해 비교한다: 마지막 기록 해시, genesis, 체크포인트 체인, 요약 내용. 요약을 낮춰 쓴 체크포인트는 "summary differs"로 잡힌다. 매 실행은 가장 새 체크포인트의 모양·정책·genesis·뒤 기록과의 연결만 확인하므로, **위조된 체크포인트를 쓸 수 있는 토큰**에는 audit와 버킷 잠금(O14, `checkpoint/v1/`·`ledger/v1/`)이 보완 수단이다. audit는 기록을 전부 읽으므로 `verify` 프로필(Class B 400)로 읽을 수 있는 기록 수에서만 돈다.

## 같음 시험

`Equivalence`: 정산됨·미정산·죽은 예약·지난 달·원장 이전 사용량·다른 작업·거부된 실행의 입장이 섞인 원장에서, 모든 분할 위치(과 체크포인트 둘의 연쇄)에 대해 "체크포인트 + 이후 기록"의 사용량이 "전체 기록"의 사용량과 같고 달이 바뀐 뒤에도 같다.

## 한계

- 입장 LIST·원장 LIST의 비용은 남는다(키 1000개당 Class A 1). 블록 접두어로 체크포인트 뒤만 본다.
- 체크포인트 크기: 작업·달·미정산 예약 수에 따라 늘며 8192바이트 상한. 넘으면 쓰기를 거부하므로 요약 형식 개정이 필요하다(현재 실제 크기는 수백 바이트).
- 접힌 죽은 예약의 늦은 정산은 무시한다. 실행이 24시간 넘게 도는 작업은 만들지 않는다(작업 프로필 최대 3600초).
- 위조·삭제는 토큰이 삭제·쓰기 권한을 가지는 한 막지 못한다. 감지(audit)와 O14 잠금이 보완한다.
