# ADR-0011 설계도 채택과 문서 위계

상태: 확정(사용자 요청) | 날짜: 2026-10-09 | 근거: `docs/BLUEPRINT.md`

## 맥락

사용자는 구현이 산으로 가지 않도록 설계도를 먼저 탄탄히 하길 요청했다. 점검 결과 세 가지 위험이 있었다.

1. 결정이 여러 번 바뀌면서 ADR 10건과 4,300줄 안팎의 문서에 현행 결정과 대체된 결정이 섞였다. 제3부 §56처럼 낡은 요약이 남아 있었다.
2. 같은 주제의 명세가 두 벌 생겼다(소비자 흐름과 화면 부록, 가격 계약과 가격 부록).
3. 구현은 규칙 엔진(L6)부터 진행됐고, 엔진이 표현할 내용을 정하는 데이터 계층(L0~L5)은 아직 없다.

## 결정

1. `docs/BLUEPRINT.md`를 구현의 단일 기준으로 채택한다. 위계는 불변 원칙 → 설계도 → 이후 ADR → 계약 문서 → 배경 문서다.
2. 모든 기능은 정보 비대칭 A1~A7 중 하나에 연결돼야 한다.
3. 상태값은 설계도 §6 레지스트리가 정본이며 코드는 `packages/schemas`에서 생성한다.
4. 설계 불변식 I1~I18은 테스트·정적 검사로 강제될 때만 구현으로 본다.
5. 구현 순서는 M1(데이터 척추) → M2(실제 문서 1건으로 전 계층 관통) → M3~M6이다. 대상 범위는 줄이지 않는다.
6. 모든 PR은 템플릿에 해당 A·Q·L·I·M을 적는다.

## 결과

- 새 결정은 ADR로 남기고 설계도 §7을 갱신해야 한다.
- 제3부와 v0.3은 배경 문서가 된다. 설계도와 충돌하면 설계도를 따른다.
- 다음 구현 작업은 엔진 기능 추가가 아니라 M1이다.
